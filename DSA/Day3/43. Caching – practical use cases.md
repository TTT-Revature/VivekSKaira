# Caching: Practical Use Cases

## 1. Overview
**Caching** is the technique of storing copies of frequently accessed data or expensive computation results in a fast, temporary storage layer (such as CPU cache, process RAM, or an in-memory distributed store like Redis) so future requests can be served without repeating slow I/O, network calls, or heavy CPU work.

### Core Request Flow (Cache Hit vs. Cache Miss)
```text
                         +------------------+
                         |   Application    |
                         +--------+---------+
                                  |
                         1. Check Cache(key)
                                  |
                                  v
                     +------------+------------+
                     |       Cache Layer       |
                     |  (RAM / LRU / Redis)    |
                     +---+-----------------+---+
                         |                 |
                [ Cache HIT ]       [ Cache MISS ]
                (< 1 ms)            (slow path)
                         |                 |
                         v                 v
                 Return Cached     2. Fetch from Primary
                    Result         (DB / External API / CPU)
                                           |
                                           v
                                   3. Store in Cache + TTL
                                           |
                                           v
                                   Return Fresh Result
```

### Fundamental Trade-Offs
Every caching layer balances three competing dimensions:
1. **Latency vs. Memory Cost:** Fast memory (RAM) is orders of magnitude faster than disk or network I/O, but significantly more expensive and capacity-bounded.
2. **Speed vs. Data Freshness (Staleness):** Cached copies can drift out of sync when underlying data changes unless bounded by expiration policies or explicit invalidation.
3. **Hit Ratio vs. Code Complexity:** Adding a cache introduces serialization, eviction, and failure-handling logic that is only justified when the **cache hit ratio** is high:

$$\text{Hit Ratio} = \frac{\text{Cache Hits}}{\text{Cache Hits} + \text{Cache Misses}}$$

## 2. Core Caching Patterns (Read and Write Strategies)

### 1. Cache-Aside (Lazy Loading)
The application manages both the cache and the primary data store directly:
* **Read Path:** Check the cache first; on a miss, query the database, write the result into the cache with a Time-to-Live (TTL), and return it.
* **Write Path:** Update the primary database first, then **invalidate (delete)** the stale cache key so the next read reloads fresh data.

```text
Read Miss:   App --(1. miss)--> Cache
             App --(2. query)-> Database
             App --(3. set)---> Cache

Write Flow:  App --(1. write)-> Database
             App --(2. del)---> Cache (invalidate stale entry)
```

### 2. Read-Through and Write-Through
* **Read-Through:** The application queries only the cache provider; on a miss, the cache itself fetches data from the underlying database, populates its store, and returns the value.
* **Write-Through:** Every write goes synchronously to the cache, which immediately writes it to the primary database before acknowledging success—guaranteeing strong consistency at the cost of higher write latency.

### 3. Write-Behind (Write-Back)
The application writes updates directly to the cache and receives an immediate acknowledgment, while the cache flushes batched writes asynchronously to the database in the background. Ideal for write-heavy telemetry or counters, but risks data loss if the cache node crashes before flushing.

### Pattern Comparison

| Pattern | Consistency | Read Latency | Write Latency | Resilience to Cache Crash | Primary Use Case |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Cache-Aside** | Eventual (TTL / invalidation) | Fast on hit; 2 hops on miss | Fast (DB write + key delete) | High (falls back to DB) | General-purpose read-heavy web apps and APIs |
| **Read-Through** | Eventual (TTL / invalidation) | Fast on hit; 2 hops on miss | Standard DB write | High (loads from DB) | Simplified app code with dedicated cache middleware |
| **Write-Through** | Strong (cache always current) | Always fast for written keys | Slower (sync cache + DB write) | High (DB always up to date) | Configuration stores, user profiles, financial ledgers |
| **Write-Behind** | Eventual (async flush) | Always fast | Fastest (in-memory only) | Low (unflushed writes at risk) | High-throughput analytics, view counters, IoT ingestion |

## 3. Practical Use Cases in Software Engineering

| Domain / Use Case | What Is Cached | Typical Cache Layer | Expiration / Invalidation Strategy |
| :--- | :--- | :--- | :--- |
| **1. CPU-Bound & Recursive Memoization** | Pure function return values, dynamic programming subproblems, parsed ASTs/regexes | Process memory (`@functools.lru_cache`, `@functools.cache`) | Bounded `maxsize` with LRU eviction; process lifetime |
| **2. Database Query & ORM Caching** | Hot product catalogs, user profiles, leaderboards, aggregation queries | Distributed cache (Redis, Memcached) | Cache-aside with short TTL (e.g., 60s–300s) + explicit delete on write |
| **3. External API & Microservice Responses** | Geocoding lookups, currency exchange rates, weather feeds, LLM/embedding responses | Redis or local SQLite persistent cache | Domain-aligned TTL (e.g., 5 min for rates, 24 hr for geocoding) |
| **4. Session State, Auth & Rate Limiting** | User session payloads, revoked JWT deny-lists, sliding-window API request counters | Distributed in-memory store (Redis) | Fixed TTL matching session/token expiry or rate-limit window |
| **5. HTTP Edge & CDN Caching** | Static assets (JS, CSS, images), public `GET` API responses, rendered HTML fragments | Browser cache, Reverse Proxy (Nginx/Varnish), CDN | `Cache-Control: max-age=...`, `ETag` conditional validation, versioned filenames |
| **6. DNS & Feature Flag Resolution** | Domain-to-IP records, feature toggles, application config | OS resolver, local worker memory + pub/sub invalidation | DNS record TTL; push invalidation or short polling |

## 4. Eviction Policies and Expiration

Because cache memory is finite, a full cache must decide which existing entry to discard when inserting a new one:

* **LRU (Least Recently Used):** Evicts the item that has gone the longest without being accessed. Implemented in $O(1)$ time using a **Hash Map + Doubly Linked List** (or `collections.OrderedDict` in Python).
* **LFU (Least Frequently Used):** Evicts the item with the lowest access count. Effective for stable popularity distributions, though older popular items can linger unless frequency counters decay over time.
* **FIFO (First-In, First-Out):** Evicts the oldest inserted entry regardless of access frequency; simplest to implement but lower hit rates than LRU.
* **TTL (Time-to-Live):** Attaches an expiration timestamp (`now + ttl_seconds`) to every entry so stale data expires automatically even without explicit write invalidation.
  * **Fixed (Absolute) TTL:** Expires strictly `T` seconds after creation—guarantees a hard upper bound on staleness.
  * **Sliding (Idle) TTL:** Resets the expiration timer on every cache hit—ideal for active user sessions.

## 5. Practical Python Implementations

### 1. In-Process Memoization with `functools` (`@cache`, `@lru_cache`, `@cached_property`)
Python's standard library `functools` module provides thread-safe, C-accelerated decorators for pure functions and lazy instance attributes:

```python
from functools import cache, cached_property, lru_cache


@cache
def edit_distance(word_a: str, word_b: str) -> int:
    """
    Unbounded memoization (equivalent to @lru_cache(maxsize=None)).
    Reduces exponential O(3^(m+n)) recursion to O(m * n) dynamic programming.
    """
    if not word_a:
        return len(word_b)
    if not word_b:
        return len(word_a)
    if word_a[0] == word_b[0]:
        return edit_distance(word_a[1:], word_b[1:])
    return 1 + min(
        edit_distance(word_a[1:], word_b),      # Delete
        edit_distance(word_a, word_b[1:]),      # Insert
        edit_distance(word_a[1:], word_b[1:]),  # Replace
    )


@lru_cache(maxsize=256)
def fetch_tax_rate(country_code: str, region_code: str) -> float:
    """
    Bounded LRU memoization for expensive pure lookups.
    Evicts least recently used keys once 256 entries are stored.
    """
    rates = {("IN", "TN"): 0.18, ("US", "CA"): 0.0725, ("DE", "BY"): 0.19}
    return rates.get((country_code, region_code), 0.0)


class SalesReport:
    """Demonstrates @cached_property for lazy, one-time per-instance computation."""

    def __init__(self, transactions: list[float]) -> None:
        self._transactions = tuple(transactions)

    @cached_property
    def summary_metrics(self) -> dict[str, float]:
        """Computed only on first access and cached on this instance."""
        total = sum(self._transactions)
        count = len(self._transactions)
        return {
            "total": total,
            "average": total / count if count else 0.0,
        }
```

### 2. Thread-Safe `TTLCache` + Cache-Aside Pattern with Negative Caching
When caching database or external API results, entries must expire after a bounded TTL. Below is a complete $O(1)$ LRU + TTL cache combined with the **Cache-Aside** pattern and **Negative Caching** (storing a `_NOT_FOUND` sentinel so repeated queries for nonexistent IDs do not overload the database):

```python
from collections import OrderedDict
from collections.abc import Hashable
import threading
import time
from typing import Generic, TypeVar

K = TypeVar("K", bound=Hashable)
V = TypeVar("V")


class _NotFoundSentinel:
    """Sentinel cached when a lookup confirms a key does not exist in primary storage."""


_NOT_FOUND = _NotFoundSentinel()


class TTLCache(Generic[K, V]):
    """
    Thread-safe bounded LRU cache with per-entry Time-to-Live (TTL) expiration.
    Get and Set execute in O(1) amortized time using OrderedDict.
    """

    def __init__(self, maxsize: int = 128, default_ttl: float = 60.0) -> None:
        if maxsize <= 0:
            raise ValueError("maxsize must be positive")
        if default_ttl <= 0:
            raise ValueError("default_ttl must be positive")
        self._maxsize: int = maxsize
        self._default_ttl: float = default_ttl
        self._store: OrderedDict[K, tuple[V, float]] = OrderedDict()
        self._lock = threading.Lock()

    def get(self, key: K) -> V | None:
        """Return cached value if present and unexpired; otherwise return None."""
        now = time.monotonic()
        with self._lock:
            entry = self._store.get(key)
            if entry is None:
                return None
            value, expires_at = entry
            if now >= expires_at:
                del self._store[key]
                return None
            self._store.move_to_end(key)
            return value

    def set(self, key: K, value: V, ttl: float | None = None) -> None:
        """Insert or update `key` with an expiration deadline and evict LRU if full."""
        effective_ttl = self._default_ttl if ttl is None else ttl
        expires_at = time.monotonic() + effective_ttl
        with self._lock:
            if key in self._store:
                self._store.move_to_end(key)
            self._store[key] = (value, expires_at)
            while len(self._store) > self._maxsize:
                self._store.popitem(last=False)

    def invalidate(self, key: K) -> None:
        """Explicitly remove `key` from cache (used after database writes)."""
        with self._lock:
            self._store.pop(key, None)


class ProductRepository:
    """Simulates a primary database wrapped with Cache-Aside and Negative Caching."""

    def __init__(self) -> None:
        self._db: dict[str, dict[str, object]] = {
            "sku-101": {"name": "Mechanical Keyboard", "price": 4500},
            "sku-102": {"name": "USB-C Dock", "price": 3200},
        }
        self._cache: TTLCache[str, dict[str, object] | _NotFoundSentinel] = TTLCache(
            maxsize=512,
            default_ttl=300.0,
        )
        self.db_queries: int = 0

    def get_product(self, sku: str) -> dict[str, object] | None:
        """Cache-aside read with 30-second negative caching for missing SKUs."""
        cached = self._cache.get(sku)
        if cached is _NOT_FOUND:
            return None
        if cached is not None:
            assert isinstance(cached, dict)
            return cached.copy()  # Return defensive copy so callers cannot mutate cache

        # Cache miss -> query primary database
        self.db_queries += 1
        record = self._db.get(sku)
        if record is None:
            self._cache.set(sku, _NOT_FOUND, ttl=30.0)
            return None

        self._cache.set(sku, record.copy())
        return record.copy()

    def update_price(self, sku: str, new_price: int) -> None:
        """Update primary database first, then invalidate stale cache entry."""
        if sku in self._db:
            self._db[sku]["price"] = new_price
            self._cache.invalidate(sku)


if __name__ == "__main__":
    print("Edit distance ('kitten', 'sitting'):", edit_distance("kitten", "sitting"))
    print("Tax rate:", fetch_tax_rate("IN", "TN"), "| Cache stats:", fetch_tax_rate.cache_info())

    repo = ProductRepository()
    print("First read (miss): ", repo.get_product("sku-101"), "| DB queries:", repo.db_queries)
    print("Second read (hit): ", repo.get_product("sku-101"), "| DB queries:", repo.db_queries)
    print("Missing SKU #1:    ", repo.get_product("sku-999"), "| DB queries:", repo.db_queries)
    print("Missing SKU #2:    ", repo.get_product("sku-999"), "| DB queries:", repo.db_queries)

    repo.update_price("sku-101", 4200)
    print("After invalidation:", repo.get_product("sku-101"), "| DB queries:", repo.db_queries)
```

## 6. Common Pitfalls and Production Failure Modes

1. **Cache Stampede (Thundering Herd):**
   When a heavily requested key expires simultaneously under high traffic, hundreds of concurrent requests miss the cache at once and hammer the primary database. Mitigate using **per-key mutex locks (single-flight coalescing)** so only one worker recomputes the value while others wait, or add **random TTL jitter** (`ttl + random.uniform(0, 10)`) so keys do not expire in lockstep.
2. **Cache Penetration (Repeated Lookups for Nonexistent Keys):**
   Queries for IDs that do not exist in the database miss the cache on every single request unless missing results are cached. Use **negative caching** with a short TTL (e.g., 15–30 seconds) or a **Bloom Filter** in front of the cache.
3. **Cache Avalanche (Mass Simultaneous Expiration):**
   If thousands of keys are loaded at startup with the exact same TTL, they all expire together and spike database load. Always randomize TTLs with jitter and stagger warm-up jobs.
4. **Using `@lru_cache` on Instance Methods or `async def` Functions:**
   * Decorating a regular instance method (`def compute(self, x):`) stores `self` in the global function cache, preventing garbage collection of every instance (memory leak). Use `@cached_property` for zero-argument properties or delegate to a helper keyed by an immutable instance ID.
   * Decorating an `async def` coroutine with `@lru_cache` caches the single-use coroutine object rather than its awaited value, raising `RuntimeError: cannot reuse already awaited coroutine` on the second call.
5. **Omitting User/Tenant Scope from Cache Keys:**
   Caching user-specific responses under a generic key like `"dashboard:summary"` instead of `"dashboard:summary:user_42"` leaks one user's private data to another. Always include tenant, user ID, locale, and schema version (`v1`) in cache keys.
6. **Mutating Returned Mutable Cached Objects:**
   In-process caches return references to stored `dict` or `list` objects. If a caller mutates the returned dictionary in place, every subsequent reader receives the corrupted object—return copies or immutable tuples/dataclasses.

## 7. Quick Reference

| Concept / Tool | Key Detail |
| :--- | :--- |
| **In-Process Memoization** | `@functools.cache` (unbounded), `@functools.lru_cache(maxsize=N)` (bounded LRU), `@functools.cached_property` |
| **Cache Introspection** | `fn.cache_info()` returns `CacheInfo(hits, misses, maxsize, currsize)`; `fn.cache_clear()` resets cache |
| **Distributed Cache** | Redis / Memcached for multi-process or multi-server shared state with native TTL |
| **Cache-Aside Flow** | Read: `cache.get()` $\to$ on miss, read DB $\to$ `cache.set(ttl)`; Write: update DB $\to$ `cache.delete()` |
| **Key Reliability Defenses** | **TTL Jitter** (avalanche), **Single-Flight Lock** (stampede), **Negative Caching** (penetration) |
| **Clock Source for TTL** | Always use `time.monotonic()` (immune to system wall-clock NTP jumps), never `time.time()` |
