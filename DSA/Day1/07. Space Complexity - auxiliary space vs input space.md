# Space Complexity: Auxiliary Space vs. Input Space

## 1. Overview
**Space complexity** measures the total amount of computer memory (RAM) an algorithm needs to run to completion as a function of its input size $n$. Just as time complexity models how CPU operations scale, space complexity models how memory consumption scales.

* **The Two Components of Total Space:**
  $$\text{Total Space Complexity} = \text{Input Space} + \text{Auxiliary Space}$$
  * **Input Space:** The memory required to hold the input data passed into the algorithm (for example, an array of $n$ integers takes $O(n)$ input space).
  * **Auxiliary Space:** The **extra (temporary) working memory** allocated by the algorithm during execution beyond the input itself—including local variables, newly created data structures (`list`, `dict`, `set`), and **recursion call stack frames**.

---

## 2. Why Auxiliary Space Matters More in Practice
When comparing two algorithms that solve the exact same problem on the exact same input of size $n$, both algorithms automatically consume the same **input space** ($O(n)$). Consequently, **auxiliary space** is the true differentiator of memory efficiency.

* **In-Place Algorithms ($O(1)$ Auxiliary Space):**
  An algorithm is **in-place** if it transforms the input directly using only a constant amount of extra memory—$O(1)$ auxiliary space—regardless of how large $n$ grows (even though its total space including the input is $O(n)$).
* **Out-of-Place Algorithms ($O(n)$ or higher Auxiliary Space):**
  An algorithm is **out-of-place** when it allocates new containers proportional to $n$ (such as returning a sorted copy, building a frequency hash map, or allocating a 2D dynamic programming table).

### Comparison on Standard Operations

| Algorithm / Approach | Input Space | Auxiliary Space | Total Space | In-Place? |
| :--- | :--- | :--- | :--- | :--- |
| **Linear Search / Binary Search (Iterative)** | $O(n)$ | $O(1)$ | $O(n)$ | Yes (read-only) |
| **Two-Pointer Array Reversal** | $O(n)$ | $O(1)$ | $O(n)$ | **Yes** |
| **Slicing Array Reversal (`arr[::-1]`)** | $O(n)$ | $O(n)$ | $O(n)$ | No (allocates full copy) |
| **Heap Sort / Insertion Sort** | $O(n)$ | $O(1)$ | $O(n)$ | **Yes** |
| **Merge Sort (Standard Top-Down)** | $O(n)$ | $O(n)$ | $O(n)$ | No ($O(n)$ merge buffer + $O(\log n)$ stack) |
| **Quick Sort (In-Place Partition)** | $O(n)$ | $O(\log n)$ avg / $O(n)$ worst | $O(n)$ | Yes (stack frames only) |
| **Two-Sum via Hash Map (`dict`)** | $O(n)$ | $O(n)$ | $O(n)$ | No |
| **2D Dynamic Programming ($n \times n$ grid)** | $O(n)$ | $O(n^2)$ | $O(n^2)$ | No |

## 3. What Counts Toward Auxiliary Space?
When analyzing a function's auxiliary space, account for all three sources of temporary memory:

### 1. Scalar Variables and Pointers ($O(1)$)
Fixed numbers of integer counters, loop indices (`i`, `left`, `right`), boolean flags, and accumulators consume constant memory independent of $n$.

### 2. Dynamically Allocated Data Structures
Any container whose size grows with $n$:
* `seen = set()` storing up to $n$ elements $\rightarrow$ **$O(n)$ auxiliary space**.
* `copy_arr = arr.copy()` or list comprehension `[x * 2 for x in arr]` $\rightarrow$ **$O(n)$ auxiliary space**.
* `dp = [[0] * n for _ in range(n)]` $\rightarrow$ **$O(n^2)$ auxiliary space**.

### 3. Function Call Stack Frames (Recursion Depth)
Every active recursive function call pushes a **stack frame** onto the call stack (storing local variables, parameters, and the return address) until the base case returns:
* **Linear Recursion** (e.g., recursive factorial or linked-list traversal of length $n$): $n$ simultaneous stack frames $\rightarrow$ **$O(n)$ auxiliary space**.
* **Divide-and-Conquer Halving** (e.g., recursive Binary Search): $\log_2 n$ active frames at maximum depth $\rightarrow$ **$O(\log n)$ auxiliary space** (whereas iterative Binary Search uses **$O(1)$** auxiliary space).
* **Binary Tree DFS:** **$O(h)$ auxiliary space**, where $h$ is tree height ($O(\log n)$ for a balanced tree; $O(n)$ for a completely skewed tree).

*(Note: Returning a newly constructed output list of size $n$ is generally counted in auxiliary space unless explicitly excluded by problem convention—always clarify whether output allocation is included.)*

## 4. Practical Python Examples: Comparing Input vs. Auxiliary Space

### Example 1: Reversing a List ($O(1)$ In-Place vs. $O(n)$ Out-of-Place)
```python
def reverse_in_place(items: list[int]) -> None:
    """
    Input Space:     O(n) (the `items` list passed by reference)
    Auxiliary Space: O(1) (only two integer pointers: `left` and `right`)
    Total Space:     O(n)
    """
    left, right = 0, len(items) - 1
    while left < right:
        items[left], items[right] = items[right], items[left]
        left += 1
        right -= 1


def reverse_out_of_place(items: list[int]) -> list[int]:
    """
    Input Space:     O(n) (the `items` list)
    Auxiliary Space: O(n) (allocates a brand-new list of n element references)
    Total Space:     O(n) + O(n) = O(n)
    """
    return items[::-1]
```

### Example 2: Recursion Call Stack Space ($O(n)$ Recursive vs. $O(1)$ Iterative)
```python
def sum_recursive(nums: list[int], index: int = 0) -> int:
    """
    Input Space:     O(n)
    Auxiliary Space: O(n) due to n nested call-stack frames
    """
    if index == len(nums):
        return 0
    return nums[index] + sum_recursive(nums, index + 1)


def sum_iterative(nums: list[int]) -> int:
    """
    Input Space:     O(n)
    Auxiliary Space: O(1) (single accumulator variable, zero recursion frames)
    """
    total = 0
    for value in nums:
        total += value
    return total
```

### Example 3: Measuring Peak Auxiliary Memory in Python (`tracemalloc`)
```python
import tracemalloc


def measure_auxiliary_bytes(func, data: list[int]) -> int:
    """Measure peak extra heap bytes allocated while executing func(data)."""
    tracemalloc.start()
    func(data)
    _, peak_bytes = tracemalloc.get_traced_memory()
    tracemalloc.stop()
    return peak_bytes


if __name__ == "__main__":
```

## 5. The Space-Time Trade-Off
In software engineering, you can frequently reduce **time complexity** by investing additional **auxiliary space** (or conserve auxiliary space at the cost of extra runtime):

| Problem | Low Auxiliary Space Approach | Fast Time (Higher Auxiliary Space) Approach |
| :--- | :--- | :--- |
| **Duplicate Detection** | Sort in-place first: $O(n \log n)$ time, **$O(1)$ auxiliary space** | Store seen items in `set`: **$O(n)$ time**, $O(n)$ auxiliary space |
| **Fibonacci ($n$-th term)** | Bottom-up two variables: **$O(n)$ time**, **$O(1)$ auxiliary space** | Top-down memoization table: $O(n)$ time, $O(n)$ auxiliary space |
| **Substring Search / Indexing** | Scan text directly: $O(N \cdot M)$ time, **$O(1)$ auxiliary space** | Build inverted index / Trie: **$O(M)$ lookup**, $O(N)$ auxiliary space |
| **2D Dynamic Programming** | Keep only previous row: $O(R \cdot C)$ time, **$O(C)$ auxiliary space** | Store full grid: $O(R \cdot C)$ time, $O(R \cdot C)$ auxiliary space |

## 6. Common Pitfalls and Best Practices

1. **Saying "Space Complexity Is $O(n)$" When You Mean $O(1)$ Auxiliary Space:**
   In technical interviews and algorithm design, when asked "What is the space complexity of Binary Search?", the expected answer is **$O(1)$** (for iterative) or **$O(\log n)$** (for recursive)—referring to **auxiliary space**, not the $O(n)$ input array. State **"O(1) auxiliary space (O(n) total including input)"** to be completely unambiguous.
2. **Forgetting Call-Stack Frames in Recursive Algorithms:**
   A recursive function with zero local lists or dictionaries still consumes **$O(\text{recursion depth})$** auxiliary memory. Furthermore, in Python, recursion depth beyond ~1,000 frames triggers `RecursionError`.
3. **Hidden Copies in Python Slicing and Comprehensions:**
   Expressions like `arr[1:]`, `arr[::-1]`, `list(items)`, or `"".join(...)` allocate new $O(n)$ objects on the heap. In recursion (such as `merge_sort(arr[:mid])`), passing slices creates $O(n)$ temporary copies at each recursion level.
4. **Confusing "In-Place" with Zero Stack Usage:**
   In-place Quick Sort does not allocate a duplicate array, so its heap auxiliary space is $O(1)$, yet its recursion stack still uses **$O(\log n)$** auxiliary space on average (and $O(n)$ in the worst case).
5. **Reusing Allocated Buffers in Hot Loops:**
   When processing large batches in tight loops, clearing and reusing an existing `list` or `dict` (`buffer.clear()`) instead of allocating a fresh container on every iteration reduces heap allocation pressure and garbage collection pauses.

## 7. Quick Reference

| Concept | Definition / Key Rule |
| :--- | :--- |
| **Input Space** | Memory occupied by the input arguments themselves (e.g., $O(n)$ for an array of length $n$) |
| **Auxiliary Space** | Extra temporary memory allocated during execution (local variables + containers + call stack) |
| **Total Space** | $\text{Input Space} + \text{Auxiliary Space}$ |
| **In-Place Algorithm** | Modifies input directly using **$O(1)$ auxiliary space** (excluding recursion stack if applicable) |
| **Recursion Stack Space** | Equals maximum call depth $\times$ frame size ($O(\log n)$ for balanced halving, $O(n)$ for linear recursion) |
| **Space-Time Trade-Off** | Trading extra auxiliary memory (hash tables, caches, DP tables) for faster time complexity |
