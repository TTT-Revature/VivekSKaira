# Quick Sort

## 1. Overview
**Quick Sort** is a comparison-based, **divide-and-conquer** sorting algorithm that sorts an array **in-place** by selecting a **pivot** element and partitioning the remaining elements around it—placing smaller elements to its left and larger elements to its right—before recursively sorting the two resulting subarrays.

* **Core Characteristics:**
  * **In-Place ($O(\log n)$ Average Auxiliary Space):** Unlike Merge Sort, Quick Sort requires no $O(n)$ temporary merge buffer; memory usage comes strictly from recursion call-stack frames.
  * **High Practical Speed:** Tight inner comparison loops and sequential memory access yield superior CPU cache locality, making Quick Sort faster in practice than Merge Sort or Heap Sort on in-memory arrays.
  * **Pivot-Sensitive Performance:** Achieves **$\Theta(n \log n)$** average runtime with balanced partitions, but degrades to **$O(n^2)$** if pivots consistently produce maximally unbalanced splits.
  * **Unstable:** Long-distance swaps during partitioning can reorder elements with equal keys.

## 2. How It Works: Partitioning and Visual Trace

### 1. The Three Divide-and-Conquer Steps
1. **Pivot Selection:** Choose a pivot element from the subarray `arr[low : high + 1]` (e.g., a random element, the median-of-three, or the last element).
2. **Partitioning ($\Theta(n)$):** Rearrange elements in-place so all elements less than or equal to the pivot precede it and all elements greater than the pivot follow it, locking the pivot at its final sorted index `p`.
3. **Conquer (Recursion):** Recursively apply Quick Sort to the left subarray `arr[low : p - 1]` and right subarray `arr[p + 1 : high]` until reaching subarrays of size $0$ or $1$ (`low >= high`).

### 2. Visual Trace (Lomuto Partition on `[10, 80, 30, 90, 40, 50, 70]`)
Using the last element `pivot = 70` (`high = 6`), `i` tracks the boundary of elements $\le 70$, and `j` scans from `0` to `5`:

```text
Initial: [ 10, 80, 30, 90, 40, 50 | 70 ]   pivot = 70, i = -1

j = 0: 10 <= 70 -> i = 0, swap(arr[0], arr[0]) -> [ 10 | 80, 30, 90, 40, 50 | 70 ]
j = 1: 80 >  70 -> no swap                     -> [ 10 | 80, 30, 90, 40, 50 | 70 ]
j = 2: 30 <= 70 -> i = 1, swap(arr[1], arr[2]) -> [ 10, 30 | 80, 90, 40, 50 | 70 ]
j = 3: 90 >  70 -> no swap                     -> [ 10, 30 | 80, 90, 40, 50 | 70 ]
j = 4: 40 <= 70 -> i = 2, swap(arr[2], arr[4]) -> [ 10, 30, 40 | 90, 80, 50 | 70 ]
j = 5: 50 <= 70 -> i = 3, swap(arr[3], arr[5]) -> [ 10, 30, 40, 50 | 80, 90 | 70 ]

Final Pivot Placement: swap(arr[i + 1], arr[6]) -> swap(arr[4], arr[6]):
Result:  [ 10, 30, 40, 50 ]  [ 70 ]  [ 90, 80 ]
           (left subarray)   (locked)  (right subarray)
```

## 3. Time and Space Complexity Analysis
Assume $n$ is the number of elements in the input array:

| Case | Partition Split Condition | Recurrence Relation | Time Complexity | Auxiliary Space (Stack) |
| :--- | :--- | :--- | :--- | :--- |
| **Best Case** | Pivot divides array into two equal halves ($\frac{n}{2}$ and $\frac{n}{2}$) | $T(n) = 2T\left(\frac{n}{2}\right) + \Theta(n)$ | **$\Omega(n \log n)$** | $O(\log n)$ |
| **Average Case** | Random pivot yields proportional splits (e.g., $10\%$ / $90\%$) | $T(n) = T(0.1n) + T(0.9n) + \Theta(n)$ | **$\Theta(n \log n)$** | $O(\log n)$ |
| **Worst Case** | Pivot is always the smallest or largest element ($0$ and $n - 1$) | $T(n) = T(n - 1) + \Theta(n)$ | **$O(n^2)$** | $O(n)$ (or $O(\log n)$ with tail-call optimization) |

* **Why Proportional Splits Still Yield $\Theta(n \log n)$:**
  Even an asymmetric $90\%\text{–}10\%$ split produces a recursion tree of depth $\log_{10/9}(n) = \Theta(\log n)$, with at most $n$ partition work per level—giving $\Theta(n \log n)$ total operations.
* **Worst-Case Trigger:**
  Always picking the first or last element as pivot on an **already-sorted** or **reverse-sorted** array creates $n$ nested partitions of sizes $n - 1, n - 2, \dots, 1$, requiring $\frac{n(n - 1)}{2} = \Theta(n^2)$ comparisons and $n$ stack frames (which triggers `RecursionError` in Python when $n \ge 1{,}000$).

## 4. Partition Schemes: Lomuto vs. Hoare vs. 3-Way

| Feature | Lomuto Partition | Hoare Partition | 3-Way Partition (Dutch National Flag) |
| :--- | :--- | :--- | :--- |
| **Pointer Movement** | Single directional scanner `j` (`low` to `high - 1`) + boundary `i` | Two converging pointers `left` and `right` moving inward from both ends | Three pointers (`lt`, `i`, `gt`) partitioning into `less`, `equal`, and `greater` |
| **Swap Count** | Higher (~$3\times$ more swaps than Hoare) | **Minimal** (swaps only out-of-place pairs) | Low; groups all equal keys in one pass |
| **Pivot Final Position** | Placed at exact final index `p` after partition | Pivot is **not** guaranteed to sit at index `p` after partition | Entire equal block `[lt..gt]` sits in final sorted position |
| **Recursive Calls** | `_sort(low, p - 1)` and `_sort(p + 1, high)` | `_sort(low, p)` and `_sort(p + 1, high)` | `_sort(low, lt - 1)` and `_sort(gt + 1, high)` |
| **All-Duplicate Input** | Degrades to **$O(n^2)$** | Splits evenly in middle $\implies$ **$\Theta(n \log n)$** | Finishes in a single pass $\implies$ **$\Theta(n)$** |

## 5. Python Implementations

### 1. Randomized In-Place Quick Sort (Lomuto Scheme)
Selecting a random pivot index before partitioning eliminates deterministic worst-case inputs and guarantees **$O(n \log n)$ expected time** on every input order:

```python
import random
from typing import TypeVar

T = TypeVar("T", int, float, str)


def quick_sort_lomuto(items: list[T]) -> list[T]:
    """
    Sort `items` in-place using Randomized Lomuto Quick Sort.
    Time: Theta(n log n) expected, O(n^2) theoretical worst
    Auxiliary Space: O(log n) expected stack frames | Stable: No
    """

    def _partition(low: int, high: int) -> int:
        # Randomize pivot to prevent O(n^2) degradation on sorted/reverse-sorted arrays
        rand_idx = random.randint(low, high)
        items[rand_idx], items[high] = items[high], items[rand_idx]

        pivot = items[high]
        store_idx = low

        for scan_idx in range(low, high):
            if items[scan_idx] <= pivot:
                items[store_idx], items[scan_idx] = items[scan_idx], items[store_idx]
                store_idx += 1

        items[store_idx], items[high] = items[high], items[store_idx]
        return store_idx

    def _sort(low: int, high: int) -> None:
        if low >= high:
            return
        pivot_idx = _partition(low, high)
        _sort(low, pivot_idx - 1)
        _sort(pivot_idx + 1, high)

    _sort(0, len(items) - 1)
    return items
```

### 2. Hoare Partition Quick Sort (Fewer Swaps)
```python
def quick_sort_hoare(items: list[T]) -> list[T]:
    """
    Sort `items` in-place using Randomized Hoare Partition Quick Sort.
    Performs roughly 3x fewer swaps than Lomuto and handles equal elements efficiently.
    Time: Theta(n log n) expected | Auxiliary Space: O(log n) expected | Stable: No
    """

    def _partition(low: int, high: int) -> int:
        pivot = items[random.randint(low, high)]
        left = low - 1
        right = high + 1

        while True:
            left += 1
            while items[left] < pivot:
                left += 1

            right -= 1
            while items[right] > pivot:
                right -= 1

            if left >= right:
                return right

            items[left], items[right] = items[right], items[left]

    def _sort(low: int, high: int) -> None:
        if low >= high:
            return
        split_idx = _partition(low, high)
        # Note: split_idx is included in the left recursive call in Hoare's scheme
        _sort(low, split_idx)
        _sort(split_idx + 1, high)

    _sort(0, len(items) - 1)
    return items
```

### 3. Three-Way Quick Sort (Optimal for Heavy Duplicates)
```python
def quick_sort_three_way(items: list[T]) -> list[T]:
    """
    Dutch National Flag 3-way Quick Sort: partitions into (< pivot, == pivot, > pivot).
    Runs in Theta(n) time when the input contains few unique keys.
    """

    def _sort(low: int, high: int) -> None:
        if low >= high:
            return

        pivot = items[random.randint(low, high)]
        lt = low       # items[low..lt - 1] < pivot
        idx = low      # items[lt..idx - 1] == pivot
        gt = high      # items[gt + 1..high] > pivot

        while idx <= gt:
            if items[idx] < pivot:
                items[lt], items[idx] = items[idx], items[lt]
                lt += 1
                idx += 1
            elif items[idx] > pivot:
                items[idx], items[gt] = items[gt], items[idx]
                gt -= 1
            else:
                idx += 1

        _sort(low, lt - 1)
        _sort(gt + 1, high)

    _sort(0, len(items) - 1)
    return items


if __name__ == "__main__":
    print("Lomuto Quick Sort:   ", quick_sort_lomuto([10, 80, 30, 90, 40, 50, 70]))
    print("Hoare Quick Sort:    ", quick_sort_hoare([10, 80, 30, 90, 40, 50, 70]))
    print("3-Way (duplicates):  ", quick_sort_three_way([4, 2, 4, 1, 4, 2, 3, 4]))
```

## 6. Common Pitfalls and Best Practices

1. **Picking a Fixed First or Last Element as Pivot:**
   Using `pivot = items[high]` without randomization causes **$O(n^2)$ runtime** and **`RecursionError`** on already-sorted or reverse-sorted arrays of size $\ge 1{,}000$ in Python. Always randomize pivot selection (`random.randint(low, high)`) or use **median-of-three** (`items[low]`, `items[mid]`, `items[high]`).
2. **Using Out-of-Place List Comprehensions (`[x for x in arr if x < pivot]`):**
   Writing Quick Sort with list comprehensions allocates three new lists on every recursive call ($O(n \log n)$ total heap allocations), discarding Quick Sort's primary in-place memory advantage over Merge Sort.
3. **Using `<=` and `>=` in Hoare Partition Inner Loops:**
   In Hoare's partition scheme, inner loops must use **strict inequalities** (`items[left] < pivot` and `items[right] > pivot`). Using `<=` or `>=` causes pointers to walk past the subarray boundaries (`IndexError`) when all elements equal the pivot.
4. **Confusing Hoare and Lomuto Recursive Subarray Bounds:**
   In Lomuto, the pivot sits at `p` and is excluded from both recursive calls (`low..p - 1` and `p + 1..high`). In Hoare, `p` is merely the boundary index between partitions, so `low..p` **must include `p`**; excluding `p` fails to sort elements correctly, while choosing `pivot = items[high]` with `low..p` causes infinite recursion.
5. **Unbounded Stack Depth in Worst-Case Partitions:**
   To guarantee **$O(\log n)$ auxiliary stack space even in the worst case**, always recurse on the **smaller** partition first and update `low` or `high` iteratively in a `while low < high:` loop for the larger partition.

## 7. Quick Reference

| Property / Comparison | Quick Sort | Merge Sort |
| :--- | :--- | :--- |
| **Best / Average Time** | $\Omega(n \log n)$ / $\Theta(n \log n)$ | $\Omega(n \log n)$ / $\Theta(n \log n)$ |
| **Worst-Case Time** | **$O(n^2)$** (mitigated via randomized / median-of-3 pivot) | **$\Theta(n \log n)$** (guaranteed) |
| **Auxiliary Space** | **$O(\log n)$** average stack frames (in-place) | **$O(n)$** auxiliary merge buffer (on arrays) |
| **Stable?** | **No** | **Yes** |
| **Cache Locality** | **Excellent** (sequential in-place scans) | Moderate (copies between primary and auxiliary buffers) |
| **Best Use Cases** | General-purpose in-memory array sorting (`C qsort`, Introsort) | Linked lists, external disk sorting, or when stability / strict $O(n \log n)$ worst-case is mandatory |
