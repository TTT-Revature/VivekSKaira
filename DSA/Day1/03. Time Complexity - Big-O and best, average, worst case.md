# Time Complexity: Big-O and Best, Average, and Worst Cases

## 1. Overview
**Time complexity** quantifies how the number of elementary operations executed by an algorithm scales as a function of its input size $n$. Rather than measuring wall-clock seconds—which vary across CPUs, compilers, and system loads—time complexity models **asymptotic growth rate**.

* **Two Orthogonal Dimensions of Runtime Analysis:**
  1. **Input Case (Best, Average, Worst):** Describes **which input configuration** of size $n$ is being evaluated (for example, an already-sorted array vs. a reverse-sorted array).
  2. **Asymptotic Notation ($O$, $\Omega$, $\Theta$):** Describes **how the growth rate is mathematically bounded** as $n \to \infty$ (upper bound, lower bound, or tight bound).

---

## 2. Asymptotic Notations: Big-O, Big-Omega, and Big-Theta
Let $T(n)$ represent the exact operation count of an algorithm for input size $n$, and let $g(n)$ be a simplified reference function (such as $n$, $n \log n$, or $n^2$).

### 1. Big-O Notation ($O$ — Asymptotic Upper Bound)
$T(n) = O(g(n))$ means $T(n)$ grows **no faster than** a constant multiple of $g(n)$ for all sufficiently large inputs:
$$0 \le T(n) \le c \cdot g(n) \quad \text{for all } n \ge n_0 \text{ (for some constants } c > 0, n_0 \ge 1\text{)}$$
* **Engineering Meaning:** Guarantees a ceiling on resource usage; the algorithm will never scale worse than $g(n)$.

### 2. Big-Omega Notation ($\Omega$ — Asymptotic Lower Bound)
$T(n) = \Omega(g(n))$ means $T(n)$ grows **at least as fast as** a constant multiple of $g(n)$ for all sufficiently large inputs:
$$0 \le c \cdot g(n) \le T(n) \quad \text{for all } n \ge n_0 \text{ (for some constants } c > 0, n_0 \ge 1\text{)}$$
* **Engineering Meaning:** Establishes a floor on the minimum work required (for example, any comparison-based sorting algorithm requires $\Omega(n \log n)$ comparisons in the worst case).

### 3. Big-Theta Notation ($\Theta$ — Asymptotic Tight Bound)
$T(n) = \Theta(g(n))$ means $T(n)$ is bounded **both above and below** by $g(n)$—i.e., $T(n) = O(g(n))$ and $T(n) = \Omega(g(n))$ simultaneously:
$$0 \le c_1 \cdot g(n) \le T(n) \le c_2 \cdot g(n) \quad \text{for all } n \ge n_0$$
* **Engineering Meaning:** Gives the exact asymptotic growth rate of the algorithm.

### Simplification Rules for Big-O Expressions
1. **Drop Constant Multipliers:** $5n \rightarrow O(n)$, $\frac{1}{2}n^2 \rightarrow O(n^2)$.
2. **Keep Only the Dominant Term:** $3n^3 + 12n^2 + 45n + 100 \rightarrow O(n^3)$.
3. **Logarithm Bases Are Equivalent:** $\log_2 n$, $\log_{10} n$, and $\ln n$ differ only by a constant factor ($\log_a n = \frac{\log_b n}{\log_b a}$), so all simplify to $O(\log n)$.

## 3. Standard Big-O Complexity Hierarchy
Ordered from **fastest (most scalable)** to **slowest (least scalable)**:

| Complexity | Class Name | Ops ($n = 10$) | Ops ($n = 100$) | Ops ($n = 10{,}000$) | Typical Algorithmic Pattern |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **$O(1)$** | Constant | $1$ | $1$ | $1$ | Array index access `arr[i]`, `dict`/`set` lookup |
| **$O(\log n)$** | Logarithmic | $\approx 3$ | $\approx 7$ | $\approx 13$ | Binary search, balanced BST lookup |
| **$O(n)$** | Linear | $10$ | $100$ | $10{,}000$ | Single pass (`sum()`, `min()`, linear search) |
| **$O(n \log n)$** | Linearithmic | $\approx 33$ | $\approx 664$ | $\approx 132{,}877$ | Merge Sort, Heap Sort, Python `sorted()` (Timsort) |
| **$O(n^2)$** | Quadratic | $100$ | $10{,}000$ | $100{,}000{,}000$ | Bubble Sort, Insertion Sort, all-pairs nested loops |
| **$O(n^3)$** | Cubic | $1{,}000$ | $1{,}000{,}000$ | $10^{12}$ | Naive matrix multiplication, Floyd-Warshall |
| **$O(2^n)$** | Exponential | $1{,}024$ | $\approx 1.27 \times 10^{30}$ | Infeasible | Generating all subsets (power set), naive Fibonacci |
| **$O(n!)$** | Factorial | $3{,}628{,}800$ | Infeasible | Infeasible | Generating all permutations, brute-force TSP |

## 4. Best, Average, and Worst Case Analysis
For a fixed input size $n$, an algorithm's operation count often depends on the **structure or ordering of the input data**:

* **Best Case:**
  The minimum number of operations required across all valid inputs of size $n$ (occurs on the most favorable input arrangement). Rarely used alone for system guarantees because real-world inputs seldom match the ideal layout.
* **Average Case:**
  The expected number of operations averaged over a probability distribution of all possible inputs of size $n$ (typically assuming uniformly random inputs). Useful for predicting typical throughput.
* **Worst Case:**
  The maximum number of operations required across all valid inputs of size $n$ (occurs on the most adversarial input arrangement). **Default engineering benchmark** because it provides a strict performance guarantee for every possible input.
* **Amortized Case:**
  The average cost per operation over a **worst-case sequence** of $k$ consecutive operations. Even if an occasional operation triggers an expensive resize or cleanup ($O(n)$), the average cost per operation across the sequence remains low (e.g., Python `list.append()` is $O(1)$ amortized).

### Case Comparison Across Classic Algorithms

| Algorithm / Operation | Best Case | Average Case | Worst Case | Why Cases Differ |
| :--- | :--- | :--- | :--- | :--- |
| **Linear Search** | $\Theta(1)$ | $\Theta(n)$ | $\Theta(n)$ | Best: target at index `0`; Worst: target at end or absent |
| **Binary Search** | $\Theta(1)$ | $\Theta(\log n)$ | $\Theta(\log n)$ | Best: target at initial midpoint; Worst: target at leaf/absent |
| **Insertion Sort** | $\Theta(n)$ | $\Theta(n^2)$ | $\Theta(n^2)$ | Best: already sorted (0 shifts); Worst: reverse-sorted ($\frac{n(n-1)}{2}$ shifts) |
| **Merge Sort** | $\Theta(n \log n)$ | $\Theta(n \log n)$ | $\Theta(n \log n)$ | Always splits in half and merges all elements regardless of order |
| **Quick Sort** | $\Theta(n \log n)$ | $\Theta(n \log n)$ | $\Theta(n^2)$ | Best/Avg: balanced partitions; Worst: pivot is always min or max element |
| **Hash Table Lookup (`dict`)** | $\Theta(1)$ | $\Theta(1)$ | $\Theta(n)$ | Best/Avg: direct bucket hit; Worst: pathological hash collisions into one bucket |

## 5. Practical Rules for Deriving Time Complexity from Code

### 1. Sequential Code Blocks (Addition Rule)
When step A takes $O(f(n))$ and step B takes $O(g(n))$, total runtime is $O(f(n) + g(n)) = O(\max(f(n), g(n)))$:
```python
# O(n) + O(n^2) -> O(n^2)
for x in items:          # O(n)
    print(x)

for x in items:          # O(n)
    for y in items:      # O(n) -> combined O(n^2)
        print(x, y)
```

### 2. Dependent Inner Loops (Triangular Series)
When the inner loop runs $0, 1, 2, \dots, n - 1$ times, sum the arithmetic progression:
$$\sum_{i=0}^{n-1} i = \frac{n(n - 1)}{2} = \frac{1}{2}n^2 - \frac{1}{2}n \implies \Theta(n^2)$$

### 3. Logarithmic Loops (Multiplicative / Divisive Step)
Whenever the loop variable or search space is multiplied or divided by a constant factor $k > 1$ on each iteration, the loop executes $\log_k n$ times:
```python
step = 1
while step < n:          # Runs log2(n) times -> O(log n)
    step *= 2
```

### 4. Multiple Distinct Input Variables
If a function takes two independent collections `arr_a` (length $A$) and `arr_b` (length $B$), keep both variables distinct—do **not** collapse both into $n$:
* Sequential traversal of both: **$O(A + B)$**.
* Comparing every element of `arr_a` with every element of `arr_b`: **$O(A \cdot B)$**.

## 6. Practical Python Example: Best, Average, and Worst Cases
The example below instruments **Linear Search** and **Insertion Sort** to count elementary comparisons across best-case, average-case, and worst-case inputs:

```python
import random


def linear_search_with_ops(arr: list[int], target: int) -> tuple[int, int]:
    """Return (found_index_or_minus_1, comparison_count)."""
    comparisons = 0
    for idx, value in enumerate(arr):
        comparisons += 1
        if value == target:
            return idx, comparisons
    return -1, comparisons


def insertion_sort_with_ops(arr: list[int]) -> tuple[list[int], int]:
    """Sort a copy of arr using Insertion Sort and return (sorted_list, comparison_count)."""
    data = arr.copy()
    comparisons = 0

    for i in range(1, len(data)):
        key = data[i]
        j = i - 1
        while j >= 0:
            comparisons += 1
            if data[j] > key:
                data[j + 1] = data[j]
                j -= 1
            else:
                break
        data[j + 1] = key

    return data, comparisons


if __name__ == "__main__":
    n = 1_000
    rng = random.Random(42)

    # 1. Linear Search Cases (n = 1,000)
    sorted_nums = list(range(n))
    _, best_ls = linear_search_with_ops(sorted_nums, target=0)       # First element: 1 op
    _, avg_ls = linear_search_with_ops(sorted_nums, target=500)      # Middle element: ~500 ops
    _, worst_ls = linear_search_with_ops(sorted_nums, target=-99)    # Absent: 1,000 ops
    print(f"Linear Search (n={n})   -> Best: {best_ls} | Avg: {avg_ls} | Worst: {worst_ls}")

    # 2. Insertion Sort Cases (n = 1,000)
    best_input = list(range(n))                                      # Already sorted: O(n)
    avg_input = rng.sample(range(n * 10), k=n)                       # Random order: O(n^2)
    worst_input = list(range(n, 0, -1))                              # Reverse sorted: O(n^2)

    _, best_is = insertion_sort_with_ops(best_input)
    _, avg_is = insertion_sort_with_ops(avg_input)
    _, worst_is = insertion_sort_with_ops(worst_input)
    print(f"Insertion Sort (n={n})  -> Best: {best_is:,} | Avg: {avg_is:,} | Worst: {worst_is:,}")
```

## 7. Common Pitfalls and Best Practices

1. **Equating "Big-O" with "Worst Case":**
   Big-O ($O$) is an **asymptotic upper bound**, not a synonym for worst-case input. You can express best-case time using Big-O (e.g., Insertion Sort's best-case runtime is $O(n)$) and worst-case time using Big-Theta (e.g., Insertion Sort's worst-case runtime is $\Theta(n^2)$).
2. **Ignoring Hidden $O(n)$ Operations Inside Python Loops:**
   Built-in Python expressions such as `x in some_list`, `some_list.pop(0)`, `some_list.insert(0, x)`, `arr[a:b]`, and `s += ch` inside a loop are $O(n)$ or $O(k)$ operations, not $O(1)$. Nesting them inside an $O(n)$ loop produces $O(n^2)$ time complexity.
3. **Using $O(n)$ When Two Inputs Have Independent Sizes:**
   Writing $O(n)$ for a function iterating over two separate lists of lengths $m$ and $k$ hides the true bottleneck when $m = 10$ and $k = 10{,}000{,}000$. Express complexity in terms of all relevant input dimensions: $O(m + k)$.
4. **Relying on Best-Case Complexity in Production:**
   An algorithm with $O(n)$ best-case time and $O(n^2)$ worst-case time (such as unrandomized Quick Sort on already-sorted input) can cause severe latency spikes or denial-of-service vulnerabilities on adversarial inputs. Prefer algorithms with strong worst-case or randomized guarantees.
5. **Over-Optimizing for Tiny Input Sizes:**
   Big-O describes asymptotic behavior as $n \to \infty$. When $n$ is guaranteed to stay small (e.g., $n \le 32$), simpler $O(n^2)$ algorithms with low constant overhead and contiguous memory access often outperform complex $O(n \log n)$ structures.

## 8. Quick Reference

| Concept | Core Definition / Formula |
| :--- | :--- |
| **Big-O ($O(g(n))$)** | Asymptotic upper bound: $T(n) \le c \cdot g(n)$ for $n \ge n_0$ |
| **Big-Omega ($\Omega(g(n))$)** | Asymptotic lower bound: $T(n) \ge c \cdot g(n)$ for $n \ge n_0$ |
| **Big-Theta ($\Theta(g(n))$)** | Asymptotic tight bound: bounded both above ($O$) and below ($\Omega$) by $g(n)$ |
| **Best Case** | Minimum steps on the most favorable input arrangement of size $n$ |
| **Average Case** | Expected steps averaged across all valid inputs of size $n$ |
| **Worst Case** | Maximum steps on the most unfavorable input arrangement of size $n$ |
| **Amortized Time** | Average time per operation across a worst-case sequence of operations (e.g., `list.append()` is $O(1)$) |
| **Complexity Ranking** | $O(1) < O(\log n) < O(n) < O(n \log n) < O(n^2) < O(n^3) < O(2^n) < O(n!)$ |
