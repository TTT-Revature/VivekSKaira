# Common Time Complexities: $O(1)$, $O(\log n)$, $O(n)$, $O(n \log n)$, and $O(n^2)$

## 1. Overview
Most algorithms encountered in everyday software engineering and technical interviews fall into one of **five core time complexity classes**. Recognizing the code patterns and data structures that produce each complexity allows you to estimate scalability immediately.

* **Growth Comparison Across Input Sizes ($n$):**

| Complexity | Name | $n = 10$ | $n = 100$ | $n = 1{,}000$ | $n = 100{,}000$ | Practical Feasibility |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **$O(1)$** | Constant | $1$ | $1$ | $1$ | $1$ | Instant at any scale |
| **$O(\log n)$** | Logarithmic | $\approx 3$ | $\approx 7$ | $\approx 10$ | $\approx 17$ | Near-instant even for billions of items |
| **$O(n)$** | Linear | $10$ | $100$ | $1{,}000$ | $100{,}000$ | Fast up to tens of millions of items |
| **$O(n \log n)$** | Linearithmic | $\approx 33$ | $\approx 664$ | $\approx 9{,}966$ | $\approx 1.66 \times 10^6$ | Standard target for sorting and divide-and-conquer |
| **$O(n^2)$** | Quadratic | $100$ | $10{,}000$ | $1{,}000{,}000$ | $10^{10}$ (slow) | Practical only for small inputs ($n \lesssim 5{,}000$) |

## 2. Detailed Breakdown of the Five Common Complexities

### 1. $O(1)$ — Constant Time
* **Behavior:** Execution time remains completely independent of input size $n$. Whether $n = 10$ or $n = 10{,}000{,}000$, the algorithm executes the exact same fixed number of operations.
* **How to Recognize It:**
  * Direct index access in a contiguous array (`arr[i]`).
  * Arithmetic formulas or bit manipulations without loops.
  * Hash table lookup, insertion, or deletion (`dict[key]`, `item in my_set` on average).
  * Pushing or popping from the top of a stack (`list.append()`, `list.pop()`) or ends of a `collections.deque` (`appendleft()`, `popleft()`).

```python
def get_middle_element(items: list[int]) -> int | None:
    """Direct index computation and access: O(1) time."""
    if not items:
        return None
    mid_index = len(items) // 2
    return items[mid_index]
```

---

### 2. $O(\log n)$ — Logarithmic Time
* **Behavior:** On every step, the algorithm eliminates a constant fraction (typically half) of the remaining search space. Doubling the input size $n$ adds only **one extra step**.
* **How to Recognize It:**
  * Loop variables that multiply or divide by a constant factor (`i *= 2` or `n //= 2`).
  * **Binary Search** on a sorted array (`bisect` module).
  * Lookup, insertion, and deletion in a balanced Binary Search Tree (AVL, Red-Black Tree).
  * Heap insertion and extraction (`heapq.heappush()`, `heapq.heappop()`).

```python
def binary_search(sorted_nums: list[int], target: int) -> int:
    """Halves the search window on every iteration: O(log n) time."""
    left, right = 0, len(sorted_nums) - 1

    while left <= right:
        mid = left + (right - left) // 2
        if sorted_nums[mid] == target:
            return mid
        if sorted_nums[mid] < target:
            left = mid + 1
        else:
            right = mid - 1

    return -1
```

---

### 3. $O(n)$ — Linear Time
* **Behavior:** Execution time grows in direct proportion to input size $n$. Doubling $n$ doubles the runtime.
* **How to Recognize It:**
  * A single pass visiting each element a constant number of times (`for x in items:`).
  * Two-pointer or sliding-window traversals where both pointers move forward across the array at most $n$ times total.
  * Built-in linear scans (`sum(arr)`, `min(arr)`, `max(arr)`, `x in my_list`).
  * Building a frequency map (`collections.Counter(items)`).

```python
def find_max_subarray_sum_k(nums: list[int], k: int) -> int:
    """Sliding window of fixed size k across n elements: O(n) time."""
    if len(nums) < k or k <= 0:
        raise ValueError("Invalid window size k")

    window_sum = sum(nums[:k])
    max_sum = window_sum

    for right in range(k, len(nums)):
        window_sum += nums[right] - nums[right - k]
        if window_sum > max_sum:
            max_sum = window_sum

    return max_sum
```

### 4. $O(n \log n)$ — Linearithmic Time
* **Behavior:** Slightly slower than linear time, combining an $O(n)$ linear scan at each level of an $O(\log n)$ recursive tree or heap hierarchy. This is the **theoretical lower bound for comparison-based sorting**.
* **How to Recognize It:**
  * Efficient sorting algorithms: **Merge Sort**, **Heap Sort**, **Timsort** (`sorted(arr)` and `arr.sort()` in Python), and average-case **Quick Sort**.
  * Divide-and-conquer algorithms that split input into halves and merge results in linear time (e.g., counting inversions, closest pair of points).
  * Building a priority queue by pushing $n$ elements one by one ($n \times O(\log n)$).

```python
def merge_sort(nums: list[int]) -> list[int]:
    """Divides list in half log(n) times and merges in O(n) per level: O(n log n) time."""
    if len(nums) <= 1:
        return nums

    mid = len(nums) // 2
    left_sorted = merge_sort(nums[:mid])
    right_sorted = merge_sort(nums[mid:])

    merged: list[int] = []
    i = j = 0
    while i < len(left_sorted) and j < len(right_sorted):
        if left_sorted[i] <= right_sorted[j]:
            merged.append(left_sorted[i])
            i += 1
        else:
            merged.append(right_sorted[j])
            j += 1

    merged.extend(left_sorted[i:])
    merged.extend(right_sorted[j:])
    return merged
```

### 5. $O(n^2)$ — Quadratic Time
* **Behavior:** Execution time grows proportionally to the square of the input size $n$. Doubling $n$ **quadruples ($4\times$)** the runtime; multiplying $n$ by $10$ increases runtime by **$100\times$**.
* **How to Recognize It:**
  * Nested loops where both the outer and inner loops depend on $n$ (comparing every element with every other element).
  * Elementary sorting algorithms: **Bubble Sort**, **Selection Sort**, and average/worst-case **Insertion Sort**.
  * Performing an $O(n)$ operation (such as `x in list` or `list.pop(0)`) inside an $O(n)$ loop.

```python
def find_all_duplicate_pairs(nums: list[int]) -> list[tuple[int, int]]:
    """Checks all unique index pairs (i, j) with i < j: O(n^2) time."""
    pairs: list[tuple[int, int]] = []
    n = len(nums)

    for i in range(n):
        for j in range(i + 1, n):
            if nums[i] == nums[j]:
                pairs.append((i, j))

    return pairs
```

## 3. Benchmarking Operation Counts Across All Five Classes
The script below counts exact elementary operations for all five complexity classes at $n = 100$ and $n = 1{,}000$ ($10\times$ input increase) to illustrate their scaling behavior:

```python
def ops_constant(n: int) -> int:
    return 1


def ops_logarithmic(n: int) -> int:
    count = 0
    value = n
    while value > 1:
        value //= 2
        count += 1
    return count


def ops_linear(n: int) -> int:
    count = 0
    for _ in range(n):
        count += 1
    return count


def ops_linearithmic(n: int) -> int:
    count = 0
    step = n
    while step > 1:
        for _ in range(n):
            count += 1
        step //= 2
    return count


def ops_quadratic(n: int) -> int:
    count = 0
    for _ in range(n):
        for _ in range(n):
            count += 1
    return count


if __name__ == "__main__":
    print(f"{'Complexity':<14} | {'n = 100':>10} | {'n = 1,000':>12} | {'Growth (10x n)':>15}")
    print("-" * 60)

    routines = [
        ("O(1)", ops_constant),
        ("O(log n)", ops_logarithmic),
        ("O(n)", ops_linear),
        ("O(n log n)", ops_linearithmic),
        ("O(n^2)", ops_quadratic),
    ]

    for label, fn in routines:
        small = fn(100)
        large = fn(1_000)
        ratio = f"{large / small:.1f}x" if small > 0 else "1.0x"
        print(f"{label:<14} | {small:>10,} | {large:>12,} | {ratio:>15}")
```

## 4. Common Pitfalls and Best Practices

1. **Assuming Nested Loops Always Mean $O(n^2)$:**
   Not every nested loop is quadratic. If the outer loop runs $n$ times and the inner loop halves its counter on every step (`j //= 2`), total operations equal $n \log_2 n \implies$ **$O(n \log n)$**. Always trace how many times the innermost statement executes in total.
2. **Accidental $O(n^2)$ via Built-In Python Methods Inside Loops:**
   Calling `item in some_list`, `some_list.index(item)`, `some_list.pop(0)`, or repeated string concatenation `text += char` inside a loop over $n$ elements executes $O(n)$ work per iteration, silently turning $O(n)$ code into **$O(n^2)$**.
3. **Confusing $O(n \log n)$ Sorting with $O(n)$:**
   Calling `sorted(items)` inside a single-pass function makes the entire function **$O(n \log n)$**, not $O(n)$, because sorting dominates the linear pass ($O(n \log n + n) = O(n \log n)$).
4. **Selecting an Approach Based on Maximum Input Size ($n$):**
   * $n \le 10^3$: $O(n^2)$ passes comfortably within milliseconds.
   * $n \le 10^5$: Must optimize from $O(n^2)$ down to **$O(n \log n)$** or **$O(n)$** (typically using sorting, two pointers, or a hash `dict`/`set`).
   * $n \ge 10^7$: Requires **$O(n)$** or **$O(\log n)$** with low constant overhead.

## 5. Quick Reference

| Complexity | Scaling When $n$ Doubles ($2n$) | Core Algorithmic Clue | Canonical Examples |
| :--- | :--- | :--- | :--- |
| **$O(1)$** | Unchanged ($1\times$) | Fixed steps; no loops over input | `arr[i]`, `dict[k]`, `set.add()`, `deque.popleft()` |
| **$O(\log n)$** | Adds $+1$ step | Halves search space each step | Binary search, `heapq.heappush()`, balanced BST |
| **$O(n)$** | Doubles ($2\times$) | Single pass or sliding window | Linear search, `sum()`, `Counter()`, two pointers |
| **$O(n \log n)$** | Slightly more than $2\times$ | Divide-and-conquer + linear merge | `sorted()`, Merge Sort, Heap Sort, Quick Sort (avg) |
| **$O(n^2)$** | Quadruples ($4\times$) | All-pairs nested loops | Bubble/Selection/Insertion Sort, pair comparisons |
