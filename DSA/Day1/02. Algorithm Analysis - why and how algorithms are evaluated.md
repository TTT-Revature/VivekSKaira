# Algorithm Analysis: Why and How Algorithms Are Evaluated

## 1. Overview
**Algorithm analysis** is the systematic study of how much computational resources—primarily **execution time (CPU operations)** and **memory (RAM)**—an algorithm consumes as a function of its input size $n$.

* **Why Algorithms Are Evaluated:**
  * **Predicting Scalability:** An algorithm that finishes in 5 milliseconds for $n = 100$ records may take several hours for $n = 1,000,000$ records. Analysis reveals whether a solution will scale before it reaches production.
  * **Objective Comparison:** Allows engineers to compare two algorithms solving the same problem (for example, Linear Search vs. Binary Search) independently of CPU speed, operating system, compiler, or programming language.
  * **Bottleneck Identification:** Pinpoints which component of a pipeline dominates runtime or memory consumption so optimization efforts target the right code path.
  * **Meeting System Constraints:** Ensures software adheres to strict latency budgets (SLAs) and memory limits (such as embedded devices or containerized microservices).

---

## 2. Two Approaches to Evaluating Algorithms
Algorithms are evaluated using two complementary methodologies: **Experimental (Empirical)** analysis and **Theoretical (Analytical)** analysis.

### 1. Experimental Analysis (A Posteriori)
Experimental analysis involves implementing the algorithm, executing it on representative datasets, and measuring actual wall-clock runtime and peak memory usage.

* **Advantages:**
  * Captures real-world hardware effects such as CPU cache locality, branch prediction, garbage collection pauses, and interpreter overhead.
  * Measures exact constant factors that theoretical models ignore.
* **Limitations:**
  * Results vary across machines, CPU loads, and programming languages.
  * Requires writing and debugging full implementations for every candidate algorithm first.
  * Can only test a finite subset of inputs—it cannot prove performance across all possible inputs as $n \to \infty$.

### 2. Theoretical Analysis (A Priori)
Theoretical analysis evaluates an algorithm mathematically from its pseudocode or source code by expressing the number of primitive operations as a function of input size $n$.

* **The Random Access Machine (RAM) Model:**
  Theoretical analysis assumes a simplified abstract computer where:
  * Simple operations (arithmetic `+`, `-`, `*`, `/`, comparisons `<`, `==`, variable assignment, indexing `arr[i]`) each take **1 unit of time**.
  * Loops and function calls are not single operations; their cost equals the sum of the primitive operations executed inside them.
  * Memory access is uniform ($O(1)$ per access) with unlimited available memory.
* **Advantages:**
  * Completely independent of hardware, OS, and language implementation.
  * Evaluates behavior across **all** possible inputs and arbitrarily large input sizes.
  * Enables comparing designs **before** writing production code.

### Experimental vs. Theoretical Comparison

| Dimension | Experimental Analysis | Theoretical Analysis |
| :--- | :--- | :--- |
| **When Performed** | After implementation (*a posteriori*) | Before or after implementation (*a priori*) |
| **Hardware Dependency** | High (depends on CPU, RAM, cache, OS) | None (platform-independent mathematical model) |
| **Input Coverage** | Limited to tested benchmark datasets | Covers all valid inputs of arbitrary size $n$ |
| **Constant Factors** | Included in measurements | Abstracted away in asymptotic notation |
| **Primary Tools** | `time.perf_counter()`, `timeit`, `tracemalloc`, profilers | Operation counting, recurrence relations, asymptotic bounds |

## 3. Core Dimensions of Evaluation

### 1. Defining Input Size ($n$)
Resource growth is always measured relative to **input size $n$**, whose definition depends on the problem domain:
* **Arrays / Lists / Strings:** Number of elements or characters ($n = \text{len(data)}$).
* **Matrices / Grids:** Dimensions $R \times C$ (or $n^2$ for an $n \times n$ matrix).
* **Graphs:** Both number of vertices $V$ and number of edges $E$ (e.g., $O(V + E)$).
* **Numerical / Cryptographic Algorithms:** Number of bits $b = \lfloor \log_2 N \rfloor + 1$ required to represent an integer $N$.

### 2. Time Complexity vs. Space Complexity
* **Time Complexity:** Measures how the count of primitive CPU operations grows as $n$ increases.
* **Space Complexity:** Measures memory consumption as $n$ increases, divided into two components:
  * **Input Space:** Memory required to store the input arguments themselves.
  * **Auxiliary Space:** Extra temporary memory allocated by the algorithm during execution—including local variables, auxiliary data structures (`dict`, `set`, `list`), and **recursion call stack frames**. *(In software engineering, "space complexity" typically refers to auxiliary space.)*

---

## 4. Input Cases vs. Asymptotic Bounds
A frequent source of confusion is treating **input cases** (Best, Average, Worst) and **asymptotic notations** ($O$, $\Omega$, $\Theta$) as the same concept. They measure two distinct axes:

### 1. Input Cases (Which Input Distribution?)
For a fixed input size $n$, an algorithm's runtime can still vary depending on the arrangement of the data:

| Case | Meaning | Example: Linear Search on Array of Size $n$ |
| :--- | :--- | :--- |
| **Best Case** | Input configuration requiring the minimum possible steps | Target is at index `0` $\rightarrow$ $1$ comparison |
| **Average Case** | Expected number of steps over a uniform distribution of all valid inputs | Target is equally likely at any index $\rightarrow \approx \frac{n}{2}$ comparisons |
| **Worst Case** | Input configuration forcing the maximum possible steps (guaranteed ceiling) | Target is at index `n - 1` or absent $\rightarrow$ $n$ comparisons |
| **Amortized Case** | Average cost per operation across a worst-case **sequence** of $k$ operations | `list.append()` costs $O(n)$ on occasional resize, but $O(1)$ amortized over $n$ appends |

*(Engineering standard: **Worst-case analysis** is prioritized because it provides a strict upper-bound guarantee that holds for every input without probabilistic assumptions.)*

### 2. Asymptotic Notations (How Does the Growth Rate Bound?)
As $n \to \infty$, lower-order terms and constant multipliers become negligible compared to the **dominant term** (e.g., in $T(n) = 4n^2 + 12n + 50$, $n^2$ dominates). Asymptotic notation classifies this growth rate:

* **Big-O ($O(g(n))$ — Asymptotic Upper Bound):**
  $f(n) = O(g(n))$ means $f(n)$ grows **no faster than** $g(n)$ beyond some threshold $n_0$ (i.e., $f(n) \le c \cdot g(n)$ for constants $c > 0, n \ge n_0$).
* **Big-Omega ($\Omega(g(n))$ — Asymptotic Lower Bound):**
  $f(n) = \Omega(g(n))$ means $f(n)$ grows **at least as fast as** $g(n)$ beyond $n_0$ (i.e., $f(n) \ge c \cdot g(n)$).
* **Big-Theta ($\Theta(g(n))$ — Asymptotic Tight Bound):**
  $f(n) = \Theta(g(n))$ means $f(n)$ is bounded both above and below by $g(n)$ (both $O(g(n))$ and $\Omega(g(n))$ hold).

*(Note: Any input case can be described with any asymptotic notation. For instance, Quick Sort has a worst-case time of $\Theta(n^2)$ and an average-case time of $\Theta(n \log n)$.)*

## 5. Step-by-Step Guide: How to Evaluate an Algorithm

### Step 1: Analytical Operation Counting
To evaluate an iterative function analytically, count how many times each line executes as a function of $n$:

```python
def find_max_and_sum(numbers: list[int]) -> tuple[int, int]:
    """Return (maximum_value, total_sum) for a non-empty list of length n."""
    max_val = numbers[0]          # 1 operation (executed once)
    total = 0                     # 1 operation (executed once)

    for num in numbers:           # Loop runs n times
        total += num              # 1 operation * n = n
        if num > max_val:         # 1 comparison * n = n
            max_val = num         # At most 1 assignment * n = n (worst case)

    return max_val, total         # 1 operation (executed once)
```

* **Total Operations (Worst Case):** $T(n) = 1 + 1 + n + n + n + 1 = 3n + 3$.
* **Drop constants and lower-order terms:** Dominant term is $n \implies$ **Time Complexity: $\Theta(n)$**.
* **Auxiliary Space:** Only two scalar variables (`max_val`, `total`) are allocated regardless of $n \implies$ **Auxiliary Space Complexity: $\Theta(1)$**.

### Step 2: Evaluating Nested Loops and Logarithmic Loops
* **Independent Sequential Loops (Add):**
  Two consecutive loops of size $n$ and $m$ take $O(n + m)$ time.
* **Nested Dependent/Independent Loops (Multiply):**
  An outer loop running $n$ times with an inner loop running $n$ times takes $n \times n = O(n^2)$ time. Even if the inner loop runs $i$ times ($0 + 1 + 2 + \dots + (n - 1) = \frac{n(n-1)}{2}$), the dominant term remains $\Theta(n^2)$.
* **Halving / Multiplying Loop Variables (Logarithmic):**
  When the problem size is divided by a constant factor $b$ on every step ($n \to n/2 \to n/4 \to \dots \to 1$), the loop runs $\log_b n$ times $\implies$ **$O(\log n)$**.

### Step 3: Evaluating Recursive Algorithms
For recursive algorithms, express runtime as a **recurrence relation** $T(n)$:
* **Binary Search:** Cuts input in half with $O(1)$ work per step:
  $$T(n) = T(n/2) + O(1) \implies O(\log n) \text{ time, } O(\log n) \text{ call-stack space}$$
* **Merge Sort:** Splits into 2 halves and merges in $O(n)$ linear work:
  $$T(n) = 2T(n/2) + O(n) \implies O(n \log n) \text{ time, } O(n) \text{ auxiliary space}$$
* **Naive Recursive Fibonacci:** Branches into 2 calls of size $n - 1$ and $n - 2$:
  $$T(n) = T(n-1) + T(n-2) + O(1) \implies O(2^n) \text{ time, } O(n) \text{ call-stack space}$$

## 6. Combining Theoretical and Empirical Evaluation in Python
The script below evaluates two duplicate-detection algorithms both **theoretically** and **empirically** by doubling the input size $n$ and measuring runtime (`time.perf_counter()`) and peak auxiliary memory (`tracemalloc`):

```python
import time
import tracemalloc
from collections.abc import Callable


def has_duplicates_quadratic(items: list[int]) -> bool:
    """
    Theoretical Evaluation:
      - Worst-Case Time: O(n^2) -> doubling n increases runtime by ~4x
      - Auxiliary Space: O(1)   -> constant memory regardless of n
    """
    n = len(items)
    for i in range(n):
        for j in range(i + 1, n):
            if items[i] == items[j]:
                return True
    return False


def has_duplicates_linear(items: list[int]) -> bool:
    """
    Theoretical Evaluation:
      - Average/Worst-Case Time: O(n) -> doubling n increases runtime by ~2x
      - Auxiliary Space:         O(n) -> stores up to n items in hash set
    """
    seen: set[int] = set()
    for item in items:
        if item in seen:
            return True
        seen.add(item)
    return False


def benchmark(func: Callable[[list[int]], bool], data: list[int]) -> tuple[float, int]:
    """Measure elapsed milliseconds and peak auxiliary bytes allocated."""
    tracemalloc.start()
    start_time = time.perf_counter()

    func(data)

    elapsed_ms = (time.perf_counter() - start_time) * 1000
    _, peak_bytes = tracemalloc.get_traced_memory()
    tracemalloc.stop()
    return elapsed_ms, peak_bytes


if __name__ == "__main__":
    sizes = [1_000, 2_000, 4_000, 8_000]
    print(f"{'n':>7} | {'O(n^2) Time (ms)':>16} | {'O(n^2) RAM (B)':>14} | {'O(n) Time (ms)':>14} | {'O(n) RAM (B)':>12}")
    print("-" * 75)

    for size in sizes:
        # Worst-case input: all unique elements so full scan is required
        worst_case_input = list(range(size))
        t_quad, mem_quad = benchmark(has_duplicates_quadratic, worst_case_input)
        t_lin, mem_lin = benchmark(has_duplicates_linear, worst_case_input)
        print(f"{size:>7} | {t_quad:>16.3f} | {mem_quad:>14,} | {t_lin:>14.4f} | {mem_lin:>12,}")
```

### Interpreting the Scaling Ratios
When $n$ doubles from `4,000` to `8,000` ($2\times$ input):
* **`has_duplicates_quadratic` ($O(n^2)$):** Runtime increases by roughly $(2)^2 = 4\times$, while peak auxiliary RAM remains near `0` bytes ($O(1)$).
* **`has_duplicates_linear` ($O(n)$):** Runtime increases by roughly $(2)^1 = 2\times$, while peak auxiliary RAM grows linearly with $n$ ($O(n)$).

## 7. Common Pitfalls and Best Practices

1. **Benchmarking Only on Tiny Inputs ($n < 100$):**
   On small arrays, an $O(n^2)$ algorithm can beat an $O(n \log n)$ algorithm due to lower constant overhead (which is why Python's Timsort uses Insertion Sort for small runs). Always test scaling across multiple input magnitudes ($10^3, 10^4, 10^5, 10^6$).
2. **Equating "Big-O" with "Worst Case":**
   Big-O ($O$) is a mathematical **upper bound**, not a synonym for worst case. You can state the Big-O of the best case, average case, or worst case.
3. **Overlooking Hidden $O(n)$ Operations Inside Loops:**
   In Python, expressions such as `x in my_list`, `my_list.pop(0)`, `arr[1:]` (list slicing), and `result += chunk` (repeated string concatenation) are **$O(n)$ or $O(k)$**, not $O(1)$. Placing them inside a loop silently turns an $O(n)$ algorithm into $O(n^2)$.
4. **Forgetting Recursion Stack Depth in Space Complexity:**
   A recursive function that allocates no lists or dictionaries still consumes **$O(d)$ auxiliary space**, where $d$ is the maximum depth of the call stack (e.g., $O(n)$ space for recursive traversal of a skewed linked list or unbalanced tree).
5. **Ignoring Constant Factors and Cache Locality in Production:**
   When two algorithms share the same asymptotic class (for example, both are $O(n)$), contiguous array traversal (`list` or NumPy arrays) is significantly faster in practice than pointer-chasing linked structures due to CPU L1/L2 cache line prefetching.

## 8. Quick Reference

| Evaluation Aspect | Key Concept / Rule |
| :--- | :--- |
| **Goal of Analysis** | Quantify how execution time and auxiliary memory grow as input size $n \to \infty$ |
| **Theoretical Analysis** | Counts primitive RAM-model operations mathematically; hardware-independent |
| **Experimental Analysis** | Measures actual runtime (`time.perf_counter()`) and memory (`tracemalloc`) on real hardware |
| **Dominant Term Rule** | Drop constant multipliers and lower-order terms ($5n^2 + 20n + 9 \rightarrow \Theta(n^2)$) |
| **Input Cases** | Best (minimum work), Average (expected work), Worst (guaranteed upper ceiling), Amortized (sequence average) |
| **Asymptotic Bounds** | $O$ = Upper bound ($\le$), $\Omega$ = Lower bound ($\ge$), $\Theta$ = Tight bound ($=$) |
| **Auxiliary Space** | Extra memory allocated beyond input size $n$, including auxiliary containers and recursion stack frames |
| **Empirical Scaling Check** | Doubling $n$ yields $\approx 1\times$ for $O(1)$, $+c$ for $O(\log n)$, $\approx 2\times$ for $O(n)$, $\approx 4\times$ for $O(n^2)$ |
