# Introduction to Data Structures and Algorithms (DSA)

## 1. Overview
**Data Structures and Algorithms (DSA)** form the foundation of efficient software engineering. Together, they determine how data is organized in memory and how step-by-step computations transform that data into useful outputs.

* **Data Structure:**
  A specialized format for organizing, storing, retrieving, and updating data in memory so specific operations can be performed efficiently.
* **Algorithm:**
  A finite, well-defined, step-by-step procedure that takes a set of inputs, performs unambiguous operations, and produces a desired output in finite time.
* **Why DSA Matters in Software Engineering:**
  * **Scalability:** Choosing an $O(n \log n)$ algorithm over an $O(n^2)$ algorithm reduces runtime on 1,000,000 records from hours to milliseconds.
  * **Resource Efficiency:** Minimizes CPU cycles, RAM consumption, network payloads, and cloud infrastructure costs.
  * **System Design Literacy:** Databases (B-trees, LSM-trees), caches (hash tables, LRU queues), compilers (ASTs, graphs), and search engines (inverted indexes, tries) are built directly on core DSA primitives.

## 2. Data Structures: Classification and Taxonomy
Data structures are broadly categorized by how elements are arranged and accessed in memory:

### 1. Primitive vs. Non-Primitive Data Structures
* **Primitive Types:** Basic building blocks provided directly by the language (`int`, `float`, `bool`, `str` / characters).
* **Non-Primitive Types:** Composite structures built from primitives to model collections and relationships, divided into **Linear**, **Non-Linear**, and **Hash-Based** structures.

### 2. Linear Data Structures
Elements are arranged sequentially in a single level, where each element has a well-defined predecessor and/or successor:
* **Array / Dynamic Array (`list` in Python):** Contiguous block of memory supporting $O(1)$ random access by index.
* **Linked List:** Collection of nodes where each node stores data and a reference (pointer) to the next (and optionally previous) node; supports $O(1)$ insertion/deletion at known positions without shifting elements.
* **Stack (LIFO — Last-In, First-Out):** Restricts insertion (`push`) and removal (`pop`) to one end (the top); used in function call stacks, expression parsing, and undo mechanisms.
* **Queue / Deque (FIFO — First-In, First-Out):** Inserts at the rear (`enqueue`) and removes from the front (`dequeue`); used in task scheduling, breadth-first search (BFS), and message buffers.

### 3. Non-Linear Data Structures
Elements are organized hierarchically or in arbitrary networks rather than a single sequence:
* **Tree (Binary Tree, Binary Search Tree, Trie, B-Tree):** Acyclic hierarchical structure with a root node and child subtrees; enables fast hierarchical search, prefix matching, and range queries.
* **Heap / Priority Queue (`heapq` in Python):** Complete binary tree satisfying the heap property (parent is always smaller or larger than its children); provides $O(1)$ access to the minimum/maximum element and $O(\log n)$ insertion/extraction.
* **Graph:** Set of vertices (nodes) connected by directed or undirected, weighted or unweighted edges; models road networks, social connections, dependencies, and state machines.

### 4. Hash-Based (Associative) Data Structures
* **Hash Table / Hash Map (`dict` in Python):** Maps keys to values by passing keys through a hash function to compute bucket indices, achieving $O(1)$ average-case lookup, insertion, and deletion.
* **Hash Set (`set` in Python):** Stores unique elements backed by a hash table for $O(1)$ average-case membership testing and deduplication.

### Summary Comparison of Core Data Structures

| Data Structure | Organization | Primary Strength | Primary Weakness | Python Equivalent |
| :--- | :--- | :--- | :--- | :--- |
| **Dynamic Array** | Contiguous memory | $O(1)$ index lookup; cache-friendly | $O(n)$ insertion/deletion in middle | `list` |
| **Linked List** | Pointer-linked nodes | $O(1)$ insertion/deletion at ends | $O(n)$ sequential search; extra pointer memory | `collections.deque` (block-linked) |
| **Stack** | LIFO linear | $O(1)$ push and pop at top | No random access to middle elements | `list` (`append` / `pop`) or `deque` |
| **Queue** | FIFO linear | $O(1)$ enqueue at rear and dequeue at front | No random access | `collections.deque` (`append` / `popleft`) |
| **Hash Table** | Hash-indexed buckets | $O(1)$ average lookup, insert, delete by key | Unordered key hashing; higher memory overhead | `dict`, `set` |
| **Binary Heap** | Array-backed tree | $O(1)$ peek min/max; $O(\log n)$ push/pop | $O(n)$ search for arbitrary elements | `heapq` |
| **Binary Search Tree** | Ordered hierarchical | $O(\log n)$ search, predecessor/successor, range queries (when balanced) | Degrades to $O(n)$ if unbalanced | Third-party (`sortedcontainers`) |
| **Graph** | Vertices + edges | Models arbitrary many-to-many relationships | Higher traversal and representation complexity | `dict[node, list[neighbor]]` |

## 3. Algorithms: Properties and Design Paradigms

### 1. Five Essential Properties of an Algorithm
Every valid algorithm must satisfy five formal criteria:
1. **Input:** Accepts zero or more well-specified inputs.
2. **Output:** Produces at least one valid output directly related to the inputs.
3. **Definiteness:** Every instruction is clear, precise, and unambiguous.
4. **Finiteness:** Terminates after a finite number of steps for all valid inputs.
5. **Effectiveness:** Every step is basic enough to be executed accurately in finite time.

### 2. Core Algorithmic Paradigms

| Paradigm | Core Strategy | Classic Examples |
| :--- | :--- | :--- |
| **Brute Force** | Evaluates all possible candidates systematically without pruning | Linear search, naive substring matching |
| **Divide and Conquer** | Splits a problem into independent subproblems, solves them recursively, and merges results | Binary Search, Merge Sort, Quick Sort |
| **Two Pointers / Sliding Window** | Maintains moving indices over a linear sequence to avoid nested loops | Pair sum in sorted array, longest substring without repeats |
| **Greedy Algorithms** | Makes the locally optimal choice at each step hoping to reach a global optimum | Dijkstra's shortest path, Huffman coding, interval scheduling |
| **Dynamic Programming (DP)** | Breaks problems into **overlapping subproblems** and caches results (memoization or tabulation) | Fibonacci, 0/1 Knapsack, Edit Distance, Longest Common Subsequence |
| **Backtracking** | Explores decision trees depth-first and abandons ("prunes") invalid paths immediately | N-Queens, Sudoku solver, permutations/combinations |

## 4. Measuring Algorithm Efficiency (Asymptotic Analysis)
Measuring execution time with a stopwatch depends heavily on CPU speed, background load, and programming language. Instead, DSA evaluates scalability using **asymptotic complexity**—how time and memory grow as input size $n \to \infty$:

* **Time Complexity:** Number of elementary operations performed relative to input size $n$.
* **Space Complexity:** Extra (auxiliary) memory allocated by the algorithm beyond the input itself.
* **Big-O Notation ($O$):** Describes the **upper bound** (worst-case growth rate) of an algorithm's resource consumption, dropping constant factors and lower-order terms (e.g., $3n^2 + 5n + 10 \rightarrow O(n^2)$).

### Common Complexity Classes (Fastest to Slowest)

| Big-O Class | Name | Operations for $n = 10,000$ | Typical Example |
| :--- | :--- | :--- | :--- |
| **$O(1)$** | Constant | $1$ | Dictionary lookup (`d[key]`), array index access (`arr[i]`) |
| **$O(\log n)$** | Logarithmic | $\approx 14$ | Binary search on a sorted array |
| **$O(n)$** | Linear | $10,000$ | Finding the maximum element in an unsorted list |
| **$O(n \log n)$** | Linearithmic | $\approx 132,877$ | Efficient sorting (`sorted()`, Merge Sort, Timsort) |
| **$O(n^2)$** | Quadratic | $100,000,000$ | Nested loops comparing every pair of elements |
| **$O(2^n)$** | Exponential | $> 10^{3010}$ (infeasible) | Generating all subsets of a set without pruning |

### The Space-Time Trade-Off
Algorithms frequently trade **additional memory** to achieve **faster execution** (or vice versa):
* Using a hash `set` to remember seen items consumes $O(n)$ extra RAM, but reduces duplicate detection from $O(n^2)$ time to $O(n)$ time.

## 5. Practical Example: How Data Structure Choice Changes Performance
Consider solving the classic **Two-Sum Existence** problem: *Given a list of integers `nums` and a `target`, determine whether any two distinct elements add up to `target`.*

```python
import time


def has_pair_brute_force(nums: list[int], target: int) -> bool:
    """Check all pairs using nested loops: O(n^2) time, O(1) auxiliary space."""
    n = len(nums)
    for i in range(n):
        for j in range(i + 1, n):
            if nums[i] + nums[j] == target:
                return True
    return False


def has_pair_two_pointers(nums: list[int], target: int) -> bool:
    """Sort first, then converge from both ends: O(n log n) time, O(n) space for sorted copy."""
    ordered = sorted(nums)
    left, right = 0, len(ordered) - 1

    while left < right:
        current_sum = ordered[left] + ordered[right]
        if current_sum == target:
            return True
        if current_sum < target:
            left += 1
        else:
            right -= 1
    return False


def has_pair_hash_set(nums: list[int], target: int) -> bool:
    """Store seen values in a hash set for O(1) complement lookup: O(n) time, O(n) space."""
    seen: set[int] = set()
    for num in nums:
        complement = target - num
        if complement in seen:
            return True
        seen.add(num)
    return False


if __name__ == "__main__":
    sample_data = list(range(15_000))
    target_sum = 29_997  # 14998 + 14999 (worst-case position at end of list)

    for label, solver in [
        ("Brute Force  O(n^2)     ", has_pair_brute_force),
        ("Two Pointers O(n log n) ", has_pair_two_pointers),
        ("Hash Set     O(n)       ", has_pair_hash_set),
    ]:
        start = time.perf_counter()
        found = solver(sample_data, target_sum)
        elapsed_ms = (time.perf_counter() - start) * 1000
        print(f"{label} -> found={found} | runtime={elapsed_ms:.3f} ms")
```

## 6. Python Built-In Data Structures Under the Hood
Understanding how CPython implements its built-in containers helps you predict real-world performance immediately:

| Python Type | Internal Implementation | Average Time Complexities |
| :--- | :--- | :--- |
| **`list`** | Over-allocated contiguous array of object pointers | Index `lst[i]`: $O(1)$ \| `append`/`pop()`: $O(1)$ amortized \| `insert(0, x)` / `pop(0)`: $O(n)$ \| `x in lst`: $O(n)$ |
| **`tuple`** | Fixed-size contiguous array of object pointers | Index `tup[i]`: $O(1)$ \| `x in tup`: $O(n)$ \| Immutable and hashable (if elements are hashable) |
| **`dict`** | Compact open-addressed hash table (preserves insertion order) | `d[k]`, `d[k] = v`, `del d[k]`, `k in d`: $O(1)$ average ($O(n)$ worst-case collisions) |
| **`set`** | Open-addressed hash table storing keys only | `s.add(x)`, `s.remove(x)`, `x in s`: $O(1)$ average |
| **`collections.deque`** | Doubly-linked list of fixed-size memory blocks | `append`/`pop` and `appendleft`/`popleft`: $O(1)$ \| Middle indexing `dq[i]`: $O(n)$ |
| **`heapq`** | In-place binary min-heap stored inside a standard `list` | `heap[0]` (peek min): $O(1)$ \| `heappush` / `heappop`: $O(\log n)$ \| `heapify`: $O(n)$ |

## 7. Common Pitfalls and Best Practices

1. **Using a `list` for Repeated Membership Lookups (`x in items`):**
   Checking `if user_id in active_users:` inside a loop performs an $O(n)$ linear scan on every iteration, turning an $O(n)$ loop into $O(n^2)$. Convert the lookup collection to a **`set`** or **`dict`** first for $O(1)$ average lookups.
2. **Using `list.pop(0)` or `list.insert(0, x)` as a FIFO Queue:**
   Removing or inserting at index `0` of a Python `list` shifts every remaining element in memory ($O(n)$). Always use **`collections.deque`** (`append` and `popleft`) for $O(1)$ queue operations.
3. **Choosing an Algorithm Without Checking Input Constraints ($n$):**
   Before coding, examine the maximum expected input size:
   * $n \le 10^3$: $O(n^2)$ solutions are typically acceptable.
   * $n \le 10^5$: Requires $O(n \log n)$ or $O(n)$ solutions.
   * $n \ge 10^7$: Requires $O(n)$, $O(\log n)$, or streaming $O(1)$-space algorithms.
4. **Overlooking Edge Cases in Data Structures:**
   Always test algorithms against boundary inputs: empty collections (`[]`), single-element inputs (`[x]`), all-duplicate elements, already-sorted or reverse-sorted inputs, negative numbers, and disconnected graph components.
5. **Forgetting Python's Default Recursion Limit (`sys.getrecursionlimit()`):**
   Recursive algorithms (such as DFS on a skewed tree or deep recursion) hit Python's default stack limit (~1,000 frames) and raise `RecursionError`. Convert deep recursive traversals into explicit stack/queue iterative loops when input depth can exceed a few hundred levels.

## 8. Quick Reference

| Concept | Key Definition / Rule of Thumb |
| :--- | :--- |
| **Data Structure** | Organized memory layout determining access, insertion, and deletion efficiency |
| **Algorithm** | Finite, unambiguous, step-by-step procedure solving a computational problem |
| **Linear Structures** | `list` (array), `deque` (linked queue/stack) — sequential element order |
| **Non-Linear Structures** | Trees, Heaps (`heapq`), Graphs — hierarchical or networked relationships |
| **Associative Structures** | `dict`, `set` — hash-based $O(1)$ average key/membership lookup |
| **Time vs. Space Complexity** | Asymptotic growth rate of CPU operations vs. auxiliary memory as input size $n$ grows |
| **Space-Time Trade-Off** | Using extra memory (e.g., hash table or DP table) to eliminate redundant computation |
