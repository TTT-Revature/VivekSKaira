# `import` and `from ... import`

## 1. Overview
Python provides two primary statement forms to bring code from external modules into the current namespace:

* **`import module`:** Loads the entire module and binds the **module object** itself to a name in your current namespace. Members are accessed via dot notation (`module.member`).
* **`from module import member`:** Loads the module into memory and binds **specific attributes** (functions, classes, constants) directly into your current namespace so they can be used without a module prefix.

*(Important Under-the-Hood Fact: Both forms execute the entire target module once and cache it in `sys.modules`. Using `from module import func` does not skip loading the rest of the module or save memory—it only changes which names are bound in your local namespace.)*

---

## 2. The `import` Statement

### Basic Usage (`import module`)
Binds the module name directly in the current scope. Every function, class, or variable from that module must be qualified with `module_name.`:

```python
import math
import os

print(math.sqrt(64))          # 8.0
print(math.pi)                # 3.141592653589793
print(os.getcwd())            # Current working directory path
```

### Importing with an Alias (`import module as alias`)
Creates a shorter or conflict-free local name for the module object:

```python
import datetime as dt

today = dt.date.today()
print(today)
```

### PEP 8 Formatting Rule
Always place separate `import` statements on individual lines rather than comma-separating different modules on one line:

```python
# Recommended (PEP 8)
import os
import sys

# Discouraged
import os, sys
```

---

## 3. The `from ... import` Statement

### Importing Specific Items
Extracts named objects from a module and binds them directly into the current namespace:

```python
from math import sqrt, factorial, pi

print(sqrt(49))        # 7.0
print(factorial(5))    # 120
print(round(pi, 4))    # 3.1416
```

### Multi-Line Imports with Parentheses
When importing several items from the same module, wrap them in parentheses `()` to keep lines within PEP 8's 79-character limit cleanly:

```python
from collections import (
    Counter,
    defaultdict,
    deque,
    namedtuple,
)
```

### Aliasing Imported Items (`from module import item as alias`)
Useful when an imported name is long or collides with an existing variable or function name in your script:

```python
from datetime import datetime as dt_class
from math import gcd as greatest_common_divisor

print(greatest_common_divisor(24, 36))  # 12
print(dt_class.now().year)              # Current year
```

## 4. Wildcard Imports (`from module import *`) and `__all__`
A wildcard import copies all public attributes from a module into the current namespace:

```python
from math import *

print(sin(0))   # 0.0
print(cos(0))   # 1.0
```

### Controlling Exports with `__all__`
* By default, `from module import *` imports every name that does **not** begin with a leading underscore (`_`).
* A module author can define a list of strings named `__all__` to explicitly restrict which names are exported by a wildcard import:

```python
# Inside custom_utils.py
__all__ = ["public_helper"]

def public_helper():
    return "Exported"

def another_func():
    return "Not exported by 'import *'"
```

### Why `from module import *` Is Discouraged
1. **Namespace Pollution:** Floods your scope with dozens of unexpected names.
2. **Silent Overwriting:** Can quietly overwrite existing variables or functions that share the same name.
3. **Reduced Readability:** Makes it unclear which module a function came from and breaks static analysis tools.

## 5. Crucial Behavioral Difference: Rebinding Module Variables
A subtle but important distinction arises when a module defines a global variable that gets reassigned later during program execution:

* **`import config`:** Always looks up `config.DEBUG` dynamically on the module object, so updates made by other modules are visible.
* **`from config import DEBUG`:** Copies the reference at import time into a new local variable `DEBUG`. If `config.DEBUG` is later reassigned to a new value, your local `DEBUG` still points to the old value.

```python
# Suppose config.py contains: DEBUG = False

# Approach 1: Qualified access reflects updates to config.DEBUG
import config
config.DEBUG = True
print(config.DEBUG)  # True

# Approach 2: Direct import binds the original value locally
from config import DEBUG
config.DEBUG = False
print(DEBUG)         # Still True (local reference was not updated)
```

## 6. PEP 8 Import Structure and Ordering
Place all imports at the **top of the file** (immediately after module docstrings and before module constants/code), organized into three distinct groups separated by a single blank line:

```python
"""Sample module demonstrating PEP 8 import organization."""

# 1. Standard library imports
import json
import os
from pathlib import Path

# 2. Related third-party imports
import requests
from pydantic import BaseModel

# 3. Local application / project imports
import metrics_utils
from app.services import auth_service
```

## 7. `import` vs. `from ... import`: Decision Guide

| Criteria | `import module` | `from module import item` |
| :--- | :--- | :--- |
| **Namespace Cleanliness** | High (only 1 module name added) | Lower (adds each imported item directly) |
| **Origin Clarity** | Explicit (`json.loads()`, `os.path.join()`) | Implicit (`loads()`, `join()`) |
| **Risk of Name Collision** | Very low | Higher (e.g., `open`, `format`, `id`, `type`) |
| **Live Module State Updates** | Sees reassigned module attributes | Holds snapshot reference from import time |
| **Best Used When** | Using many items from a module, or when module context clarifies meaning (`re.sub`, `json.dump`) | Importing 1–3 distinct classes/functions or submodules (`from pathlib import Path`) |
