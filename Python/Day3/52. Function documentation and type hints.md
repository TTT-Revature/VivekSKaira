# Function Documentation and Type Hints

## 1. Overview
Because Python is a dynamically typed language, reading a function signature alone does not always reveal what data types it expects or what behavior it performs. Python solves this using two complementary standards:

* **Docstrings (PEP 257):** Human-readable string literals placed at the start of a function to explain **what** the function does, its parameters, return values, and potential exceptions.
* **Type Hints / Annotations (PEP 484):** Optional metadata attached to parameters and return values specifying **expected data types** for IDEs, linters, and static type checkers (such as `mypy` or `pyright`).
* **Zero Runtime Enforcement:** Python stores both docstrings and type annotations as metadata on the function object, but **does not enforce type hints at runtime**.

---

## 2. Function Documentation (Docstrings — PEP 257)
A **docstring** is a string literal enclosed in triple double-quotes (`"""..."""`) placed as the **first statement** inside a function body.

### 1. Single-Line Docstrings
Used for short, self-explanatory functions where the summary fits on a single line (closing quotes stay on the same line):

```python
def celsius_to_fahrenheit(celsius: float) -> float:
    """Convert a temperature from Celsius to Fahrenheit."""
    return (celsius * 9 / 5) + 32
```

### 2. Multi-Line Docstrings (Google Style)
Used for non-trivial functions. Start with a concise one-line summary in the imperative mood, followed by a blank line, and structured sections (`Args:`, `Returns:`, `Raises:`):

```python
def calculate_discount(price: float, discount_percent: float) -> float:
    """Calculate the final price after applying a percentage discount.

    Args:
        price: Original item price before discount (must be non-negative).
        discount_percent: Discount percentage between 0 and 100.

    Returns:
        Final discounted price rounded to two decimal places.

    Raises:
        ValueError: If price is negative or discount_percent is outside 0-100.
    """
    if price < 0 or not (0 <= discount_percent <= 100):
        raise ValueError("Invalid price or discount percentage.")
    return round(price * (1 - discount_percent / 100), 2)
```

### Accessing Docstrings at Runtime
Python attaches a function's docstring to its `__doc__` attribute and displays it via the built-in `help()` function:

```python
print(celsius_to_fahrenheit.__doc__)
# Output: Convert a temperature from Celsius to Fahrenheit.

help(calculate_discount)
```

## 3. Basic Type Hints (PEP 484)
Type hints annotate parameters using `param: type` and return values using `-> return_type` before the colon `:`.

### Standard Parameter and Return Annotations
```python
# Parameters with default values place '= default' after the type annotation
def format_badge(name: str, batch_id: int, active: bool = True) -> str:
    status = "ACTIVE" if active else "INACTIVE"
    return f"[{batch_id}] {name} ({status})"

print(format_badge("Vivek", 101))
# Output: [101] Vivek (ACTIVE)
```

### Annotating Functions That Return Nothing (`-> None`)
When a function performs an action (such as printing or mutating a list in place) without returning a value, annotate its return type as `-> None`:

```python
def log_event(message: str) -> None:
    print(f"[EVENT] {message}")
```

### Annotating `*args` and `**kwargs`
Annotate `*args` with the expected type of **each individual positional argument**, and `**kwargs` with the expected type of **each keyword argument's value**:

```python
def summarize_metrics(label: str, *scores: int, **metadata: str) -> None:
    print(f"{label}: scores={scores}, metadata={metadata}")

summarize_metrics("Week 2", 88, 92, 95, track="FDE", status="Completed")
```

### Inspecting Annotations at Runtime (`__annotations__`)
```python
print(format_badge.__annotations__)
# Output: {'name': <class 'str'>, 'batch_id': <class 'int'>, 'active': <class 'bool'>, 'return': <class 'str'>}
```

## 4. Annotating Collections, Optionals, and Unions
Modern Python (3.9+ and 3.10+) supports clean, built-in type syntax without needing legacy imports from the `typing` module:

```python
from collections.abc import Callable
from typing import Any

# 1. Built-in generic collections (Python 3.9+)
def get_top_scores(scores: list[int], count: int = 3) -> list[int]:
    return sorted(scores, reverse=True)[:count]

def map_trainees(records: list[tuple[int, str]]) -> dict[int, str]:
    return {uid: name for uid, name in records}

# 2. Union types using '|' (Python 3.10+; replaces typing.Union[int, float])
def normalize_number(value: int | float) -> float:
    return float(value)

# 3. Optional values using 'Type | None' (replaces typing.Optional[str])
def find_email(username: str, directory: dict[str, str]) -> str | None:
    return directory.get(username)

# 4. Callable (functions passed as arguments): Callable[[ArgTypes...], ReturnType]
def apply_operation(x: int, y: int, op: Callable[[int, int], int]) -> int:
    return op(x, y)

# 5. Any (opts out of type checking for dynamic payloads)
def debug_payload(payload: Any) -> None:
    print(repr(payload))
```

## 5. Runtime Behavior vs. Static Type Checking (`mypy`)
Python's interpreter ignores type hints during execution—passing an unexpected type will **not** raise a `TypeError` unless an operation inside the function body fails.

```python
def add_numbers(a: int, b: int) -> int:
    return a + b

# Python allows this at runtime because '+' works on strings:
print(add_numbers("Py", "thon"))  # 'Python' (no runtime error!)
```

To catch type mismatches before running your code, use a **static type checker** such as `mypy` from the terminal:

```bash
pip install mypy
mypy script.py
# Output: error: Argument 1 to "add_numbers" has incompatible type "str"; expected "int"
```

---

## 6. Best Practices
* **Do Not Duplicate Types in Docstrings:** When type hints are present in the signature, omit redundant `(int)` or `(str)` type labels inside the docstring `Args:` section and focus on meaning, constraints, and edge cases.
* **Annotate Public Functions:** Prioritize adding docstrings and type hints to public functions, utility modules, and API boundaries.
* **Keep Docstrings Synchronized:** Whenever you modify a function's parameters, defaults, or return behavior, update its docstring and type annotations at the same time.

## 7. Quick Reference

| Feature | Syntax Example | Purpose |
| :--- | :--- | :--- |
| **Docstring** | `"""Summary of function."""` | Documents function purpose, arguments, return value, and errors (PEP 257) |
| **Inspect Docstring** | `func.__doc__` / `help(func)` | Reads the docstring at runtime |
| **Parameter & Return Hint** | `def f(x: int, y: str = "a") -> bool:` | Declares expected input and output types (PEP 484) |
| **Void Return Hint** | `def log(msg: str) -> None:` | Indicates the function returns `None` |
| **Generic Collections** | `list[str]`, `dict[str, int]`, `set[int]` | Specifies element/key/value types inside containers (Python 3.9+) |
| **Union / Optional Hint** | `int \| float` / `str \| None` | Allows multiple types or `None` (Python 3.10+) |
| **Callable Hint** | `Callable[[int, int], float]` | Annotates a function parameter taking `(int, int)` and returning `float` |
| **Static Type Check** | `mypy filename.py` | Validates type annotations statically without executing the code |
