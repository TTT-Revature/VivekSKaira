# Inheritance and Method Overriding in Python

## 1. Overview
**Inheritance** is a core Object-Oriented Programming (OOP) mechanism that allows a new class (the **child**, **derived**, or **subclass**) to acquire the attributes and methods of an existing class (the **parent**, **base**, or **superclass**).

* **Core Purpose:** Promotes code reuse, models hierarchical **"is-a"** relationships (e.g., a `Trainer` *is an* `Employee`; a `SavingsAccount` *is a* `BankAccount`), and enables polymorphism.
* **Implicit Root Class (`object`):** In Python 3, every class implicitly inherits from the built-in **`object`** base class—even when no parentheses are written (`class Foo:` is equivalent to `class Foo(object):`).
* **Method Overriding:** Occurs when a subclass defines a method with the **same name** as a method in its superclass, replacing or extending the inherited behavior for instances of that subclass.

## 2. Single Inheritance and Runtime Type Checks
To inherit from a parent class, pass the parent class name in parentheses after the subclass name: `class SubClass(SuperClass):`.

```python
class Employee:
    """Base class representing a general company employee."""

    company = "Revature"

    def __init__(self, emp_id: int, name: str, base_salary: float) -> None:
        self.emp_id = emp_id
        self.name = name
        self.base_salary = base_salary

    def get_details(self) -> str:
        return f"[{self.emp_id}] {self.name} ({self.company})"

    def calculate_pay(self) -> float:
        return self.base_salary

class Trainer(Employee):
    """Subclass inheriting attributes and methods from Employee."""

    def assign_batch(self, batch_code: str) -> str:
        return f"{self.name} assigned to batch {batch_code}"

# Trainer inherits __init__, company, get_details(), and calculate_pay()
trainer = Trainer(101, "Vivek", 60000.0)
print(trainer.get_details())          # [101] Vivek (Revature)
print(trainer.calculate_pay())        # 60000.0
print(trainer.assign_batch("FDE-04")) # Vivek assigned to batch FDE-04
```

### Checking Inheritance Relationships (`isinstance` & `issubclass`)
Python provides two built-in functions to inspect class hierarchies at runtime:

```python
print(isinstance(trainer, Trainer))    # True (direct instance)
print(isinstance(trainer, Employee))   # True (instance of a subclass of Employee)
print(isinstance(trainer, object))     # True (all classes inherit from object)

print(issubclass(Trainer, Employee))   # True
print(issubclass(Employee, Trainer))   # False
print(issubclass(Trainer, Trainer))    # True (a class is considered a subclass of itself)
```

## 3. Method Overriding and `super()`
When a subclass needs specialized behavior, it can **override** an inherited method by redefining it inside the subclass body. There are two primary patterns:

1. **Complete Replacement:** The subclass provides an entirely new implementation without calling the parent method.
2. **Behavior Extension (`super()`):** The subclass calls **`super().method_name(...)`** to execute the parent's logic first (or last) and adds subclass-specific behavior around it.

### Using `super()` in `__init__` and Regular Methods
**`super()`** returns a temporary proxy object that delegates method calls to the next class in the Method Resolution Order (MRO). Always use `super()` rather than hardcoding the parent class name.

```python
class Employee:
    def __init__(self, emp_id: int, name: str, base_salary: float) -> None:
        self.emp_id = emp_id
        self.name = name
        self.base_salary = base_salary

    def get_details(self) -> str:
        return f"[{self.emp_id}] {self.name}"

    def calculate_pay(self) -> float:
        return self.base_salary

class TechnicalTrainer(Employee):
    def __init__(
        self,
        emp_id: int,
        name: str,
        base_salary: float,
        track: str,
        session_bonus: float,
    ) -> None:
        # Delegate shared attribute initialization to Employee.__init__
        super().__init__(emp_id, name, base_salary)
        self.track = track
        self.session_bonus = session_bonus

    # Extending parent behavior with super()
    def get_details(self) -> str:
        base_info = super().get_details()
        return f"{base_info} | Track: {self.track}"

    # Extending parent calculation with super()
    def calculate_pay(self) -> float:
        return super().calculate_pay() + self.session_bonus

tt = TechnicalTrainer(202, "Vivek", 60000.0, "FDE Python", 12000.0)
print(tt.get_details())    # [202] Vivek | Track: FDE Python
print(tt.calculate_pay())  # 72000.0
```

## 4. Forms of Inheritance in Python
Python supports several inheritance topologies depending on domain requirements:

| Inheritance Type | Structure | Syntax Example | Description |
| :--- | :--- | :--- | :--- |
| **Single** | `A -> B` | `class B(A):` | One child class inherits from one parent class |
| **Multilevel** | `A -> B -> C` | `class B(A): ... class C(B):` | A subclass acts as a parent for another subclass |
| **Hierarchical** | `A -> B`, `A -> C` | `class B(A): ... class C(A):` | Multiple independent subclasses share one common parent |
| **Multiple** | `A, B -> C` | `class C(A, B):` | One child class inherits from two or more parent classes |

### Multiple Inheritance and Mixins
In modern Python, multiple inheritance is most cleanly applied using **Mixins**—small, focused helper classes that add a reusable capability (such as JSON serialization or timestamping) without standing alone as full domain entities:

```python
import json
from datetime import datetime, timezone

class TimestampMixin:
    """Provides UTC creation timestamp metadata."""

    def get_timestamp(self) -> str:
        return datetime.now(timezone.utc).isoformat()

class JsonSerializableMixin:
    """Serializes an object's __dict__ attributes to a JSON string."""

    def to_json(self) -> str:
        return json.dumps(self.__dict__, indent=2)

class AuditEvent(TimestampMixin, JsonSerializableMixin):
    def __init__(self, action: str, actor: str) -> None:
        self.action = action
        self.actor = actor
        self.created_at = self.get_timestamp()

event = AuditEvent("REPO_PUSH", "vivek")
print(event.to_json())
```

## 5. Method Resolution Order (MRO) and the Diamond Problem
When multiple inheritance is used—especially in a **diamond hierarchy** where two parent classes inherit from the same grandparent class—Python must determine the exact order in which classes are searched for attributes and methods.

### C3 Linearization Algorithm
Python computes a deterministic **Method Resolution Order (MRO)** using the **C3 Linearization** algorithm, which guarantees three rules:
1. Subclasses are always searched **before** their base classes.
2. Base classes listed in `class Child(Parent1, Parent2):` are searched **left to right**.
3. No class is visited more than once; any shared ancestor is pushed after all of its subclasses.

You can inspect any class's MRO via **`ClassName.__mro__`** (returns a tuple) or **`ClassName.mro()`** (returns a list).

```python
class BaseService:
    def execute(self) -> str:
        return "BaseService"

class AuthMiddleware(BaseService):
    def execute(self) -> str:
        return f"AuthMiddleware -> {super().execute()}"

class LoggingMiddleware(BaseService):
    def execute(self) -> str:
        return f"LoggingMiddleware -> {super().execute()}"

# Diamond inheritance: Pipeline -> (AuthMiddleware, LoggingMiddleware) -> BaseService
class ApiPipeline(AuthMiddleware, LoggingMiddleware):
    def execute(self) -> str:
        return f"ApiPipeline -> {super().execute()}"

print([cls.__name__ for cls in ApiPipeline.__mro__])
# ['ApiPipeline', 'AuthMiddleware', 'LoggingMiddleware', 'BaseService', 'object']

pipeline = ApiPipeline()
print(pipeline.execute())
# ApiPipeline -> AuthMiddleware -> LoggingMiddleware -> BaseService
```
*(Notice how `super().execute()` inside `AuthMiddleware` delegates to `LoggingMiddleware`—the next class in `ApiPipeline.__mro__`—rather than jumping directly to `BaseService`.)*

## 6. Inheritance ("is-a") vs. Composition ("has-a")
Not every code-reuse scenario should use inheritance. When one class simply uses another class as a component, prefer **composition** (storing an instance of the helper class as an attribute):

| Criterion | Inheritance ("is-a") | Composition ("has-a") |
| :--- | :--- | :--- |
| **Relationship** | Subclass is a specialized kind of superclass (`Car` is a `Vehicle`) | Class owns or collaborates with another object (`Car` has an `Engine`) |
| **Coupling** | Tight coupling; changes in parent affect all descendants | Loose coupling; components can be swapped or mocked easily |
| **Polymorphism** | Subclasses pass `isinstance(obj, Parent)` checks automatically | Achieved via duck typing or shared interfaces |
| **When to Prefer** | True specialization hierarchies and mixins | Complex systems, runtime component swapping, avoiding deep trees |

## 7. Common Pitfalls and Best Practices

### 1. Forgetting to Call `super().__init__(...)`
When a subclass defines its own `__init__`, Python **does not** call the parent's `__init__` automatically. Omitting `super().__init__(...)` leaves parent attributes uninitialized and triggers `AttributeError`:

```python
class Device:
    def __init__(self, serial_no: str) -> None:
        self.serial_no = serial_no

class Sensor(Device):
    def __init__(self, serial_no: str, unit: str) -> None:
        super().__init__(serial_no)  # Required so self.serial_no is initialized
        self.unit = unit
```

### 2. Calling `ParentClass.__init__(self, ...)` Directly Instead of `super()`
Hardcoding `ParentClass.method(self)` bypasses the MRO chain and causes shared grandparent initializers to run twice in diamond inheritance hierarchies. Always use `super()`.

### 3. Breaking the Liskov Substitution Principle (LSP) When Overriding
An overridden method should honor the parent method's contract—accepting compatible arguments and returning a compatible return type—so any code expecting a `Parent` object works seamlessly when given a `Child` object.

### 4. Overriding Class Attributes vs. Mutating Shared Collections
Assigning `class Child(Parent): rate = 0.2` cleanly overrides `Parent.rate` for `Child` without modifying `Parent.rate`. However, mutating a list or dict defined on `Parent` (`Child.items.append("x")`) mutates the shared object across both `Parent` and `Child`.

## 8. Quick Reference

| Construct / Function | Syntax | Purpose |
| :--- | :--- | :--- |
| Define subclass | `class Child(Parent):` | Inherits attributes and methods from `Parent` |
| Multiple inheritance | `class Child(ParentA, ParentB):` | Inherits from multiple classes; searched left to right |
| Call parent method | `super().method(args)` | Delegates to the next class in the MRO chain |
| Override method | Redefine `def method(self, ...):` in child | Replaces or extends inherited behavior |
| Instance check | `isinstance(obj, ClassOrTuple)` | Returns `True` if `obj` is an instance of class or any subclass |
| Subclass check | `issubclass(SubCls, ParentCls)` | Returns `True` if `SubCls` inherits from `ParentCls` |
| Inspect MRO | `ClassName.__mro__` / `ClassName.mro()` | Shows the C3-linearized method lookup sequence |
