# Unit Testing Concepts in Python

## 1. Overview
**Unit testing** is the practice of verifying that the smallest testable parts of an application—typically individual functions, methods, or classes—behave as expected in isolation. The specific component being verified in a test is called the **System Under Test (SUT)**.

* **Why Unit Testing Matters:**
  * **Early Bug Detection:** Catches logic errors immediately during development before code reaches integration or production.
  * **Safe Refactoring:** Gives developers confidence to restructure internal implementation details while proving external behavior remains intact.
  * **Living Documentation:** Well-named unit tests demonstrate how functions should be called and what outputs or exceptions they produce for given inputs.
  * **Better Code Design:** Code that is easy to unit test is naturally modular, loosely coupled, and follows single-responsibility principles.

### Where Unit Tests Fit: The Testing Pyramid
Automated test suites are typically structured as a three-tier pyramid balancing execution speed, isolation, and confidence:

| Layer | Scope | Speed & Cost | External Dependencies |
| :--- | :--- | :--- | :--- |
| **End-to-End (E2E) Tests** | Entire user workflows through UI/HTTP APIs | Slowest; highest maintenance cost | Real databases, services, and network calls |
| **Integration Tests** | Interactions between multiple modules, databases, or external APIs | Moderate speed and setup cost | Real or containerized databases, filesystems, queues |
| **Unit Tests (Base Layer)** | Single functions, methods, or classes in isolation | Fastest (milliseconds); lowest cost | Replaced with lightweight **test doubles** (stubs/mocks) |

## 2. Anatomy of a Unit Test: The AAA Pattern
Almost every well-structured unit test follows the **AAA (Arrange, Act, Assert)** pattern—also known in Behavior-Driven Development (BDD) as **Given, When, Then**:

1. **Arrange (Given):** Set up the test data, initialize objects, and configure any required preconditions or test doubles.
2. **Act (When):** Invoke the single function or method being tested with the arranged inputs.
3. **Assert (Then):** Verify that the returned value, state mutation, or raised exception matches the expected outcome.

```python
# Production code: src/billing/discounts.py
def calculate_discounted_price(price: float, discount_percent: float) -> float:
    """Return final price after applying a percentage discount (0 to 100)."""
    if price < 0:
        raise ValueError("Price cannot be negative")
    if not 0 <= discount_percent <= 100:
        raise ValueError("Discount percent must be between 0 and 100")
    return round(price * (1 - discount_percent / 100), 2)
```

```python
# Unit test following Arrange-Act-Assert
def test_calculate_discounted_price_applies_valid_percentage() -> None:
    # Arrange
    original_price = 200.0
    discount = 15.0

    # Act
    final_price = calculate_discounted_price(original_price, discount)

    # Assert
    assert final_price == 170.0
```

## 3. Properties of Effective Unit Tests: FIRST Principles
High-quality unit tests adhere to the **FIRST** acronym:

| Principle | Meaning | Practical Requirement |
| :--- | :--- | :--- |
| **F — Fast** | Tests execute in milliseconds | Avoid `time.sleep()`, disk I/O, network requests, or database queries |
| **I — Independent** | Each test runs standalone in any order | Never rely on state created or mutated by a previously executed test |
| **R — Repeatable** | Same result every run across any machine | Eliminate randomness (`random`), system clock dependencies (`datetime.now()`), and environment coupling |
| **S — Self-Validating** | Clear boolean pass/fail verdict | Use automated assertions (`assert`), never manual `print()` inspection |
| **T — Timely** | Written alongside or before production code | Write tests during feature development rather than deferring them indefinitely |

## 4. Designing Test Cases: Paths and Boundaries
Testing only a single normal input leaves edge cases and failure modes unverified. Comprehensive unit testing covers four distinct categories of inputs:

### 1. Happy Path (Nominal Cases)
Standard, valid inputs representing normal everyday usage (e.g., `calculate_discounted_price(100.0, 20.0) == 80.0`).

### 2. Boundary Values and Edge Cases
Bugs cluster at the edges of valid input domains—such as `0`, negative numbers, empty collections (`""`, `[]`, `{}`), `None`, single-element lists, and inclusive/exclusive thresholds (`<` vs. `<=`):

```python
def test_calculate_discounted_price_boundaries() -> None:
    # Lower boundary: 0% discount leaves price unchanged
    assert calculate_discounted_price(50.0, 0.0) == 50.0
    # Upper boundary: 100% discount reduces price to zero
    assert calculate_discounted_price(50.0, 100.0) == 0.0
    # Zero price edge case
    assert calculate_discounted_price(0.0, 25.0) == 0.0
```

### 3. Negative Cases (Error and Exception Handling)
Verify that invalid inputs fail fast with the expected exception type and informative message rather than silently returning corrupted values.

### 4. State Transitions vs. Return Values
* **Pure Functions:** Tested by asserting the **return value** for given inputs.
* **Stateful Objects:** Tested by calling a mutating method (`cart.add_item(...)`) and asserting the resulting object state (`len(cart.items) == 1` and `cart.total == 25.0`).

## 5. Isolating Units with Test Doubles
A unit test must fail **only** when the unit under test has a bug—not because an external database is offline, a third-party REST API timed out, or the system clock ticked past midnight.

### Dependency Injection Enables Isolation
Passing dependencies (such as a database repository, HTTP client, or clock) into a function or class rather than hardcoding them internally allows tests to substitute lightweight **test doubles**:

```python
from typing import Protocol


class ExchangeRateProvider(Protocol):
    def get_rate(self, base: str, target: str) -> float: ...


def convert_currency(amount: float, base: str, target: str, provider: ExchangeRateProvider) -> float:
    """Convert amount using an injected exchange rate provider."""
    rate = provider.get_rate(base, target)
    return round(amount * rate, 2)


# Lightweight Fake/Stub replacing a live external currency API during unit testing
class StubRateProvider:
    def __init__(self, fixed_rate: float) -> None:
        self.fixed_rate = fixed_rate

    def get_rate(self, base: str, target: str) -> float:
        return self.fixed_rate


def test_convert_currency_uses_provider_rate() -> None:
    stub_provider = StubRateProvider(fixed_rate=84.50)
    result = convert_currency(10.0, "USD", "INR", provider=stub_provider)
    assert result == 845.0
```

### The Five Types of Test Doubles
| Test Double | Role in Unit Testing | Example |
| :--- | :--- | :--- |
| **Dummy** | Passed solely to satisfy a parameter signature; never actually used | Passing `None` or an empty object for an unused logger parameter |
| **Stub** | Returns hardcoded, predetermined answers to calls made during the test | `StubRateProvider` returning `84.50` without making network calls |
| **Spy** | Wraps or records how a dependency was called (call count, arguments) for later assertion | Recording that `email_sender.send()` was invoked once with `"user@example.com"` |
| **Mock** | Pre-programmed object with expectations verifying specific method calls and arguments | `unittest.mock.MagicMock` asserting `.assert_called_once_with(...)` |
| **Fake** | Working, simplified in-memory implementation of a real dependency | An in-memory dictionary repository replacing a PostgreSQL database |

## 6. Test-Driven Development (TDD) and Code Coverage

### 1. Test-Driven Development (Red-Green-Refactor)
**TDD** is a development workflow where unit tests drive software design before implementation code is written:

1. **Red:** Write a small failing unit test for a new behavior or requirement.
2. **Green:** Write the simplest possible production code required to make the test pass.
3. **Refactor:** Clean up duplication, improve naming, and refine design while keeping all tests green.

### 2. Code Coverage Metrics
**Code coverage** measures what percentage of production code executes while running the test suite:
* **Line (Statement) Coverage:** Percentage of executable lines run during tests.
* **Branch Coverage:** Percentage of conditional branches (`if` true path AND `else` false path) exercised during tests.

*(Important Limitation: High coverage (e.g., 95%–100%) only proves that lines were **executed**, not that their outputs were **verified**. A test that runs a function without meaningful `assert` statements achieves 100% coverage while catching zero bugs.)*

## 7. Common Pitfalls and Best Practices

1. **Testing Implementation Details Instead of Public Behavior:**
   Asserting on private helper methods (`_internal_step()`) or internal data structures couples tests tightly to internal code. Test through the public interface so internal refactoring does not break valid tests.
2. **Sharing Mutable State Across Tests:**
   Mutating a module-level list, global variable, or shared class attribute inside one test causes order-dependent failures in subsequent tests. Create fresh fixtures/objects per test.
3. **Writing Logic (`if`, `for`, `try`) Inside Unit Tests:**
   Complex control flow inside test functions can contain bugs of its own and obscure what is being verified. Keep unit tests linear, declarative, and easy to read at a glance.
4. **Over-Mocking Everything:**
   Mocking simple value objects or pure helper functions makes tests brittle and verbose. Use real objects for pure domain logic, and reserve mocks/stubs for slow, non-deterministic, or external I/O boundaries (databases, HTTP APIs, filesystems, system clocks).
5. **Vague Test Names:**
   Names like `test_discount_1()` or `test_error()` force developers to read the entire test body to understand what broke. Name tests descriptively after the scenario and expected behavior: `test_apply_discount_raises_value_error_when_percent_exceeds_100`.

## 8. Quick Reference

| Concept | Key Takeaway |
| :--- | :--- |
| **System Under Test (SUT)** | The specific function, method, or class being verified by a unit test |
| **AAA Pattern** | **Arrange** inputs/state -> **Act** by calling SUT -> **Assert** expected outcome |
| **FIRST Principles** | **F**ast, **I**ndependent, **R**epeatable, **S**elf-Validating, **T**imely |
| **Boundary Testing** | Explicitly testing `0`, empty inputs, `None`, and exact min/max threshold values |
| **Test Doubles** | Dummy, Stub, Spy, Mock, and Fake—used to isolate SUT from external dependencies |
| **Dependency Injection** | Passing external collaborators as parameters so tests can inject stubs/fakes cleanly |
| **TDD Cycle** | **Red** (write failing test) -> **Green** (make it pass) -> **Refactor** (improve code) |
| **Branch Coverage** | Measures whether both `True` and `False` outcomes of every conditional branch were tested |
