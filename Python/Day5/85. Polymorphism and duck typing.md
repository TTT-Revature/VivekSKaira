# Polymorphism and Duck Typing in Python

## 1. Overview
**Polymorphism** (from the Greek for *"many forms"*) is an Object-Oriented Programming principle where a single interface—such as a function, method name, or operator—can operate seamlessly on objects of different types, with each type executing its own appropriate behavior.

In Python, polymorphism is achieved naturally through four complementary mechanisms:
1. **Duck Typing (Dynamic Polymorphism):** Any object that implements the required methods or attributes works, regardless of its class hierarchy.
2. **Inheritance-Based Polymorphism (Subtype Polymorphism):** Subclasses override a shared base-class method so callers can invoke the same method uniformly across instances.
3. **Operator & Built-In Polymorphism:** Built-in operators (`+`, `*`, `==`) and functions (`len()`, `iter()`, `str()`) delegate to special dunder methods (`__add__`, `__len__`, `__iter__`).
4. **Static Duck Typing (`typing.Protocol`):** Structural subtyping that lets static type checkers verify duck-typed interfaces without requiring inheritance.

---

## 2. Duck Typing
Python's primary approach to polymorphism is **duck typing**, inspired by the testing maxim:

> *"If it walks like a duck and it quacks like a duck, then it must be a duck."*

Under duck typing, Python does **not** check an object's explicit class or inheritance tree before calling a method. Instead, it checks at runtime whether the object provides the expected behavior (methods and attributes).

### Example: Polymorphic Exporters Without a Shared Parent Class
`JsonExporter`, `CsvExporter`, and `CloudBucketUploader` share **no common base class**, yet `run_export()` works with all three because each defines an `.export(records)` method:

```python
import json

class JsonExporter:
    def export(self, records: list[dict[str, object]]) -> str:
        return json.dumps(records)

class CsvExporter:
    def export(self, records: list[dict[str, object]]) -> str:
        if not records:
            return ""
        headers = ",".join(records[0].keys())
        rows = [",".join(str(v) for v in row.values()) for row in records]
        return "\n".join([headers, *rows])

class ConsoleLogger:
    def export(self, records: list[dict[str, object]]) -> str:
        return f"Logged {len(records)} record(s) to stdout."

def run_export(exporter: object, data: list[dict[str, object]]) -> None:
    # Relies purely on the presence of .export(), not inheritance
    output = exporter.export(data)
    print(output)

sample_data = [{"id": 1, "name": "Vivek"}, {"id": 2, "name": "Rashi"}]

for target in (JsonExporter(), CsvExporter(), ConsoleLogger()):
    run_export(target, sample_data)
    print("---")
```

## 3. EAFP vs. LBYL in Duck-Typed Code
Duck typing pairs naturally with Python's **EAFP** coding idiom rather than pre-checking types:

* **EAFP (*Easier to Ask for Forgiveness than Permission*):** Assume the object supports the required operation, call it directly, and handle `AttributeError` or `TypeError` in a `try...except` block if it does not.
* **LBYL (*Look Before You Leap*):** Explicitly check types or attributes (`isinstance()`, `hasattr()`) before calling the method.

```python
class FileStorage:
    def save(self, payload: str) -> str:
        return f"Saved '{payload}' to local disk."

class LegacyCache:
    def put(self, payload: str) -> str:
        return f"Cached '{payload}' in memory."

# EAFP (Preferred Pythonic duck typing)
def persist_eafp(backend: object, data: str) -> str:
    try:
        return backend.save(data)  # type: ignore[attr-defined]
    except AttributeError:
        return f"Fallback: {type(backend).__name__} does not support .save()"

# LBYL (More verbose; risks rigid coupling if using isinstance)
def persist_lbyl(backend: object, data: str) -> str:
    if hasattr(backend, "save") and callable(backend.save):
        return backend.save(data)  # type: ignore[attr-defined]
    return f"Fallback: {type(backend).__name__} does not support .save()"

print(persist_eafp(FileStorage(), "config.yaml"))  # Saved 'config.yaml' to local disk.
print(persist_eafp(LegacyCache(), "config.yaml"))  # Fallback: LegacyCache does not support .save()
```

## 4. Inheritance-Based Polymorphism (Subtype Polymorphism)
When classes model a genuine **"is-a"** hierarchy, a base class defines a common interface and subclasses override those methods with specialized logic. Calling code interacts only with the base-class interface, making it easy to add new subclasses without modifying existing consumers.

```python
class NotificationChannel:
    """Base interface for sending alerts."""

    def send(self, recipient: str, message: str) -> str:
        raise NotImplementedError("Subclasses must implement send().")

class EmailChannel(NotificationChannel):
    def send(self, recipient: str, message: str) -> str:
        return f"[EMAIL to {recipient}] {message}"

class SmsChannel(NotificationChannel):
    def send(self, recipient: str, message: str) -> str:
        return f"[SMS to {recipient}] {message}"

class SlackChannel(NotificationChannel):
    def send(self, recipient: str, message: str) -> str:
        return f"[SLACK @{recipient}] {message}"

def broadcast_alert(channels: list[NotificationChannel], user: str, text: str) -> None:
    # Single loop dispatches dynamically to each subclass's overridden send() method
    for channel in channels:
        print(channel.send(user, text))

active_channels: list[NotificationChannel] = [
    EmailChannel(),
    SmsChannel(),
    SlackChannel(),
]
broadcast_alert(active_channels, "vivek", "Deployment succeeded.")
```
*(Note: Python's `abc.ABC` and `@abstractmethod` formalize this pattern by preventing instantiation of any subclass that fails to implement required methods.)*

## 5. Operator and Built-In Function Polymorphism
Python's built-in operators and functions are polymorphic because they rely on **dunder (special) methods** rather than hardcoded types:

* **`+` (`__add__`):** Adds numbers (`10 + 5 -> 15`), concatenates strings (`"Py" + "thon" -> "Python"`), and merges lists (`[1] + [2] -> [1, 2]`).
* **`len()` (`__len__`):** Works on strings, lists, tuples, dictionaries, sets, and any custom class implementing `__len__`.
* **`for x in obj` (`__iter__`):** Iterates uniformly over lists, files, generators, dictionaries, and custom iterables.

```python
class BatchQueue:
    """Custom container supporting built-in len() and + operator polymorphism."""

    def __init__(self, tasks: list[str]) -> None:
        self.tasks = list(tasks)

    def __len__(self) -> int:
        return len(self.tasks)

    def __add__(self, other: "BatchQueue") -> "BatchQueue":
        if not isinstance(other, BatchQueue):
            return NotImplemented
        return BatchQueue(self.tasks + other.tasks)

    def __repr__(self) -> str:
        return f"BatchQueue({self.tasks!r})"

q1 = BatchQueue(["ingest", "validate"])
q2 = BatchQueue(["transform", "load"])

combined = q1 + q2
print(combined)       # BatchQueue(['ingest', 'validate', 'transform', 'load'])
print(len(combined))  # 4
```

## 6. Static Duck Typing with `typing.Protocol`
Traditional duck typing relies purely on runtime checks, meaning static type checkers (`mypy`, `pyright`, IDE analyzers) cannot verify method signatures ahead of time unless classes share a base class.

Introduced in Python 3.8 (PEP 544), **`typing.Protocol`** provides **structural subtyping** (static duck typing): any class that implements the methods and attribute types declared on a `Protocol` is automatically recognized as compatible—**without inheriting from the `Protocol`**.

```python
from typing import Protocol

class RunnableTask(Protocol):
    """Structural interface: any class with .run() -> str satisfies this protocol."""

    def run(self) -> str:
        ...

# Neither class inherits from RunnableTask
class DataBackupTask:
    def run(self) -> str:
        return "Database backup completed."

class CacheWarmupTask:
    def run(self) -> str:
        return "Redis cache warmed up."

def execute_pipeline(tasks: list[RunnableTask]) -> None:
    for task in tasks:
        print(task.run())

execute_pipeline([DataBackupTask(), CacheWarmupTask()])
```

## 7. Comparison: Polymorphism Approaches in Python

| Approach | Inheritance Required? | Checked When? | Best Used When |
| :--- | :--- | :--- | :--- |
| **Duck Typing (Runtime)** | No | Runtime (via method call / EAFP) | Writing flexible utilities, adapters, or working with third-party objects |
| **`typing.Protocol` (Structural)** | No | Static analysis (and optionally runtime via `@runtime_checkable`) | Combining duck-typing flexibility with full IDE autocomplete and static type safety |
| **Inheritance Overriding** | Yes (`class Sub(Base):`) | Runtime (via MRO dispatch) | Modeling strict "is-a" hierarchies that share state or default implementations |
| **Dunder Methods (`__len__`, `__add__`)** | No | Runtime (via Python data model) | Integrating custom classes seamlessly with Python operators and built-ins |

## 8. Common Pitfalls and Best Practices

### 1. Avoid Rigid `type()` and Over-Specific `isinstance()` Checks
Checking `if type(obj) is list:` or chaining `isinstance(x, (ClassA, ClassB))` defeats polymorphism by rejecting compatible wrappers, mocks, subclasses, and duck-typed objects:

```python
# PITFALL: Rejects tuples, generators, and custom iterables unnecessarily
def total_items_rigid(collection: object) -> int:
    if type(collection) is not list:
        raise TypeError("Expected a list")
    return len(collection)

# CORRECT: Accept any Iterable (polymorphic across lists, tuples, sets, generators)
from collections.abc import Iterable

def total_items_flexible(items: Iterable[object]) -> int:
    return sum(1 for _ in items)
```

### 2. Keep Method Signatures Consistent Across Polymorphic Classes
All classes participating in a polymorphic interface should accept compatible parameters and return consistent types. If `JsonExporter.export(records)` takes one argument while `CsvExporter.export(records, delimiter)` requires two positional arguments, polymorphic callers will fail with `TypeError`.

### 3. Avoid Over-Broad `try...except AttributeError` Blocks
When using EAFP for duck typing, wrap **only** the attribute lookup or method call in `try...except AttributeError`—not the entire function body. Wrapping large blocks can accidentally swallow `AttributeError` bugs raised *inside* the called method's own implementation.

## 9. Quick Reference

| Concept / Tool | Syntax / Mechanism | Purpose |
| :--- | :--- | :--- |
| Duck typing | Call `obj.method()` directly | Treats objects as compatible based on behavior rather than class type |
| EAFP pattern | `try: obj.fn() except AttributeError:` | Pythonic error-handling style for runtime duck typing |
| Method overriding | Redefine parent method in subclass | Specializes shared base-class behavior per subclass |
| Operator polymorphism | `__add__`, `__len__`, `__iter__`, `__str__` | Enables custom objects to work with `+`, `len()`, loops, and `print()` |
| Structural subtyping | `class MyProto(Protocol): ...` | Enables static type checking of duck-typed interfaces without inheritance |
| Abstract collections | `collections.abc` (`Iterable`, `Sequence`, `Mapping`) | Standard structural interfaces for polymorphic container functions |
