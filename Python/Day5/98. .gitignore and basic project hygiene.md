# `.gitignore` and Basic Project Hygiene in Python

## 1. Overview
**Project hygiene** is the practice of keeping a repository clean, secure, reproducible, and easy for collaborators to navigate. A central pillar of Git hygiene is the **`.gitignore`** file—a plain-text configuration file placed at the root of a Git repository that tells Git which untracked files and directories should never be staged or committed.

* **Core Principle of Repository Cleanliness:**
  * **Commit:** Source code (`src/`), tests (`tests/`), dependency manifests (`pyproject.toml`, `requirements.txt`), safe configuration templates (`.env.example`), and documentation (`README.md`).
  * **Ignore:** Virtual environments (`.venv/`), compiled bytecode (`__pycache__/`), tool caches, build outputs, OS/IDE metadata, and secret credentials (`.env`).

---

## 2. How `.gitignore` Pattern Matching Works
Git evaluates `.gitignore` rules line by line from top to bottom against untracked file paths relative to the repository root:

| Pattern Syntax | Example | Behavior |
| :--- | :--- | :--- |
| `# comment` | `# Bytecode files` | Ignored as a comment; blank lines are also ignored |
| `*.ext` | `*.pyc`, `*.log` | Matches any file ending with `.pyc` or `.log` in any directory |
| `*.py[cod]` | `*.py[cod]` | Character class matching `.pyc`, `.pyo`, or `.pyd` files |
| `dir/` | `.venv/`, `__pycache__/` | Trailing slash matches **directories only** (and everything inside them) |
| `/pattern` | `/build/` | Leading slash anchors the pattern strictly to the **repository root** |
| `**` | `**/logs/*.txt` | Matches zero or more nested directory levels |
| `!pattern` | `!.env.example` | **Negation:** re-includes a file that was matched by an earlier ignore rule |

*(Note: Once a parent directory such as `.venv/` is ignored, Git does not traverse inside it—so a negation rule like `!.venv/important.txt` cannot re-include files inside an already ignored directory.)*

## 4. Ignoring Files Already Tracked by Git
A frequent point of confusion is that **`.gitignore` only applies to untracked files**. If you accidentally committed `.env`, `.DS_Store`, or `__pycache__/` before adding them to `.gitignore`, Git will continue tracking changes to them.

### Removing Tracked Files from Git Index Without Deleting Them Locally
Use **`git rm --cached`** to remove files from Git's staging index while keeping your local working copy intact:

```bash
# 1. Stop tracking a single file (e.g., .env) while keeping it on disk
git rm --cached .env

# 2. Stop tracking an entire directory recursively (e.g., __pycache__ or .venv)
git rm -r --cached __pycache__

# 3. Refresh all ignore rules across the entire repository index
git rm -r --cached .
git add .

# 4. Commit the cleanup
git commit -m "chore: untrack ignored artifacts and update .gitignore"
```

## 5. Essential Project Hygiene Practices

### 1. Secret Management (`.env` vs. `.env.example`)
Never hardcode API keys, database passwords, or tokens in Python source files, and never commit `.env` files.
* Store actual secrets in a local **`.env`** file (listed in `.gitignore`).
* Commit a **`.env.example`** file containing variable keys with safe placeholder values so teammates can configure their environment quickly:

```ini
# .env.example (Safe to commit)
APP_ENV=development
DATABASE_URL=postgresql://username:password@localhost:5432/app_db
API_SECRET_KEY=replace_with_local_secret_key
```

### 2. Clear and Actionable `README.md`
Every repository should include a root **`README.md`** covering:
* **Project Purpose:** A concise 1–2 sentence overview of what the project does.
* **Prerequisites:** Required Python version (e.g., Python 3.11+).
* **Setup Instructions:** Exact commands to create `.venv`, activate it, and install dependencies.
* **Usage & Testing:** How to run the application (`python -m package_name`) and execute tests (`pytest`).

### 3. Automated Formatting, Linting, and Pre-Commit Checks
Enforcing consistent style prevents noisy diffs and catches bugs before code reaches GitHub:
* **Linters & Formatters:** Configure tools like **`ruff`** (fast linter + formatter) or **`black`** + **`mypy`** in `pyproject.toml`.
* **Pre-Commit Hooks (`pre-commit`):** Automatically check trailing whitespace, YAML/TOML syntax, secret leaks, and formatting every time you run `git commit`.

### 4. Clean Git Commit Discipline
* **Atomic Commits:** Each commit should represent one logical change (e.g., adding a module, fixing a bug, or updating docs) rather than bundling unrelated edits together.
* **Descriptive Commit Messages:** Use clear, imperative summaries (for example, `feat: add CSV validation helper` or `docs: add notes on .gitignore and project hygiene`).
* **Inspect Before Staging:** Run **`git status`** and **`git diff`** before `git add` to verify no temporary scratch scripts, large data dumps, or credentials are staged.

## 6. Global `.gitignore` for Personal Machine Clutter
OS-specific files (`.DS_Store` on macOS, `Thumbs.db` on Windows) and personal editor settings belong in a **global `.gitignore`** on your machine rather than cluttering every team repository:

```bash
# Create a global ignore file in your home directory
cat << 'EOF' >> ~/.gitignore_global
.DS_Store
Thumbs.db
.vscode/
.idea/
EOF

# Register it globally with Git
git config --global core.excludesfile ~/.gitignore_global
```

## 7. Common Pitfalls and Best Practices

1. **Assuming `.gitignore` Erases Committed Secrets from Git History:**
   Adding `.env` to `.gitignore` and running `git rm --cached .env` removes the file from *future* commits, but the secret remains visible in earlier commit history. If a real credential was ever pushed to GitHub, **revoke and rotate the key immediately** and purge it from history using `git filter-repo`.
2. **Using Overly Broad Wildcards:**
   Adding `*.json` or `data/` to `.gitignore` can silently block legitimate configuration schemas or small unit-test fixtures (`tests/fixtures/sample.json`). Ignore specific output folders (`build/`, `data/raw/*.csv`) instead.
3. **Committing Generated Coverage Reports or Logs:**
   Files like `.coverage`, `htmlcov/`, and `app.log` change on every local test run, creating constant merge conflicts. Always include them in `.gitignore`.
4. **Leaving Scratch Files and Commented-Out Dead Code in Commits:**
   Delete temporary files (`test_scratch.py`, `output.txt`) and rely on Git history rather than leaving large blocks of commented-out code in production modules.

## 8. Quick Reference

| Task / Pattern | Command / Rule | Purpose |
| :--- | :--- | :--- |
| Ignore virtual environments | `.venv/` | Prevents committing thousands of local interpreter/package files |
| Ignore Python bytecode | `__pycache__/`, `*.py[cod]` | Excludes compiled `.pyc`/`.pyo` cache files |
| Ignore secrets safely | `.env` + `!.env.example` | Blocks real credentials while keeping the template tracked |
| Untrack an already-committed file | `git rm --cached <file>` | Removes `<file>` from Git index without deleting it locally |
| Check why a file is ignored | `git check-ignore -v <file>` | Displays the exact `.gitignore` file and line number matching `<file>` |
| Inspect untracked/ignored files | `git status --ignored` | Lists both untracked files and files currently excluded by `.gitignore` |
| Configure global machine ignores | `git config --global core.excludesfile ~/.gitignore_global` | Ignores OS/IDE files across all repositories on your computer |
