# Python Project Structure

## 1. Overview
A well-organized **project structure** separates application source code, tests, configuration, documentation, and dependency manifests into predictable directories. Consistent layout conventions make a repository easier to navigate, test, package, and scale across teams.

* **Core Goals of Good Project Structure:**
  * **Separation of Concerns:** Isolates business logic, data models, configuration, and external interfaces (CLI, API, database).
  * **Testability:** Keeps test suites separate from production code while guaranteeing tests run against the actual installed package.
  * **Reproducibility & Packaging:** Centralizes build rules, dependency specifications, and tool configurations at the repository root.

---

## 2. Standard Repository Layouts
The Python Packaging Authority (PyPA) recognizes two primary repository layouts: the **`src` layout** and the **flat layout**.

### 1. The `src` Layout (Recommended for Libraries and Production Services)
Placing the importable package inside a dedicated **`src/`** directory prevents Python from accidentally importing unbuilt source files from the current working directory during testing.

```text
order_processor/                  # Repository root
├── .github/                      # CI/CD workflows (GitHub Actions)
│   └── workflows/
│       └── ci.yml
├── docs/                         # Architecture and API documentation
├── scripts/                      # One-off admin, migration, or automation scripts
├── src/
│   └── order_processor/          # Top-level importable Python package
│       ├── __init__.py
│       ├── __main__.py           # Entry point for `python -m order_processor`
│       ├── config.py             # Environment and application settings
│       ├── exceptions.py         # Domain-specific custom exceptions
│       ├── models/               # Data structures, dataclasses, schemas
│       │   ├── __init__.py
│       │   └── order.py
│       ├── services/             # Core business logic
│       │   ├── __init__.py
│       │   └── billing.py
│       ├── repositories/         # Database and external storage access
│       │   ├── __init__.py
│       │   └── order_repo.py
│       └── utils/                # Pure, stateless helper functions
│           ├── __init__.py
│           └── validators.py
├── tests/                        # Automated test suite (kept outside src/)
│   ├── conftest.py               # Shared pytest fixtures
│   ├── unit/
│   │   └── test_billing.py
│   └── integration/
│       └── test_order_repo.py
├── .env.example                  # Template of required environment variables
├── .gitignore                    # Files and directories excluded from Git
├── pyproject.toml                # Build system, metadata, dependencies, tool config
├── requirements.txt              # Pinned runtime dependencies (for deployment)
└── README.md                     # Setup instructions and project overview
```

### 2. The Flat Layout (Suitable for Small Scripts and Prototypes)
Places the package directory directly at the repository root alongside `tests/` and `pyproject.toml`:

```text
simple_cli/
├── simple_cli/
│   ├── __init__.py
│   └── cli.py
├── tests/
│   └── test_cli.py
├── .gitignore
├── pyproject.toml
└── README.md
```

### Comparison: `src` Layout vs. Flat Layout

| Dimension | `src` Layout | Flat Layout |
| :--- | :--- | :--- |
| **Package Location** | `repo_root/src/<package_name>/` | `repo_root/<package_name>/` |
| **Import Isolation** | Requires editable install (`pip install -e .`); prevents accidental local imports | Root directory is automatically on `sys.path` when running from root |
| **Packaging Safety** | Prevents test folders or root scripts from accidentally bundling into wheels | Higher risk of accidentally packaging non-source root directories |
| **Best Suited For** | Distributable libraries, multi-module applications, CI/CD pipelines | Small single-purpose tools, quick prototypes, standalone scripts |

## 3. Essential Root-Level Configuration Files

### 1. `pyproject.toml` (Unified Project Configuration — PEP 518 / PEP 621)
Modern Python projects consolidate package metadata, build instructions, dependencies, and tool settings (`pytest`, `ruff`, `mypy`) inside **`pyproject.toml`** rather than scattering multiple dotfiles (`setup.py`, `setup.cfg`, `pytest.ini`, `.flake8`) across the root:

```toml
[build-system]
requires = ["setuptools>=69.0"]
build-backend = "setuptools.build_meta"

[project]
name = "order-processor"
version = "0.1.0"
description = "Order validation and billing pipeline"
readme = "README.md"
requires-python = ">=3.11"
dependencies = [
    "pydantic>=2.9.0",
    "python-dotenv>=1.0.1",
]

[project.optional-dependencies]
dev = [
    "pytest>=8.3.0",
    "ruff>=0.8.0",
    "mypy>=1.13.0",
]

[project.scripts]
order-cli = "order_processor.__main__:main"

[tool.pytest.ini_options]
testpaths = ["tests"]
pythonpath = ["src"]

[tool.ruff]
line-length = 100
target-version = "py311"
```

### 2. `.gitignore` and `.env.example`
* **`.gitignore`:** Prevents local virtual environments, bytecode caches, IDE folders, build artifacts, and secret files from entering version control:
  ```gitignore
  # Environments and secrets
  .venv/
  venv/
  .env

  # Python bytecode and caches
  __pycache__/
  *.py[cod]
  .pytest_cache/
  .mypy_cache/
  .ruff_cache/

  # Distribution / packaging
  build/
  dist/
  *.egg-info/
  ```
* **`.env.example`:** Documents expected environment variables with safe placeholder values (`DATABASE_URL=postgresql://user:pass@localhost:5432/app`) so teammates know what to put in their local untracked `.env` file.

## 4. Internal Package Architecture (Layered Design)
Inside `src/<package_name>/`, organize submodules by **responsibility** rather than dumping unrelated functions into a single `helpers.py` file:

| Layer / Directory | Responsibility | Allowed Dependencies |
| :--- | :--- | :--- |
| **`models/`** (or `domain/`) | Data classes, entities, validation schemas, value objects | Standard library only (no DB or HTTP logic) |
| **`repositories/`** (or `db/`) | Data persistence, SQL queries, file/API storage adapters | `models/`, `config.py`, `exceptions.py` |
| **`services/`** | Core business rules and workflow orchestration | `models/`, `repositories/`, `utils/`, `config.py` |
| **`api/`** or **`cli/`** (`__main__.py`) | External entry points, HTTP routes, argument parsing | `services/`, `models/`, `config.py` |
| **`config.py`** | Typed settings loaded from environment variables | Standard library / `pydantic-settings` |
| **`exceptions.py`** | Custom exception hierarchy for the domain | Standard library (`Exception`) |

*(Key Architectural Rule: Keep dependency flow **one-directional**—`api/cli -> services -> repositories -> models`. Lower layers like `models/` must never import from `services/` or `api/`, which eliminates circular imports and keeps unit tests fast.)*

## 5. Organizing the `tests/` Directory
Mirroring your source package layout inside `tests/` makes it immediately obvious where tests for any module live:

```text
tests/
├── conftest.py                  # Shared fixtures (sample orders, mock repositories)
├── unit/                        # Fast, isolated tests with no network or database I/O
│   ├── test_models.py
│   └── test_billing_service.py
└── integration/                 # Tests verifying database, filesystem, or API interactions
    └── test_order_repository.py
```

* Name test files **`test_<module_name>.py`** so `pytest` discovers them automatically.
* Keep `tests/` outside `src/<package_name>/` so test code is never shipped inside production wheels or Docker runtime images.

## 6. Common Pitfalls and Best Practices

1. **Dumping Everything into One Giant `utils.py`:**
   A catch-all `utils.py` quickly turns into an unorganized grab-bag with tangled dependencies. Group functions by domain purpose (`date_formatting.py`, `file_io.py`, `validators.py`).
2. **Hardcoding Relative File Paths (`open("../../data/input.csv")`) Inside Modules:**
   Relative string paths break whenever a script is launched from a different working directory. Resolve paths relative to `Path(__file__).resolve()` or pass explicit `Path` objects via `config.py`.
3. **Coupling Business Logic Directly to CLI `print()` or Web Frameworks:**
   If a function inside `services/` calls `sys.exit()` or parses HTTP request objects directly, it cannot be reused by a background worker or tested cleanly. Have `services/` accept plain Python objects/dataclasses and return data or raise domain exceptions.
4. **Committing `.env`, `.venv/`, or `__pycache__/` to Git:**
   Always configure `.gitignore` before making your initial commit (`git init`) so secrets and platform-specific binaries never enter repository history.
5. **Forgetting Editable Installation with the `src` Layout:**
   When using `src/`, install your local package in editable mode (`python -m pip install -e ".[dev]"`) inside your active `.venv` so `pytest` and scripts resolve `import order_processor` cleanly from anywhere.

## 7. Quick Reference

| Element | Standard Path | Purpose |
| :--- | :--- | :--- |
| Source package (`src` layout) | `src/<pkg_name>/` | Isolates importable package code from repository root files |
| Package marker & facade | `src/<pkg_name>/__init__.py` | Marks regular package and exposes top-level public symbols |
| CLI / module entry point | `src/<pkg_name>/__main__.py` | Executed when running `python -m <pkg_name>` |
| Central configuration | `pyproject.toml` | Defines build system, dependencies, scripts, and linter/test settings |
| Test suite | `tests/unit/`, `tests/integration/` | Mirrors `src/` structure; discovered automatically by `pytest` |
| Shared test fixtures | `tests/conftest.py` | Provides reusable `pytest` fixtures across test modules |
| Environment template | `.env.example` | Documents required environment variables safely in Git |
| Editable install command | `python -m pip install -e .` | Links `site-packages` directly to `src/<pkg_name>/` during development |
