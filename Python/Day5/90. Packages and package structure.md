# Packages and Package Structure in Python

## 1. Overview
As Python applications grow beyond a single script, organizing all functions and classes in one file becomes unmaintainable. **Packages** solve this by structuring modules into a hierarchical directory tree accessed via **dot notation** (`package.subpackage.module`).

* **Module:** A single `.py` file containing Python definitions and statements.
* **Package:** A directory that groups related modules and nested **subpackages** under a shared namespace.
* **Core Benefits:**
  * **Logical Modularity:** Separates domain concerns (e.g., `auth`, `database`, `api`, `utils`).
  * **Namespace Isolation:** Prevents naming collisions—`payments.validator` and `users.validator` can coexist cleanly without conflict.
  * **Controlled Public API:** Exposes clean top-level interfaces while hiding internal helper modules.

---

## 2. Regular Packages vs. Namespace Packages
Python supports two types of packages depending on whether an `__init__.py` file is present.

### 1. Regular Packages (Standard)
* Any directory containing an **`__init__.py`** file (even if the file is completely empty).
* When imported, Python executes `__init__.py` and binds the resulting module object to the package name.
* Stores a single directory path list in `package.__path__`.

### 2. Namespace Packages (PEP 420, Python 3.3+)
* A directory of `.py` modules **without an `__init__.py` file**.
* Allows a single logical package to be split across **multiple directories or distributions** on `sys.path` (commonly used for plugin architectures, e.g., `company.auth` and `company.billing` installed as separate packages).
* Contains no initialization code because there is no `__init__.py` to execute.

```text
# Regular Package                  # Namespace Package (PEP 420)
analytics/                         plugins/
├── __init__.py                    ├── csv_loader.py
├── loader.py                      └── json_loader.py
└── metrics.py
```

| Feature | Regular Package | Namespace Package (PEP 420) |
| :--- | :--- | :--- |
| **Requires `__init__.py`?** | Yes | No |
| **Initialization Code** | Supported via `__init__.py` | Not supported |
| **Multi-Directory Split** | Single directory only | Can span multiple directories on `sys.path` |
| **Typical Use Case** | Application codebases and standard libraries | Extensible plugin ecosystems and multi-repo distributions |

---

## 3. The Role of `__init__.py`
Inside a regular package, **`__init__.py`** serves three practical purposes:

1. **Package Marker:** Identifies the directory as a regular Python package (required by tools like `pytest` and static analyzers for reliable package discovery).
2. **Package-Level Initialization:** Executes **once** the first time the package or any of its submodules is imported (cached thereafter in `sys.modules`).
3. **Facade / Public API Re-Exporting:** Imports selected classes or functions from deeper submodules so callers can import directly from the top-level package rather than knowing internal file paths.

### Controlling Wildcard Imports (`__all__`)
Defining **`__all__`** (a list of public string names) in `__init__.py` or a module explicitly declares the public interface and restricts what **`from package import *`** exports:

```python
# File: data_pipeline/__init__.py
"""Data pipeline package exposing core ingestion and transformation APIs."""

from .ingestion import load_csv
from .transform import clean_records

__version__ = "1.0.0"
__all__ = ["load_csv", "clean_records", "__version__"]
```

```python
# Caller code can import directly from the top-level package:
from data_pipeline import load_csv, clean_records, __version__
```

## 4. Absolute vs. Relative Imports
When modules inside a package import each other, Python offers two import styles:

```text
ecommerce/
├── __init__.py
├── config.py
├── orders/
│   ├── __init__.py
│   ├── service.py
│   └── validator.py
└── utils/
    ├── __init__.py
    └── currency.py
```

### 1. Absolute Imports (Recommended by PEP 8)
Specify the full path starting from the **top-level package root** on `sys.path`. Absolute imports remain readable and unambiguous even when files are moved.

```python
# Inside ecommerce/orders/service.py
from ecommerce.config import TAX_RATE
from ecommerce.orders.validator import validate_order
from ecommerce.utils.currency import format_inr
```

### 2. Relative Imports
Specify the target module relative to the **current module's `__package__` attribute** using leading dots:
* **Single dot (`.`):** Refers to the current package directory.
* **Double dot (`..`):** Refers to the parent package directory (each additional dot moves one level higher).

```python
# Inside ecommerce/orders/service.py
from . import validator                  # Sibling module in ecommerce.orders
from .validator import validate_order    # Symbol from sibling module
from ..config import TAX_RATE            # Module in parent package (ecommerce)
from ..utils.currency import format_inr  # Sibling subpackage (ecommerce.utils)
```

| Aspect | Absolute Import | Relative Import |
| :--- | :--- | :--- |
| **Syntax** | `from pkg.subpkg import mod` | `from . import mod` / `from ..subpkg import mod` |
| **Readability** | Explicit full path; easy to locate anywhere | Concise for tightly coupled sibling modules |
| **Renaming Top Package** | Requires updating import paths | Works without modification inside the package |
| **PEP 8 Guidance** | **Preferred default** across projects | Acceptable within complex internal subpackages |

## 5. Standard Project and Package Layouts
When structuring a real-world Python repository for distribution, testing, and CI/CD, two standard directory layouts are used:

### 1. The `src` Layout (Recommended for Libraries & Production Services)
Placing the package inside a dedicated **`src/`** directory isolates importable package code from repository-root scripts, documentation, and configuration files. It guarantees that test runners (`pytest`) test the **installed package** rather than accidentally importing unbuilt files from the working directory.

```text
inventory_service/              # Repository root
├── pyproject.toml              # Build configuration, dependencies, and tool settings
├── README.md                   # Project documentation
├── .gitignore
├── src/
│   └── inventory_service/      # Top-level importable package
│       ├── __init__.py
│       ├── __main__.py         # CLI entry point for `python -m inventory_service`
│       ├── config.py
│       ├── models/
│       │   ├── __init__.py
│       │   └── item.py
│       ├── services/
│       │   ├── __init__.py
│       │   └── stock_manager.py
│       └── utils/
│           ├── __init__.py
│           └── validators.py
└── tests/                      # Test suite kept outside the distributable package
    ├── __init__.py
    ├── test_models.py
    └── test_services.py
```

### 2. The Flat Layout
Places the package directory directly at the repository root alongside `tests/` and `pyproject.toml`. Common in small internal tools and single-service applications where editable installation (`pip install -e .`) is not used.

## 6. Executable Packages (`__main__.py`)
Adding a **`__main__.py`** file inside a package makes the entire package directly executable from the command line using **`python -m <package_name>`**:

```python
# File: src/inventory_service/__main__.py
import sys
from inventory_service.services.stock_manager import run_audit

def main() -> int:
    print("Starting inventory audit...")
    run_audit()
    return 0

if __name__ == "__main__":
    sys.exit(main())
```

```bash
# Runs inventory_service/__main__.py with __name__ == "__main__"
python -m inventory_service
```

## 7. Common Pitfalls and Best Practices

### 1. Running a Submodule File Directly Without `-m`
Executing `python ecommerce/orders/service.py` sets `__name__ = "__main__"` and `__package__ = None`, causing any relative import (`from .validator import ...`) to crash with:
`ImportError: attempted relative import with no known parent package`.
* **Fix:** Always run modules inside a package from the project root using the **`-m` flag**:
  ```bash
  python -m ecommerce.orders.service
  ```

### 2. Circular Imports Across Package Modules
When `module_a.py` imports `module_b.py` at top level while `module_b.py` simultaneously imports `module_a.py` at top level, Python raises `ImportError: cannot import name '...' from partially initialized module`.
* **Fixes:**
  1. Extract shared models, constants, or interfaces into a third lower-level module (e.g., `models.py` or `types.py`) that both modules import.
  2. Move type-annotation-only imports inside an `if TYPE_CHECKING:` block (`from typing import TYPE_CHECKING`).
  3. Defer the import inside the specific function where it is needed as a last resort.

### 3. Shadowing Standard Library Module Names
Naming a file or subpackage `logging.py`, `json.py`, `email.py`, `random.py`, or `typing.py` inside a directory on `sys.path` overrides Python's built-in standard library module of the same name, causing confusing `AttributeError` failures.

### 4. Keeping `__init__.py` Fast and Side-Effect-Free
Avoid opening database connections, reading large files, or making network calls at the top level of `__init__.py`. Every `import package.submodule` executes `__init__.py` first, which slows down startup and complicates unit testing.

## 8. Quick Reference

| File / Construct | Location / Syntax | Purpose |
| :--- | :--- | :--- |
| `__init__.py` | Inside package directory | Marks a regular package, runs initialization, and defines public exports |
| `__all__` | `["func_a", "ClassB"]` | Controls symbols exported by `from package import *` |
| `__main__.py` | Inside package directory | Entry point executed when running `python -m package_name` |
| Namespace package | Directory without `__init__.py` | PEP 420 package capable of spanning multiple directories on `sys.path` |
| Absolute import | `from pkg.sub import item` | Imports using full path from package root (PEP 8 recommended) |
| Relative import | `from . import sibling` / `from .. import parent_mod` | Imports relative to current package (`__package__`) |
| `python -m pkg.mod` | Terminal command | Executes a package submodule properly with package context intact |
| `src/` layout | `project_root/src/pkg_name/` | Isolates distributable source code from root configs and `tests/` |
