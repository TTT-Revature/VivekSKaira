# `super()` in Python

## 1. Overview
**`super()`** is a built-in Python function that returns a temporary **proxy object** used to delegate method calls and attribute lookups to a parent or sibling class in a class hierarchy.

* **Core Misconception Clarified:** `super()` does **not** strictly mean "call my direct parent class." Rather, it means **"call the next class in the current object's Method Resolution Order (`__mro__`)."**
* **Why `super()` Exists:**
  * Eliminates hardcoding parent class names inside subclasses, making inheritance hierarchies easier to refactor.
  * Enables **cooperative multiple inheritance**, ensuring that shared ancestor methods (especially `__init__`) execute in a predictable order and are never called twice.
  * Works seamlessly across instance methods, `@classmethod` factories, and descriptors such as `@property`.

---

## 2. Syntax and Forms of `super()`
Python provides two ways to invoke `super()`:

### 1. Zero-Argument Form: `super()` (Standard in Python 3)
When called with no arguments inside a class method, the Python compiler automatically injects two hidden references:
1. The **current class** (`__class__`) in which the method is lexically defined.
2. The **first argument** passed to the method (typically `self` for instance methods or `cls` for class methods).

```python
class BaseLogger:
    def log(self, message: str) -> str:
        return f"[BASE] {message}"

class TimestampLogger(BaseLogger):
    def log(self, message: str) -> str:
        # Zero-argument super() resolves to super(TimestampLogger, self)
        parent_output = super().log(message)
        return f"2026-11-23 | {parent_output}"

logger = TimestampLogger()
print(logger.log("System initialized"))  # 2026-11-23 | [BASE] System initialized
```

### 2. Explicit Two-Argument Form: `super(type, object_or_type)`
You can pass arguments explicitly to control the starting point in the MRO:
* **`super(ClassA, instance)`:** Searches `type(instance).__mro__` starting **immediately after `ClassA`**, binding methods to `instance`.
* **`super(ClassA, SubClass)`:** Searches `SubClass.__mro__` starting **immediately after `ClassA`**, binding `@classmethod` calls to `SubClass` (requires `issubclass(SubClass, ClassA)`).

```python
class GrandParent:
    def greet(self) -> str:
        return "Hello from GrandParent"

class Parent(GrandParent):
    def greet(self) -> str:
        return "Hello from Parent"

class Child(Parent):
    def greet(self) -> str:
        return "Hello from Child"

c = Child()
print(super(Child, c).greet())   # Hello from Parent (starts after Child)
print(super(Parent, c).greet())  # Hello from GrandParent (skips Parent, starts after Parent)
```

## 3. Common Usage Patterns

### 1. Extending `__init__` and Instance Methods
The most frequent use of `super()` is initializing inherited attributes in `__init__` before adding subclass-specific attributes:

```python
class Account:
    def __init__(self, account_id: str, balance: float) -> None:
        self.account_id = account_id
        self.balance = balance

    def summary(self) -> str:
        return f"Account {self.account_id}: Balance = {self.balance:.2f}"

class SavingsAccount(Account):
    def __init__(self, account_id: str, balance: float, interest_rate: float) -> None:
        super().__init__(account_id, balance)
        self.interest_rate = interest_rate

    def summary(self) -> str:
        return f"{super().summary()} | Interest Rate = {self.interest_rate:.1%}"

acc = SavingsAccount("SAV-101", 10000.0, 0.045)
print(acc.summary())  # Account SAV-101: Balance = 10000.00 | Interest Rate = 4.5%
```

### 2. Using `super()` Inside `@classmethod`
Inside a `@classmethod`, `super()` binds to `cls`, preserving polymorphism across subclasses:

```python
class Document:
    def __init__(self, title: str) -> None:
        self.title = title

    @classmethod
    def create_default(cls) -> "Document":
        return cls("Untitled Document")

class MarkdownNote(Document):
    @classmethod
    def create_default(cls) -> "MarkdownNote":
        note = super().create_default()  # Calls Document.create_default with cls=MarkdownNote
        note.title = f"{note.title}.md"
        return note

doc = MarkdownNote.create_default()
print(type(doc) is MarkdownNote, doc.title)  # True Untitled Document.md
```

### 3. Extending a Parent `@property`
When overriding a `@property` setter in a subclass, use the two-argument class form `super(SubClass, SubClass).prop.__set__(self, value)` to delegate validation back to the parent property descriptor:

```python
class BaseConfig:
    def __init__(self, timeout: int) -> None:
        self._timeout = timeout

    @property
    def timeout(self) -> int:
        return self._timeout

    @timeout.setter
    def timeout(self, value: int) -> None:
        if value <= 0:
            raise ValueError("Timeout must be greater than zero.")
        self._timeout = value

class StrictConfig(BaseConfig):
    @BaseConfig.timeout.setter
    def timeout(self, value: int) -> None:
        if value > 60:
            raise ValueError("StrictConfig timeout cannot exceed 60 seconds.")
        super(StrictConfig, StrictConfig).timeout.__set__(self, value)

cfg = StrictConfig(30)
cfg.timeout = 45
print(cfg.timeout)  # 45
```

## 4. Cooperative Multiple Inheritance and MRO
In a **diamond inheritance** hierarchy, a subclass inherits from two classes that share a common base class. Because `super()` follows the instance's C3-linearized **`__mro__`**, each class in the hierarchy is visited **once and only once**.

### Cooperative `__init__` with `**kwargs`
When multiple classes in a diamond hierarchy accept different keyword arguments in `__init__`, each class extracts its own parameters and forwards the remaining `**kwargs` to `super().__init__(**kwargs)` until reaching `object.__init__()`:

```python
class Person:
    def __init__(self, name: str, **kwargs: object) -> None:
        super().__init__(**kwargs)
        self.name = name

class Employee(Person):
    def __init__(self, emp_id: int, **kwargs: object) -> None:
        super().__init__(**kwargs)
        self.emp_id = emp_id

class Mentor(Person):
    def __init__(self, specialty: str, **kwargs: object) -> None:
        super().__init__(**kwargs)
        self.specialty = specialty

class TechnicalMentor(Employee, Mentor):
    def __init__(self, name: str, emp_id: int, specialty: str) -> None:
        super().__init__(name=name, emp_id=emp_id, specialty=specialty)

# MRO: TechnicalMentor -> Employee -> Mentor -> Person -> object
tm = TechnicalMentor(name="Vivek", emp_id=101, specialty="Python")
print([cls.__name__ for cls in TechnicalMentor.__mro__])
print(tm.name, tm.emp_id, tm.specialty)  # Vivek 101 Python
```

### Execution Flow Across the MRO
```text
TechnicalMentor.__init__(name="Vivek", emp_id=101, specialty="Python")
  -> Employee.__init__(emp_id=101, name="Vivek", specialty="Python")
       -> Mentor.__init__(specialty="Python", name="Vivek")
            -> Person.__init__(name="Vivek")
                 -> object.__init__()
```
*(If `Employee` and `Mentor` had called `Person.__init__(self, ...)` directly instead of `super()`, `Person.__init__` would have executed twice.)*

## 5. `super()` vs. Hardcoded Parent Class Calls

| Criterion | `super().method(...)` | `ParentClass.method(self, ...)` |
| :--- | :--- | :--- |
| **Lookup Mechanism** | Dynamic via `type(self).__mro__` | Static direct call to `ParentClass` |
| **Diamond Inheritance** | Safe: calls shared ancestors **once** | Unsafe: can execute shared ancestors **multiple times** |
| **Sibling Delegation** | Delegates to next sibling in MRO | Skips siblings in multiple inheritance |
| **Refactoring Resilience** | Renaming or inserting base classes requires no edits inside methods | Every hardcoded `ParentClass` reference must be updated manually |
| **Works in `@classmethod`?** | Yes (`super()` binds to `cls`) | Awkward and brittle when subclassed |

## 6. Common Pitfalls and Best Practices

### 1. Calling Zero-Argument `super()` Outside a Method
Zero-argument `super()` relies on the enclosing method's lexical `__class__` cell and first argument. Calling `super()` at module level or inside a nested helper function that lacks a `self`/`cls` parameter raises `RuntimeError`:

```python
# PITFALL: RuntimeError: super(): no arguments
# print(super())

# CORRECT: Supply explicit arguments if calling outside a method
c = Child()
print(super(Child, c).greet())
```

### 2. Attempting to Assign Attributes Through `super()`
The `super` proxy object supports **attribute and method lookup** (`super().method()`), not direct attribute assignment (`super().attr = value`). Instance attributes live on `self`, so always assign attributes via `self.attr = value`.

### 3. Breaking the Cooperative Chain in Multiple Inheritance
In multiple inheritance, if *any* intermediate class overrides a method and forgets to call `super()`, the remaining classes after it in the MRO will never be reached. Every class participating in cooperative multiple inheritance must call `super()`.

### 4. Passing Unexpected Arguments to `object.__init__()`
`object.__init__()` accepts no extra arguments. In cooperative `__init__` chains, always peel off your class's keyword parameters before calling `super().__init__(**kwargs)` so `kwargs` is empty by the time `Person` (or the root domain class) delegates to `object.__init__()`.

## 7. Quick Reference

| Syntax | Context | Behavior |
| :--- | :--- | :--- |
| `super().method(*args)` | Inside instance or class method | Delegates to the next class in `type(self).__mro__` (or `cls.__mro__`) |
| `super().__init__(*args)` | Inside subclass `__init__` | Initializes parent/sibling state along the MRO |
| `super(Cls, obj).method()` | Any scope (with instance `obj`) | Searches `type(obj).__mro__` starting after `Cls`, bound to `obj` |
| `super(Cls, SubCls).cm()` | Any scope (with subclass `SubCls`) | Searches `SubCls.__mro__` starting after `Cls`, bound to `SubCls` |
| `ClassName.__mro__` | Class inspection | Returns the tuple of classes searched in order by `super()` |
