# Virtual Environments and `venv` in Python

## 1. Overview
A **virtual environment** is an isolated, self-contained directory tree that houses a specific Python interpreter binary (or symlink) alongside its own independent **`site-packages`** directory for third-party libraries.

* **Why Virtual Environments Are Essential:**
  * **Prevents Dependency Conflicts:** Allows Project A to use `fastapi==0.100.0` while Project B uses `fastapi==0.115.0` on the same machine without colliding.
  * **Protects the System Python:** Keeps OS-managed or global Python installations clean and prevents broken upgrades.
  * **Enables Reproducibility:** Lets you export an exact list of project dependencies (`requirements.txt` or `pyproject.toml`) so teammates, trainers, and CI/CD pipelines recreate the identical environment.
* **What Is `venv`?**
  Introduced in Python 3.3 (PEP 405), **`venv`** is Python's built-in standard library module for creating lightweight virtual environments—requiring zero third-party installations.

## 2. Creating, Activating, and Deactivating a `venv`

### 1. Creating a Virtual Environment
Run the `venv` module as a script using `-m` from your project root directory. Naming the folder **`.venv`** (with a leading dot) is the widely adopted convention recognized automatically by VS Code, PyCharm, and modern tooling:

```bash
# macOS / Linux
python3 -m venv .venv

# Windows
python -m venv .venv
```

### 2. Activating the Virtual Environment
Activating a virtual environment updates your current shell's `PATH` variable so that `python` and `pip` resolve to the binaries inside `.venv` first, and prefixes your terminal prompt with `(.venv)`.

| Operating System / Shell | Activation Command |
| :--- | :--- |
| **macOS / Linux (`bash` / `zsh`)** | `source .venv/bin/activate` |
| **Windows (PowerShell)** | `.venv\Scripts\Activate.ps1` |
| **Windows (Command Prompt / `cmd`)** | `.venv\Scripts\activate.bat` |
| **Windows (Git Bash)** | `source .venv/Scripts/activate` |

*(Note on Windows PowerShell: If script execution is restricted, allow local scripts for the current user once with `Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser`.)*

### 3. Verifying the Active Environment
Confirm that your shell points to the virtual environment's interpreter rather than the global installation:

```bash
# Check interpreter path (macOS/Linux: which python | Windows: where python)
which python
# Output: /projects/my_app/.venv/bin/python

# Verify programmatically inside Python
python -c "import sys; print(sys.prefix); print(sys.base_prefix)"
```
When a virtual environment is active, **`sys.prefix`** points to `.venv`, while **`sys.base_prefix`** points to the underlying base Python installation (`sys.prefix != sys.base_prefix`).

### 4. Deactivating and Removing a Virtual Environment
* **Deactivate (exit back to global shell):**
  ```bash
  deactivate
  ```
* **Delete an environment completely:** Since a virtual environment contains no source code, simply delete the `.venv` folder (`rm -rf .venv` on macOS/Linux or `rmdir /s /q .venv` on Windows) and recreate it whenever needed.

## 3. Internal Anatomy of a `venv`
Inspecting a newly created `.venv` folder reveals how Python isolates packages without duplicating the entire standard library:

```text
.venv/
├── pyvenv.cfg                  # Configuration linking to the base Python installation
├── bin/                        # (Scripts/ on Windows) python, pip, activate scripts
│   ├── activate
│   ├── pip
│   └── python -> /usr/local/bin/python3
├── include/                    # C header files for compiling C-extension packages
└── lib/                        # (Lib/ on Windows)
    └── python3.12/
        └── site-packages/      # Isolated directory where third-party packages install
```

### Role of `pyvenv.cfg`
When the Python binary inside `.venv/bin/python` starts up, it looks for **`pyvenv.cfg`** one directory above itself:

```ini
home = /usr/local/bin
include-system-site-packages = false
version = 3.12.4
executable = /usr/local/bin/python3.12
command = /usr/local/bin/python3 -m venv .venv
```
* **`include-system-site-packages = false`:** Ensures global third-party packages are hidden by default for full isolation. (Pass `--system-site-packages` during `python -m venv` creation only if you intentionally want global packages visible.)

## 4. Managing Dependencies Inside a `venv`
Once activated, use **`python -m pip`** to install, inspect, and lock packages inside the isolated `site-packages` directory:

```bash
# 1. Upgrade pip inside the newly created environment
python -m pip install --upgrade pip

# 2. Install project packages
python -m pip install requests python-dotenv pytest

# 3. List installed packages in the active environment
python -m pip list

# 4. Export exact pinned versions to requirements.txt
python -m pip freeze > requirements.txt

# 5. Recreate the exact environment on another machine or CI runner
python -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
```

## 5. `venv` vs. Other Python Environment Tools

| Tool | Built-In? | Scope & Key Capabilities | When to Use |
| :--- | :--- | :--- | :--- |
| **`venv`** | **Yes (Stdlib)** | Lightweight Python-only virtual environments (`python -m venv`) | Default choice for standard Python projects and training repositories |
| **`virtualenv`** | No (PyPI) | Faster environment creation, supports creating envs for multiple Python versions | Legacy codebases or workflows needing `--python` version discovery |
| **`conda`** | No (Anaconda/Miniforge) | Manages Python versions + non-Python C/C++/CUDA system libraries | Data science, scientific computing, and GPU/ML stacks |
| **`uv`** | No (Astral) | Ultra-fast Rust-based `venv` creator, `pip` replacement, and lockfile manager | Modern high-speed dependency resolution and project management |

## 6. Common Pitfalls and Best Practices

### 1. Never Commit `.venv/` to Git
Virtual environments contain thousands of platform-specific files and absolute paths. Always exclude `.venv/` in **`.gitignore`** and commit only **`requirements.txt`** or **`pyproject.toml`**:

```gitignore
# .gitignore
.venv/
venv/
__pycache__/
*.py[cod]
```

### 2. Never Move or Rename an Existing `.venv` Directory
Activation scripts and installed console entry points inside `.venv/bin/` (or `.venv\Scripts\`) embed hardcoded absolute paths created at setup time. Moving or renaming the project folder breaks those paths. Instead, delete `.venv` and recreate it from `requirements.txt`.

### 3. Always Run `python -m pip` Instead of Bare `pip`
If a virtual environment is not activated—or if `PATH` has conflicting entries—running bare `pip install` may install packages into a different Python installation. Running **`python -m pip install ...`** guarantees packages install into the exact Python interpreter you are executing.

### 4. Recreate Environments When Upgrading Major Python Versions
A `.venv` links to a specific minor Python release (such as `python3.11`). After upgrading Python on your machine (e.g., to `python3.12`), remove the old `.venv` and build a fresh one with the new interpreter.

## 7. Quick Reference

| Task | Command / Expression | Notes |
| :--- | :--- | :--- |
| Create virtual environment | `python3 -m venv .venv` | Creates isolated `.venv` directory in current folder |
| Activate (macOS / Linux) | `source .venv/bin/activate` | Prepends `.venv/bin` to shell `PATH` |
| Activate (Windows PowerShell) | `.venv\Scripts\Activate.ps1` | Prepends `.venv\Scripts` to shell `PATH` |
| Deactivate environment | `deactivate` | Restores original shell `PATH` |
| Check if running in a `venv` | `sys.prefix != sys.base_prefix` | Evaluates to `True` inside an active virtual environment |
| Install packages safely | `python -m pip install <pkg>` | Installs into active interpreter's `site-packages` |
| Export pinned dependencies | `python -m pip freeze > requirements.txt` | Saves exact installed package versions |
| Install from requirements file | `python -m pip install -r requirements.txt` | Reconstructs environment dependencies |
