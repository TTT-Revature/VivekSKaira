# `requirements.txt` and Dependency Management in Python

## 1. Overview
Modern Python applications rarely rely solely on the standard library; they depend on third-party packages installed from PyPI. Managing those packages systematically ensures that code running on your laptop behaves identically on a teammate's machine, in CI/CD pipelines, and in production servers.

* **Dependency:** Any external library or package required for your project to run, test, or build.
* **`requirements.txt`:** A plain-text configuration file listing a project's dependencies (and usually their exact versions) so `pip` can reproduce the environment with a single command.
* **Core Goals of Dependency Management:**
  * **Reproducibility:** Guaranteeing deterministic builds across environments.
  * **Isolation:** Keeping application runtime packages distinct from development, linting, and testing tools.
  * **Conflict Resolution:** Ensuring all packages agree on compatible versions of shared sub-dependencies.

---

## 2. Direct vs. Transitive Dependencies
When you install a single package, `pip` automatically resolves and installs every package that library needs to function. Understanding the two tiers of dependencies is essential for keeping `requirements.txt` clean:

| Dependency Type | Definition | Example |
| :--- | :--- | :--- |
| **Direct (Top-Level)** | Packages explicitly imported and used by your own application code | `requests`, `fastapi`, `pandas`, `pytest` |
| **Transitive (Indirect)** | Sub-dependencies pulled in automatically by your direct dependencies | `urllib3`, `certifi`, `idna`, `charset-normalizer` (required by `requests`) |

### Inspecting Your Dependency Tree
```bash
# List only top-level packages that no other installed package depends on
python -m pip list --not-required

# View what a specific package requires and which packages require it
python -m pip show urllib3

# Verify there are no broken or conflicting dependency versions
python -m pip check
```

## 3. Creating and Installing `requirements.txt`

### 1. Exporting Installed Packages (`pip freeze`)
Inside an **active virtual environment**, `pip freeze` outputs every installed package in `package==version` format:

```bash
# 1. Activate your isolated virtual environment first
source .venv/bin/activate        # macOS / Linux
# .venv\Scripts\Activate.ps1     # Windows PowerShell

# 2. Export exact pinned versions to requirements.txt
python -m pip freeze > requirements.txt
```

### 2. Installing Dependencies from `requirements.txt`
To recreate the exact environment on another machine or deployment container:

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```

*(Note: `pip freeze` records both direct and transitive dependencies. While this locks the entire environment, it does not distinguish which packages you intentionally chose versus which ones were pulled in automatically.)*

## 4. `requirements.txt` Syntax and Features
A `requirements.txt` file supports more than simple `package==version` lines. Each non-empty line is passed directly to `pip`'s requirement parser.

```text
# Comments start with '#' and blank lines are ignored

# 1. Exact version pinning (recommended for deployed applications)
fastapi==0.115.6
uvicorn==0.34.0

# 2. Version ranges and compatible release specifiers (PEP 440)
pydantic>=2.9.0,<3.0.0
requests~=2.32.0

# 3. Package extras (installs optional sub-dependencies bundled with a package)
passlib[bcrypt]==1.7.4
sqlalchemy[asyncio]==2.0.36

# 4. Environment markers (PEP 508: conditional install by OS or Python version)
pywin32==308; sys_platform == "win32"
tomli>=2.0.1; python_version < "3.11"

# 5. Include another requirements file or apply a constraints file
-r base.txt
-c constraints.txt

# 6. Install from a Git repository (pinned to a tag or commit hash) or local editable project
git+[https://github.com/psf/requests.git@v2.32.3](https://github.com/psf/requests.git@v2.32.3)
-e .
```

### Cryptographic Hash Verification (`--hash`)
For high-security production deployments, `pip` supports SHA-256 hash checking. When hashes are present, `pip` refuses to install any archive whose digest does not match—protecting against compromised package mirrors or tampered artifacts:

```text
certifi==2024.8.30 \
    --hash=sha256:922820b53db7a72570da3f57acba3002ce62a8222222011b3ffff44fec545bc3
```

## 5. Structuring Multi-Environment Dependencies

### 1. Layered Requirements Files
Production servers should not install test frameworks, linters, or debuggers (`pytest`, `ruff`, `mypy`). Split dependencies into layered files inside a `requirements/` directory:

```text
project_root/
├── requirements/
│   ├── base.txt        # Core runtime dependencies shared everywhere
│   ├── dev.txt         # Local development, testing, and linting tools
│   └── prod.txt        # Production-only server dependencies (e.g., gunicorn)
└── src/
```

```text
# File: requirements/base.txt
fastapi==0.115.6
pydantic==2.10.3
python-dotenv==1.0.1
```

```text
# File: requirements/dev.txt
-r base.txt
pytest==8.3.4
ruff==0.8.2
mypy==1.13.0
```

```text
# File: requirements/prod.txt
-r base.txt
gunicorn==23.0.0
```

```bash
# Developers install runtime + dev tools:
python -m pip install -r requirements/dev.txt

# Production builds install only runtime + production server:
python -m pip install -r requirements/prod.txt
```

### 2. Separating Abstract vs. Locked Dependencies (`pip-tools` Workflow)
A widespread industry pattern separates **what you want** from **what gets resolved**:
1. **`requirements.in` (Human-Maintained):** Lists only your **direct** dependencies with loose bounds (e.g., `fastapi>=0.115`, `requests>=2.32`).
2. **`requirements.txt` (Machine-Generated Lockfile):** Compiled automatically by **`pip-compile`** (`pip-tools`) or **`uv pip compile`**, pinning every direct and transitive package with comments showing *why* each transitive package was included:

```text
# Auto-generated by pip-compile:
certifi==2024.8.30
    # via requests
charset-normalizer==3.4.0
    # via requests
idna==3.10
    # via requests
requests==2.32.3
    # via -r requirements.in
urllib3==2.2.3
    # via requests
```

## 6. `requirements.txt` vs. `pyproject.toml` and Lockfiles
Modern Python projects frequently combine `pyproject.toml` with lockfiles or `requirements.txt` depending on whether the project is an **application** or a **reusable library**:

| Mechanism | Primary Purpose | Version Strategy | Best Suited For |
| :--- | :--- | :--- | :--- |
| **`requirements.txt`** | Simple, universal list consumed directly by `pip install -r` | Exact pins (`==`) for reproducible environments | Web apps, APIs, scripts, Docker images, and training projects |
| **`pyproject.toml` (`[project.dependencies]`)** | PEP 621 standard metadata declaring abstract package dependencies | Compatible ranges (`>=`, `<`, `~=`) | Distributable libraries and installable Python packages |
| **Dedicated Lockfiles (`uv.lock`, `poetry.lock`)** | Cross-platform dependency graph with hashes and exact resolutions | Exact pins + cryptographic hashes across OSes | Large production applications using modern project managers |

## 7. Common Pitfalls and Best Practices

1. **Running `pip freeze` Without an Active Virtual Environment:**
   Running `pip freeze > requirements.txt` globally dumps dozens of unrelated system or user-wide packages into your project file. Always verify `which python` (or `where python`) points inside `.venv` before freezing.
2. **Orphaned Transitive Dependencies After `pip uninstall`:**
   Running `pip uninstall pandas` removes `pandas`, but leaves behind transitive packages like `pytz` or `tzdata`. If you then run `pip freeze > requirements.txt`, those unused packages remain in your file. Maintain a clean list of direct dependencies and rebuild your `.venv` periodically to prune orphans.
3. **Over-Pinning in Reusable Libraries vs. Under-Pinning in Applications:**
   * **Applications (APIs, web apps, data pipelines):** Pin exact versions (`==`) so sudden upstream releases do not break production deployments.
   * **Libraries (packages meant to be installed into other projects):** Use flexible lower bounds (`>=`) so consumers do not hit irreconcilable version conflicts with their other dependencies.
4. **Ignoring Python Version Compatibility:**
   A `requirements.txt` generated on Python 3.12 may fail on Python 3.9 if a pinned package version dropped support for older interpreters. Document the target Python version in `README.md` or `requires-python` in `pyproject.toml`.

## 8. Quick Reference

| Command / Syntax | Purpose |
| :--- | :--- |
| `python -m pip freeze > requirements.txt` | Exports all installed packages and exact versions in the active environment |
| `python -m pip install -r requirements.txt` | Installs all dependencies specified in `requirements.txt` |
| `python -m pip install -r reqs.txt -c constraints.txt` | Installs dependencies while enforcing version limits from `constraints.txt` |
| `python -m pip list --not-required` | Lists top-level packages not depended on by any other installed package |
| `python -m pip check` | Checks installed packages for missing or incompatible dependencies |
| `-r other_requirements.txt` | Directive inside a requirements file to include another requirements file |
| `pkg[extra]==1.2.0` | Installs a package along with its named optional dependency group |
| `pkg==1.2.0; sys_platform == "linux"` | Environment marker restricting installation to a specific OS or Python version |
