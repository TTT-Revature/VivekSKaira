# Exception Handling: `try`, `except`, `else`, and `finally`

## 1. Overview
In Python, runtime errors are represented as objects called **exceptions**. When an error occurs during execution, Python stops normal sequential execution and searches up the call stack for a matching exception handler—if none is found, the program terminates with a traceback.

Python's **`try` statement** provides structured exception handling using four clauses in a strict syntactic order:

1. **`try`:** Wraps the code block that might raise an exception.
2. **`except`:** Catches and handles specific exception types raised inside the `try` block.
3. **`else` (Optional):** Executes **only if** the `try` block completes without raising any exception.
4. **`finally` (Optional):** Executes **unconditionally** upon exiting the `try` statement, regardless of whether an exception occurred, was caught, went uncaught, or exited via `return`.

---

## 2. Syntax and Execution Flow

### Complete Structure
```python
try:
    # Risky code that may raise an exception
    ...
except SpecificError as err:
    # Runs ONLY if SpecificError (or a subclass) is raised in 'try'
    ...
except (AnotherError, ThirdError) as err:
    # Runs if either AnotherError or ThirdError is raised in 'try'
    ...
else:
    # Runs ONLY if 'try' completed with ZERO exceptions (requires at least one 'except')
    ...
finally:
    # ALWAYS runs before leaving the try statement (cleanup logic)
    ...
```
*(Note: A `try` statement must have at least one `except` clause or a `finally` clause. An `else` clause is valid only when preceded by at least one `except` clause.)*

### Execution Paths by Scenario

| Scenario | Execution Order | Outcome |
| :--- | :--- | :--- |
| **1. No exception raised** | `try` -> `else` -> `finally` | Normal completion; `except` blocks are skipped |
| **2. Exception raised and matched** | `try` (stops at error line) -> matching `except` -> `finally` | Exception is handled; `else` and remaining `except` blocks are skipped |
| **3. Exception raised and NOT matched** | `try` (stops at error line) -> `finally` -> propagates upward | `finally` runs first, then the unhandled exception crashes or bubbles up |
| **4. `return` / `break` inside `try` or `except`** | `try`/`except` (up to jump) -> `finally` -> exits function/loop | `finally` still executes before control leaves the block |

## 3. Catching Exceptions (`except` Patterns)

### 1. Catching Specific Exceptions and Inspecting Details
Bind the caught exception instance using **`as variable_name`** to inspect its error message, type, and arguments:

```python
def parse_port(raw_port: str) -> int:
    try:
        port = int(raw_port)
        if not (1 <= port <= 65535):
            raise ValueError(f"Port {port} out of valid range (1-65535)")
        return port
    except ValueError as err:
        print(f"[{type(err).__name__}] Invalid port configuration: {err}")
        return 8080  # Fallback default

print(parse_port("abc"))    # [ValueError] Invalid port configuration: invalid literal for int()... -> 8080
print(parse_port("90000"))  # [ValueError] Invalid port configuration: Port 90000 out of valid range... -> 8080
```

### 2. Catching Multiple Exceptions
Group multiple exception classes inside a **tuple** when they share the same recovery logic, or chain separate `except` blocks when each error requires distinct handling:

```python
def divide_elements(items: list[str], index: int, divisor: int) -> float | None:
    try:
        value = int(items[index])
        return value / divisor
    except (IndexError, ValueError) as err:
        print(f"Input lookup or conversion failed: {err}")
        return None
    except ZeroDivisionError:
        print("Divisor cannot be zero.")
        return None
```

### 3. Ordering `except` Blocks (Specific Before General)
Python evaluates `except` clauses top-to-bottom and executes **only the first matching block** (using `isinstance(exc, CaughtType)`). Always place **child (more specific) exceptions** before **parent (more general) exceptions**:

```python
try:
    with open("missing_config.json", mode="r", encoding="utf-8") as f:
        data = f.read()
except FileNotFoundError:
    # Specific subclass of OSError -> checked first
    print("Config file not found; creating defaults.")
except PermissionError:
    # Another specific subclass of OSError -> checked second
    print("Permission denied when reading config file.")
except OSError as err:
    # General parent class -> catches any other OS/file error
    print(f"General OS error: {err}")
```

## 4. The `else` Clause: Isolating Risky Operations
The **`else`** block runs **only when no exception was raised in the `try` block**.

### Why Use `else` Instead of Putting Everything in `try`?
Placing follow-up logic inside `else` keeps the `try` block minimal and prevents your `except` handlers from accidentally catching—and misdiagnosing—errors raised by subsequent operations:

```python
def load_and_double(raw_value: str) -> int | None:
    try:
        # Only isolate the operation that can actually fail during parsing
        number = int(raw_value)
    except ValueError:
        print(f"Cannot convert {raw_value!r} to an integer.")
        return None
    else:
        # Runs only if int(raw_value) succeeded; errors here won't be masked as ValueError
        result = number * 2
        print(f"Successfully doubled {number} -> {result}")
        return result

load_and_double("21")    # Successfully doubled 21 -> 42
load_and_double("text")  # Cannot convert 'text' to an integer.
```

## 5. The `finally` Clause: Guaranteed Cleanup
The **`finally`** block is guaranteed to execute on every exit path from a `try` statement. While `with` statements are preferred for standard context-managed resources (like files), `finally` is essential when working with custom cleanup hooks, temporary state resets, or low-level connections.

```python
def run_job(job_name: str, should_fail: bool = False) -> str:
    print(f"[{job_name}] Acquiring temporary lock...")
    try:
        if should_fail:
            raise RuntimeError("Worker crashed mid-task")
        print(f"[{job_name}] Executing task...")
    except RuntimeError as err:
        print(f"[{job_name}] Handled error: {err}")
        return "FAILED"
    else:
        print(f"[{job_name}] Task succeeded.")
        return "SUCCESS"
    finally:
        # Runs BEFORE the function actually returns "SUCCESS" or "FAILED"
        print(f"[{job_name}] Releasing temporary lock.")

print("Outcome 1:", run_job("SyncJob", should_fail=False))
print("---")
print("Outcome 2:", run_job("BackupJob", should_fail=True))
```

## 6. Common Built-In Exception Hierarchy
Understanding Python's built-in exception hierarchy helps you catch the right level of abstraction without intercepting system-exit signals:

```text
BaseException
 ├── SystemExit              (raised by sys.exit())
 ├── KeyboardInterrupt       (raised when user presses Ctrl+C)
 ├── GeneratorExit           (raised when generator.close() is called)
 └── Exception               (base class for all standard runtime errors)
      ├── ArithmeticError
      │    └── ZeroDivisionError
      ├── LookupError
      │    ├── IndexError
      │    └── KeyError
      ├── OSError
      │    ├── FileNotFoundError
      │    ├── FileExistsError
      │    └── PermissionError
      ├── TypeError
      ├── ValueError
      ├── AttributeError
      ├── NameError
      └── RuntimeError
```

* **Catch `Exception`, Never Bare `except:`:** A bare `except:` catches `BaseException`, which traps `KeyboardInterrupt` (preventing `Ctrl+C` termination) and `SystemExit`. Always catch specific exception classes, or at broadest `except Exception as err:`.

## 7. Common Pitfalls and Best Practices

1. **Silent Exception Swallowing (`except Exception: pass`):**
   Catching all exceptions and doing nothing hides bugs and makes debugging nearly impossible. Always catch the narrowest exception type possible and log or handle it meaningfully.
2. **Putting a `return` Statement Inside `finally`:**
   If a `finally` block executes `return`, `break`, or `continue`, it **overrides** any `return` value from `try`/`except`/`else` and **silently discards any active unhandled exception**:
   ```python
   def broken_finally() -> str:
       try:
           raise ValueError("Critical failure")
       finally:
           return "OK"  # DANGER: Swallows ValueError completely and returns "OK"!

   print(broken_finally())  # 'OK' (exception vanished silently)
   ```
3. **Referencing Variables Defined Late in `try` Inside `finally`:**
   If an exception occurs on line 1 of `try` before a resource variable is assigned, referencing that variable in `finally` raises `UnboundLocalError` or `NameError`. Initialize resource variables to `None` before the `try` block:
   ```python
   resource = None
   try:
       resource = acquire_resource()
       process(resource)
   finally:
       if resource is not None:
           resource.close()
   ```

## 8. Quick Reference

| Clause | Required? | When It Executes | Primary Purpose |
| :--- | :--- | :--- | :--- |
| `try:` | Yes | Always entered first | Isolates code that may raise an exception |
| `except ExcType as e:` | Required unless `finally` is present | When `try` raises an instance of `ExcType` | Recovers from, logs, or translates specific errors |
| `except (E1, E2) as e:` | Optional | When `try` raises `E1` or `E2` | Handles multiple related exceptions uniformly |
| `else:` | Optional (requires `except`) | Only if `try` finishes with **no** exceptions | Runs success-path code without risking false `except` matches |
| `finally:` | Optional | **Always** before exiting the `try` statement | Releases resources, resets state, and performs mandatory cleanup |
