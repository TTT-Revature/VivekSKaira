# Debugger and Breakpoints in Python

## 1. Overview
A **debugger** is an interactive diagnostic tool that lets you pause a running program at specific points, step through code line by line, inspect the call stack, and examine or modify variables in real time.

* **Breakpoint:** An intentional stopping point placed in code (either programmatically via `breakpoint()` or visually in an IDE gutter) where the debugger suspends execution and hands control to the developer.
* **How Python Debuggers Work:** Under the hood, Python's built-in debugger (**`pdb`**) registers a trace callback using **`sys.settrace()`** (or `sys.monitoring` in Python 3.12+) that intercepts line-execution, function-call, and exception events as the interpreter runs bytecode.
* **Why Use a Debugger Over `print()`?**
  * Eliminates cluttering source files with dozens of temporary `print()` statements.
  * Lets you inspect *any* variable, object attribute, or expression on the spot—even ones you did not anticipate needing beforehand.
  * Allows testing fixes live by mutating variables mid-execution without restarting the program.

## 2. Setting Breakpoints in Code (`breakpoint()` & `PYTHONBREAKPOINT`)

### 1. The Built-In `breakpoint()` Function
Introduced in Python 3.7 (PEP 553), **`breakpoint()`** is the standard way to drop into a debugger at any line. Internally, `breakpoint()` calls `sys.breakpointhook()`, which defaults to `pdb.set_trace()`.

```python
def calculate_batch_bonus(scores: list[int], multiplier: float) -> float:
    valid_scores = [s for s in scores if s >= 60]
    total = sum(valid_scores)

    # Execution pauses immediately after this line and opens the (Pdb) prompt
    breakpoint()

    bonus = (total / len(valid_scores)) * multiplier
    return round(bonus, 2)

print(calculate_batch_bonus([55, 80, 92, 74], 1.15))
```

### 2. Conditional Breakpoints in Code
To pause execution **only when a specific bug condition occurs** (such as on iteration `500` of a loop or when a value becomes `None`), guard `breakpoint()` with an `if` statement:

```python
def process_records(records: list[dict[str, int]]) -> None:
    for idx, record in enumerate(records):
        if record.get("amount", 0) < 0:
            # Pauses only when an invalid negative record is encountered
            breakpoint()
        print(f"Processed #{idx}: {record}")
```

### 3. Controlling Debugger Behavior with `PYTHONBREAKPOINT`
Without modifying a single line of code, you can disable all `breakpoint()` calls or swap `pdb` for a third-party debugger (such as `ipdb` or `pudb`) via the **`PYTHONBREAKPOINT`** environment variable:

| Command / Environment Setting | Effect |
| :--- | :--- |
| `python app.py` | Default behavior: invokes `pdb.set_trace()` |
| `PYTHONBREAKPOINT=0 python app.py` | **Disables** all `breakpoint()` calls completely (becomes a no-op) |
| `PYTHONBREAKPOINT=ipdb.set_trace python app.py` | Uses `ipdb` (enhanced autocomplete and syntax highlighting) instead of `pdb` |

## 3. Stepping Through Code Execution
Once paused at a `(Pdb)` prompt, stepping commands control how execution advances:

| Command | Short | Execution Behavior | When to Use |
| :--- | :--- | :--- | :--- |
| `next` | `n` | Executes the current line and stops at the **next line in the same function** (steps *over* function calls) | You trust a called function and do not want to trace inside it |
| `step` | `s` | Executes the current line and stops **inside the first function called** on that line (steps *into* calls) | You suspect the bug is inside the function being called |
| `return` | `r` | Runs until the **current function returns** to its caller (steps *out* of function) | You stepped into a helper function by mistake and want to finish it quickly |
| `until [lineno]` | `unt` | Continues until reaching a line number **greater than the current line** (or `lineno`) | Exiting a `for`/`while` loop cleanly without hitting every remaining iteration |
| `continue` | `c` | Resumes normal execution until the **next breakpoint** is hit or the program exits | You finished inspecting the current state and want to jump to the next stop |
| `jump lineno` | `j` | Sets the next line to execute without running intermediate lines (within bottom frame only) | Re-running a block or skipping over code during a live debug session |

### Example: `next` vs. `step` vs. `until`
```python
def apply_tax(amount: float) -> float:
    tax = amount * 0.18     # 'step' enters here; 'next' skips over apply_tax()
    return amount + tax

def summarize_cart(prices: list[float]) -> float:
    total = 0.0
    for price in prices:    # 'until' on the loop body jumps past the loop once finished
        total += apply_tax(price)
    return total

breakpoint()
print(summarize_cart([100.0, 200.0, 300.0]))
```

## 4. Managing Breakpoints Dynamically Inside `pdb`
You do not have to edit source files to add, disable, or make breakpoints conditional—`pdb` lets you manage breakpoints interactively while paused:

```text
(Pdb) b 42                        # Set a permanent breakpoint at line 42 of current file
(Pdb) b utils/parser.py:18        # Set a breakpoint at line 18 of utils/parser.py
(Pdb) b 42, user_id == 105        # Set a conditional breakpoint (stops only when condition is True)
(Pdb) tbreak 55                   # Set a temporary breakpoint (auto-deletes after first hit)
(Pdb) b                           # List all active breakpoints with their IDs and hit counts
(Pdb) ignore 1 10                 # Ignore breakpoint #1 for the next 10 hits
(Pdb) condition 1 len(items) == 0 # Attach or update a condition on existing breakpoint #1
(Pdb) disable 1                   # Temporarily disable breakpoint #1 without deleting it
(Pdb) enable 1                    # Re-enable breakpoint #1
(Pdb) clear 1                     # Permanently delete breakpoint #1
```

## 5. Inspecting and Modifying State at Runtime

### 1. Evaluating Expressions and Watching Variables
* **`p <expr>` / `pp <expr>`:** Evaluates and prints (or pretty-prints) any valid Python expression, variable, or method call.
* **`a` (`args`):** Prints all arguments and their values passed to the current function.
* **`display <expr>`:** Watches an expression and automatically prints its value every time execution stops (remove with `undisplay <expr>`).
* **`whatis <expr>`:** Prints the data type of an expression.

### 2. Navigating the Call Stack
* **`w` (`where`):** Displays the full call stack, marking the active frame with `>`.
* **`u` (`up`) / `d` (`down`):** Moves one frame up (toward the caller) or down (toward the inner callee) so you can inspect local variables in calling functions.

### 3. Live Variable Mutation and the `!` Prefix
In `pdb`, single-letter commands like `c`, `n`, `s`, `p`, `l`, and `q` take precedence over variable names. If your code has a variable named `c` or `n`, prefix Python statements with **`!`** so `pdb` executes them as Python code rather than debugger commands:

```text
(Pdb) p c          # Prints variable 'c'
10
(Pdb) c            # Interpreted as 'continue' command!
(Pdb) !c = 25      # Uses '!' prefix to reassign variable 'c' to 25 safely
(Pdb) interact     # Drops into a full interactive Python REPL sharing current local variables
```

## 6. Post-Mortem and IDE Debugging

### 1. Post-Mortem Debugging (`pdb.post_mortem()` / `pdb.pm()`)
When an unhandled exception crashes a script or occurs in an interactive REPL, **post-mortem debugging** opens `pdb` at the exact stack frame and variable state where the exception happened:

```python
import pdb
import traceback

def run_pipeline() -> None:
    data = {"count": 0}
    print(100 / data["count"])

try:
    run_pipeline()
except Exception:
    traceback.print_exc()
    pdb.post_mortem()  # Launches interactive (Pdb) session at the ZeroDivisionError line
```
*(From the terminal, run **`python -m pdb -c continue script.py`** to run a script at full speed and drop into `pdb` post-mortem mode only if an unhandled exception occurs.)*

### 2. Visual IDE Debuggers (VS Code & PyCharm)
Modern IDEs wrap Python's debugging protocol (`debugpy` in VS Code, `pydevd` in PyCharm) with a graphical interface:
* **Gutter Breakpoints:** Click to the left of any line number to toggle red-dot breakpoints without editing code.
* **Conditional & Logpoint Breakpoints:** Right-click a gutter breakpoint to add boolean hit conditions, hit-count thresholds, or **Logpoints** (which print formatted expressions to the debug console without pausing execution).
* **Variables & Watch Panels:** Continuously displays local/global scopes, call stacks, and pinned watch expressions while stepping via toolbar shortcuts (`F10` Step Over, `F11` Step Into, `Shift+F11` Step Out, `F5` Continue).

## 7. Best Practices and Common Pitfalls

1. **Never Commit `breakpoint()` Calls to Git:**
   Leaving an active `breakpoint()` in production or CI/CD pipelines hangs automated test runners waiting for standard input (or raises `BdbQuit`). Use pre-commit hooks or linters (such as `ruff` rule `T100`) to block committed `breakpoint()` statements.
2. **Avoid Side Effects When Evaluating Expressions in `pdb`:**
   Running `p iterator.__next__()` or `p items.pop()` inside `pdb` mutates program state and consumes iterators, which can alter subsequent execution behavior.
3. **Avoid `jump` Across `with` or `try...finally` Blocks:**
   Using `pdb`'s `jump` command to leap into or out of context managers (`with`) or `try...finally` blocks bypasses `__enter__`/`__exit__` setup and cleanup, leaving resources locked or uninitialized.
4. **Debugging Multithreaded or Async Code:**
   Standard `pdb` attaches to `sys.stdin`/`sys.stdout` on the main thread and can interleave prompts if multiple threads hit `breakpoint()` simultaneously. Use IDE debuggers (which support per-thread call stacks) or conditional breakpoints restricted to a single thread/task when debugging concurrent code.

## 8. Quick Reference

| Command / Function | Short | Category | Description |
| :--- | :--- | :--- | :--- |
| `breakpoint()` | — | Entry point | Pauses execution and invokes `sys.breakpointhook()` (`pdb` by default) |
| `PYTHONBREAKPOINT=0` | — | Env var | Disables all `breakpoint()` calls globally without changing source code |
| `next` | `n` | Stepping | Steps **over** function calls to the next line in the current frame |
| `step` | `s` | Stepping | Steps **into** a function called on the current line |
| `return` | `r` | Stepping | Steps **out** of the current function back to its caller |
| `until` | `unt` | Stepping | Advances past the current line number (exits loops cleanly) |
| `continue` | `c` | Stepping | Resumes execution until the next breakpoint or program exit |
| `break [loc], [cond]` | `b` | Breakpoints | Sets a permanent (and optionally conditional) breakpoint |
| `tbreak [loc]` | `tbreak` | Breakpoints | Sets a one-time temporary breakpoint that deletes itself on first hit |
| `p <expr>` / `pp <expr>` | `p` / `pp` | Inspection | Prints or pretty-prints an expression's current value |
| `display <expr>` | `display` | Inspection | Automatically prints `<expr>` every time execution stops |
| `where` / `up` / `down` | `w` / `u` / `d` | Stack | Displays call stack and navigates between caller/callee frames |
| `!<statement>` | `!` | Mutation | Executes a Python statement directly (prevents clashes with `pdb` commands) |
| `pdb.post_mortem()` | — | Post-mortem | Opens `pdb` at the failure frame inside an `except` handler |
