# Logging and Log Levels in Python

## 1. Overview
Python's built-in **`logging`** module provides a flexible, thread-safe framework for recording diagnostic messages, runtime events, and errors from an application.

* **Why Use `logging` Over `print()`?**
  * **Severity Filtering:** Categorizes messages by importance (`DEBUG` through `CRITICAL`), allowing you to filter out verbose diagnostics in production without editing source code.
  * **Configurable Destinations:** Routes logs simultaneously to the console (`stderr`/`stdout`), rotating files, system logs, or external monitoring services.
  * **Rich Contextual Metadata:** Automatically attaches timestamps, module names, line numbers, process/thread IDs, and full exception tracebacks.
  * **Hierarchical Control:** Allows enabling or muting logs per module or package independently.

---

## 2. Standard Log Levels
Python defines **five standard severity levels**, each mapped to an integer value. When a logger is configured with a threshold level, it processes messages **at or above** that numeric severity and ignores lower-severity messages.

| Level | Numeric Value | Logger Method | When to Use |
| :--- | :--- | :--- | :--- |
| `DEBUG` | `10` | `logger.debug()` | Detailed diagnostic information for troubleshooting during development |
| `INFO` | `20` | `logger.info()` | Confirmation that normal application operations are working as expected |
| `WARNING` | `30` | `logger.warning()` | Unexpected events or potential issues (e.g., low disk space, deprecated API), though the app still runs |
| `ERROR` | `40` | `logger.error()` | A serious problem where a specific operation or request failed |
| `CRITICAL` | `50` | `logger.critical()` | A severe system-level failure indicating the program itself may be unable to continue running |

*(Note: By default, Python's root logger has a threshold of **`WARNING` (`30`)**, which is why `logging.debug()` and `logging.info()` produce no output until the logging level is explicitly lowered.)*

```python
import logging

# Default threshold is WARNING (30)
logging.debug("Variable x = 42")           # Ignored by default
logging.info("Server initialization done") # Ignored by default
logging.warning("Cache miss; querying DB") # Output: WARNING:root:Cache miss; querying DB
logging.error("Failed to parse payload")   # Output: ERROR:root:Failed to parse payload
logging.critical("Database unreachable")   # Output: CRITICAL:root:Database unreachable
```

## 3. Basic Configuration (`logging.basicConfig()`)
For single-file scripts and small applications, **`logging.basicConfig()`** configures the root logger in a single call.

### 1. Formatting and Level Thresholds
```python
import logging

logging.basicConfig(
    level=logging.DEBUG,
    format="%(asctime)s | %(levelname)-8s | %(name)s:%(lineno)d | %(message)s",
    datefmt="%Y-%m-%d %H:%M:%S",
)

logging.debug("Loaded environment settings")
logging.info("Batch pipeline started")
logging.warning("Retrying request (attempt 2/3)")
```

### 2. Logging to Both a File and the Console
Passing a list of handlers to `handlers=[...]` routes every log record to multiple destinations simultaneously:

```python
import logging
from pathlib import Path

log_file = Path("application.log")

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s [%(levelname)s] %(message)s",
    handlers=[
        logging.FileHandler(log_file, mode="a", encoding="utf-8"),
        logging.StreamHandler(),  # Outputs to console (sys.stderr by default)
    ],
    force=True,  # Reconfigures root logger even if basicConfig() was already called
)

logging.info("Application started successfully.")
logging.error("Connection timeout while calling upstream API.")
```

## 4. Core Logging Architecture
For multi-module projects and production applications, Python's `logging` module separates concerns across four modular components:

1. **Logger (`logging.Logger`):** The entry point your application code calls (`logger.info(...)`). Loggers form a dot-separated hierarchy (e.g., `app`, `app.db`, `app.api`).
2. **Handler (`logging.Handler`):** Sends log records to a specific destination (console, file, rotating file, socket, HTTP). Each handler can have its own severity level.
3. **Formatter (`logging.Formatter`):** Defines the text layout and metadata fields of the final log message.
4. **Filter (`logging.Filter`):** Provides fine-grained boolean filtering logic beyond numeric log levels.

```text
Application Code -> Logger (level check) -> Handler(s) (level check) -> Formatter -> Output Destination
```

### Modular Logger Setup (`logging.getLogger(__name__)`)
Always create a module-specific logger using **`logging.getLogger(__name__)`** rather than calling `logging.info()` on the root logger directly:

```python
import logging
from logging.handlers import RotatingFileHandler

def configure_logger(name: str) -> logging.Logger:
    logger = logging.getLogger(name)
    logger.setLevel(logging.DEBUG)

    # Avoid adding duplicate handlers if configure_logger() is called multiple times
    if logger.handlers:
        return logger

    formatter = logging.Formatter(
        fmt="%(asctime)s | %(levelname)-8s | %(name)s | %(message)s",
        datefmt="%Y-%m-%d %H:%M:%S",
    )

    # 1. Console handler: shows INFO and above
    console_handler = logging.StreamHandler()
    console_handler.setLevel(logging.INFO)
    console_handler.setFormatter(formatter)

    # 2. Rotating file handler: captures DEBUG and above, rotates at 1 MB (keeps 3 backups)
    file_handler = RotatingFileHandler(
        "service.log",
        maxBytes=1_048_576,
        backupCount=3,
        encoding="utf-8",
    )
    file_handler.setLevel(logging.DEBUG)
    file_handler.setFormatter(formatter)

    logger.addHandler(console_handler)
    logger.addHandler(file_handler)
    return logger

logger = configure_logger(__name__)
logger.debug("Detailed SQL query trace")  # Written only to service.log
logger.info("Service ready on port 8000") # Written to both console and service.log
```

## 5. Logging Exceptions and Stack Traces
Inside an `except` block, use **`logger.exception()`** (which logs at `ERROR` level) or pass **`exc_info=True`** to any logging method to capture the full exception traceback automatically:

```python
import logging

logging.basicConfig(level=logging.ERROR, format="%(asctime)s | %(levelname)s | %(message)s")
logger = logging.getLogger(__name__)

def divide_numbers(a: int, b: int) -> float | None:
    try:
        return a / b
    except ZeroDivisionError:
        # Automatically appends the full stack trace to the ERROR log entry
        logger.exception("Failed to divide %s by %s", a, b)
        return None

divide_numbers(10, 0)
```
*(Tip: Use `logger.warning("Retrying after error", exc_info=True)` when you want to record a traceback at `WARNING` or `DEBUG` severity rather than `ERROR`.)*

## 6. Common `LogRecord` Format Attributes

| Attribute | Format Specifier | Description |
| :--- | :--- | :--- |
| `asctime` | `%(asctime)s` | Human-readable timestamp when the `LogRecord` was created |
| `levelname` | `%(levelname)s` | Text name of the log level (`DEBUG`, `INFO`, `WARNING`, `ERROR`, `CRITICAL`) |
| `levelno` | `%(levelno)s` | Numeric severity value (`10`, `20`, `30`, `40`, `50`) |
| `name` | `%(name)s` | Name of the logger (e.g., `__main__` or `services.auth`) |
| `message` | `%(message)s` | The formatted log message string |
| `filename` | `%(filename)s` | Filename portion of the source file where the log call was made |
| `funcName` | `%(funcName)s` | Name of the function containing the logging call |
| `lineno` | `%(lineno)d` | Source line number where the logging call was issued |
| `process` / `threadName` | `%(process)d` / `%(threadName)s` | Process ID and thread name (useful in concurrent applications) |

## 7. Best Practices and Common Pitfalls

1. **Use Lazy `%`-Style Formatting in Log Calls:**
   Pass message arguments separately (`logger.debug("Item %s processed", item)`) rather than using f-strings (`logger.debug(f"Item {item} processed")`). With lazy formatting, Python skips string interpolation completely if the log level is disabled—saving CPU cycles in tight loops.
2. **Use `logging.getLogger(__name__)` in Every Module:**
   Using `__name__` automatically names each logger after its module path (e.g., `app.utils.parser`), making it easy to trace where logs originate and control verbosity per package.
3. **`logging.basicConfig()` Only Runs Once by Default:**
   Calling `basicConfig()` a second time has no effect if the root logger already has handlers attached. Pass **`force=True`** (Python 3.8+) if you intentionally need to override an existing configuration.
4. **Never Log Sensitive Credentials:**
   Avoid logging passwords, API keys, JWT tokens, session cookies, or personally identifiable information (PII) in plain text.
5. **Do Not Configure Handlers Inside Reusable Libraries:**
   Library modules should only obtain a logger via `logging.getLogger(__name__)` and emit log records—leaving handler destinations and formatting up to the top-level application entry point.

## 8. Quick Reference

| Function / Class / Option | Purpose | Key Notes |
| :--- | :--- | :--- |
| `logging.getLogger(__name__)` | Creates or retrieves a named logger | Recommended per-module logger pattern |
| `logging.basicConfig(...)` | Configures root logger level, format, and handlers | Ignored on subsequent calls unless `force=True` |
| `logger.debug()` / `.info()` | Logs diagnostic (`10`) or operational (`20`) events | Hidden unless logger level is set to `DEBUG` or `INFO` |
| `logger.warning()` / `.error()` | Logs recoverable issues (`30`) or operation failures (`40`) | `WARNING` (`30`) is Python's default threshold |
| `logger.critical()` | Logs severe system-halting failures (`50`) | Highest built-in severity level |
| `logger.exception(msg, *args)` | Logs an `ERROR` message with full exception traceback | Call only inside an `except` block |
| `RotatingFileHandler` | Writes logs to disk and rotates files by byte size | Prevents log files from exhausting disk space |
