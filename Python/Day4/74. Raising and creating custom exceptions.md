# Raising and Creating Custom Exceptions

## 1. Overview
In addition to handling built-in errors raised by the Python interpreter, applications frequently need to **signal their own error conditions** when business rules, input constraints, or system invariants are violated.

* **Raising Exceptions (`raise`):** Explicitly interrupts normal execution and throws an exception object up the call stack.
* **Custom Exceptions:** User-defined exception classes (inheriting from `Exception`) that represent domain-specific failures—making error handling clearer, more expressive, and easier to catch selectively than generic built-in errors.

---

## 2. Raising Exceptions (`raise`)
Use the **`raise`** statement to trigger an exception at any point in your code. You can pass either an **exception instance** (most common) or an **exception class** (which Python instantiates with no arguments).

### Syntax and Input Validation Example
```python
def calculate_discount(price: float, discount_percent: float) -> float:
    """Calculates final price after validating numeric inputs."""
    if not isinstance(price, (int, float)) or not isinstance(discount_percent, (int, float)):
        raise TypeError("Price and discount_percent must be numeric.")

    if price < 0:
        raise ValueError(f"Price cannot be negative; received {price}.")

    if not (0 <= discount_percent <= 100):
        raise ValueError(f"Discount must be between 0 and 100; received {discount_percent}.")

    return price * (1 - discount_percent / 100)

print(calculate_discount(1000.0, 15.0))  # 850.0
# calculate_discount(1000.0, 120.0)      # Raises ValueError: Discount must be between 0 and 100...
```
*(Note: The object passed to `raise` must be an instance or subclass of `BaseException`. Attempting to `raise "some error"` raises `TypeError: exceptions must derive from BaseException`.)*

## 3. Re-Raising and Exception Chaining (`raise ... from ...`)

### 1. Re-Raising the Active Exception (Bare `raise`)
Inside an `except` block, using **`raise`** with no arguments re-throws the exact exception that was just caught **without altering its original traceback**. This is ideal for logging or cleanup before letting the caller handle the failure:

```python
def process_record(record: dict[str, int]) -> int:
    try:
        return 100 // record["divisor"]
    except ZeroDivisionError:
        print("[LOG] Division by zero encountered while processing record.")
        raise  # Re-raises the original ZeroDivisionError with full traceback intact
```

### 2. Explicit Exception Chaining (`raise NewError from original_err`)
When translating a low-level technical exception (such as `KeyError`, `ValueError`, or `OSError`) into a higher-level domain exception, use **`from`** to preserve the root cause in **`__cause__`**. Python's traceback displays both exceptions clearly (`The above exception was the direct cause of the following exception:`):

```python
class ConfigLoadError(Exception):
    """Raised when application configuration cannot be parsed."""

def get_timeout(config: dict[str, str]) -> int:
    try:
        return int(config["TIMEOUT"])
    except (KeyError, ValueError) as err:
        raise ConfigLoadError("Invalid or missing TIMEOUT setting.") from err

try:
    get_timeout({"TIMEOUT": "invalid_number"})
except ConfigLoadError as err:
    print("Caught :", err)
    print("Cause  :", repr(err.__cause__))  # ValueError("invalid literal for int()...")
```

### 3. Suppressing Exception Context (`raise NewError from None`)
If an exception is raised inside an `except` block *without* `from`, Python implicitly attaches the previous exception to `__context__`. When you want to hide noisy internal implementation details and present only a clean domain error, chain **`from None`**:

```python
def lookup_user_role(roles: dict[str, str], username: str) -> str:
    try:
        return roles[username]
    except KeyError:
        # Suppresses the internal KeyError traceback from user-facing output
        raise LookupError(f"User {username!r} does not exist.") from None
```

## 4. Creating Custom Exceptions
To create a custom exception, define a new class that inherits directly (or indirectly) from **`Exception`**.

### Minimal Custom Exception
```python
class InvalidEmailError(Exception):
    """Raised when an email address fails format validation."""

def register_user(email: str) -> str:
    if "@" not in email or "." not in email.split("@")[-1]:
        raise InvalidEmailError(f"Malformed email address: {email!r}")
    return f"Registered {email}"

try:
    register_user("vivek-at-example")
except InvalidEmailError as err:
    print(f"Registration failed: {err}")
```

## 5. Adding Custom Attributes and Context
Custom exceptions are full Python classes. Overriding **`__init__`** allows you to attach structured metadata (such as error codes, offending values, or retry delays) so `except` handlers can inspect fields programmatically rather than parsing error strings.

Always call **`super().__init__(message)`** inside `__init__` so the base `Exception` class populates `.args` and standard string formatting continues to work:

```python
class InsufficientBalanceError(Exception):
    """Raised when a withdrawal exceeds the available account balance."""

    def __init__(self, balance: float, amount: float, account_id: str) -> None:
        self.balance = balance
        self.amount = amount
        self.account_id = account_id
        self.shortfall = amount - balance
        message = (
            f"Account {account_id}: cannot withdraw {amount:.2f} "
            f"(available balance: {balance:.2f}, shortfall: {self.shortfall:.2f})"
        )
        super().__init__(message)

def withdraw(account_id: str, balance: float, amount: float) -> float:
    if amount > balance:
        raise InsufficientBalanceError(balance=balance, amount=amount, account_id=account_id)
    return balance - amount

try:
    withdraw("ACC-101", balance=500.0, amount=750.0)
except InsufficientBalanceError as err:
    print(err)
    print(f"Structured shortfall data: {err.shortfall:.2f}")
```

## 6. Designing Domain-Specific Exception Hierarchies
In larger modules, libraries, or services, define a **base exception class** for your application or module and derive specific exceptions from it. This gives callers flexibility:

* Catch **specific subclasses** when distinct recovery steps are needed.
* Catch the **base exception** to handle any error originating from that module uniformly.

```python
# Base exception for the entire payment module
class PaymentError(Exception):
    """Base class for all payment processing exceptions."""

# Specific domain subclasses
class CardDeclinedError(PaymentError):
    """Raised when the issuing bank declines the transaction."""

class PaymentGatewayTimeoutError(PaymentError):
    """Raised when the payment provider fails to respond in time."""

def charge_card(card_status: str) -> None:
    if card_status == "declined":
        raise CardDeclinedError("Card was declined by issuer.")
    if card_status == "timeout":
        raise PaymentGatewayTimeoutError("Gateway timed out after 30s.")

# Caller can handle specific errors individually and catch all other PaymentErrors together
for status in ("declined", "timeout"):
    try:
        charge_card(status)
    except CardDeclinedError as err:
        print(f"[USER ACTION REQUIRED] {err}")
    except PaymentError as err:
        print(f"[RETRYABLE SYSTEM ERROR] {err}")
```

## 7. Best Practices and Common Pitfalls

1. **Inherit from `Exception`, Never `BaseException`:**
   `BaseException` sits above `KeyboardInterrupt` and `SystemExit`. Inheriting from `Exception` ensures standard `except Exception:` handlers catch your custom error while allowing system-exit signals to work properly.
2. **Follow the `Error` Naming Convention (PEP 8):**
   End custom exception names with **`Error`** (e.g., `AuthenticationError`, `SchemaValidationError`) whenever the exception represents an error condition.
3. **Always Call `super().__init__(message)`:**
   If you override `__init__` without calling `super().__init__(message)`, `err.args` remains an empty tuple `()`, `str(err)` returns `""`, and object serialization (`pickle` / `multiprocessing`) can fail.
4. **Know When to Use Built-In vs. Custom Exceptions:**
   * **Use built-in exceptions** (`ValueError`, `TypeError`, `KeyError`, `IndexError`, `FileNotFoundError`) for general programming contracts and standard invalid arguments.
   * **Use custom exceptions** for business-logic violations, external service/API failures, and module-level exception hierarchies.

## 8. Quick Reference

| Construct / Pattern | Syntax | Purpose |
| :--- | :--- | :--- |
| Raise an exception | `raise ValueError("Invalid age")` | Stops normal execution and throws an exception instance |
| Re-raise caught exception | `raise` (inside `except`) | Propagates the active exception while preserving its traceback |
| Chain with root cause | `raise DomainError("...") from err` | Links `err` to `DomainError.__cause__` for clear debugging |
| Suppress context | `raise DomainError("...") from None` | Hides the underlying caught exception from the traceback |
| Minimal custom exception | `class MyAppError(Exception): pass` | Defines a domain-specific exception class |
| Custom exception with state | `def __init__(self, ...): super().__init__(msg)` | Attaches structured attributes while preserving `.args` and `str(err)` |
