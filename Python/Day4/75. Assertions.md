# Assertions in Python

## 1. Overview
An **assertion** is a built-in debugging aid and sanity-check statement (`assert`) that verifies whether a condition assumed to be `True` actually holds during program execution.

* **Behavior:**
  * If the condition evaluates to **`True`** (truthy), execution continues normally with no visible effect.
  * If the condition evaluates to **`False`** (falsy), Python immediately interrupts execution and raises an **`AssertionError`** (with an optional diagnostic message).
* **Purpose:** Assertions are designed to detect **internal programmer bugs, broken invariants, and impossible states** during development and testing—not to handle expected runtime errors or validate external user input.

---

## 2. Syntax and Internal Execution

### Two Syntactic Forms
```python
# 1. Basic form: raises AssertionError with no message if condition is falsy
assert condition

# 2. Diagnostic form: passes 'message' to AssertionError(message)
assert condition, "Descriptive error message explaining the violated assumption"
```

### How Python Executes `assert` Under the Hood
`assert` is a **keyword statement**, not a function. Internally, Python compiles every `assert` statement as if it were guarded by the built-in boolean constant **`__debug__`**:

```python
# Python compiles:
#   assert x > 0, "x must be positive"
# Into the conceptual equivalent:
if __debug__:
    if not (x > 0):
        raise AssertionError("x must be positive")
```
*(Note: Because `message` is evaluated only when `condition` is falsy, formatting expensive diagnostic strings inside `assert cond, f"..."` incurs zero string-formatting overhead when the assertion passes.)*

---

## 3. Disabling Assertions (`__debug__`, `-O`, and `-OO`)
In Python, **`__debug__`** is a built-in read-only constant set to `True` by default. However, assertions can be completely stripped out at compile time when running Python in optimized mode:

* Running **`python -O script.py`** (or setting `PYTHONOPTIMIZE=1`) sets `__debug__ = False` and **omits all `assert` statements from the generated bytecode**.
* Running **`python -OO script.py`** (or setting `PYTHONOPTIMIZE=2`) removes both `assert` statements and docstrings (`__doc__`).

| Execution Command | `__debug__` Value | Assertions Executed? | Docstrings Retained? |
| :--- | :--- | :--- | :--- |
| `python app.py` | `True` | Yes | Yes |
| `python -O app.py` | `False` | **No (stripped from bytecode)** | Yes |
| `python -OO app.py` | `False` | **No (stripped from bytecode)** | No |

```python
print("Debug mode active:", __debug__)

# Under `python -O`, the following line does not even exist in compiled bytecode
assert False, "This never runs when Python is invoked with -O"
```

## 4. Valid Use Cases for Assertions

### 1. Enforcing Internal Invariants and Post-Conditions
Use `assert` to verify that internal algorithms maintain expected invariants or return valid outputs:

```python
def normalize_scores(scores: list[float]) -> list[float]:
    """Scales non-negative scores into the [0.0, 1.0] range."""
    max_score = max(scores)
    normalized = [s / max_score for s in scores]

    # Post-condition sanity check on internal calculation
    assert all(0.0 <= val <= 1.0 for val in normalized), (
        f"Normalized values out of [0, 1] bounds: {normalized}"
    )
    return normalized

print(normalize_scores([50.0, 75.0, 100.0]))  # [0.5, 0.75, 1.0]
```

### 2. Guarding Unreachable Code Paths
When branching over a closed set of internal states, an assertion catches unhandled cases immediately if a new state is added later:

```python
def get_role_priority(role: str) -> int:
    if role == "admin":
        return 1
    if role == "trainer":
        return 2
    if role == "intern":
        return 3
    assert False, f"Unhandled internal role: {role!r}"
```

### 3. Inline Smoke Tests in Modules
Assertions are frequently placed inside `if __name__ == "__main__":` blocks (and used directly by test frameworks such as **`pytest`**) to verify expected function behavior:

```python
def clamp(value: int, low: int, high: int) -> int:
    return max(low, min(value, high))

if __name__ == "__main__":
    assert clamp(5, 1, 10) == 5
    assert clamp(-3, 1, 10) == 1
    assert clamp(25, 1, 10) == 10
    print("All smoke tests passed.")
```

## 5. When NOT to Use Assertions (`assert` vs. `raise`)
Because assertions vanish under `-O` optimization, **never rely on `assert` for application logic, security, or external validation**.

| Criterion | `assert condition, msg` | `if not condition: raise Exc(msg)` |
| :--- | :--- | :--- |
| **Primary Intent** | Catch internal bugs and broken developer assumptions | Handle invalid external input, runtime errors, and business rules |
| **Exception Raised** | Always `AssertionError` | Specific exception (`ValueError`, `TypeError`, `PermissionError`, etc.) |
| **Can Be Disabled?** | **Yes** (`python -O` / `PYTHONOPTIMIZE=1`) | **No** — always executes in every environment |
| **User / API Input Validation** | Never use | Always use |
| **Security & Auth Checks** | Never use (critical vulnerability if `-O` is enabled) | Always use |

### Example: Proper Separation of `raise` and `assert`
```python
def withdraw_funds(balance: float, amount: float) -> float:
    # 1. Use 'raise' for external/caller input validation (cannot be disabled)
    if amount <= 0:
        raise ValueError(f"Withdrawal amount must be positive; got {amount}")
    if amount > balance:
        raise ValueError(f"Insufficient balance ({balance:.2f}) for withdrawal ({amount:.2f})")

    new_balance = balance - amount

    # 2. Use 'assert' for internal invariant verification
    assert new_balance >= 0, f"Invariant violated: negative balance {new_balance}"
    return new_balance
```

## 6. Common Pitfalls and Edge Cases

### 1. The Parentheses / Non-Empty Tuple Trap
Because `assert` is a statement rather than a function, wrapping the condition and message in parentheses turns them into a **2-element tuple**. In Python, any non-empty tuple is always truthy—meaning the assertion **never fails**, even when the condition is `False`:

```python
# PITFALL: Parentheses create a 2-tuple (False, "Error"), which evaluates to True!
# Python 3.8+ emits: SyntaxWarning: assertion is always true, perhaps remove parentheses?
assert (1 == 2, "Math is broken")  # NEVER raises AssertionError!

# CORRECT: Omit outer parentheses
assert 1 == 2, "Math is broken"    # Raises AssertionError: Math is broken
```

### 2. Putting Side Effects Inside an `assert` Statement
Never call functions that mutate data, update counters, or perform I/O inside an `assert` expression—those operations will silently stop executing when run with `python -O`:

```python
queue = ["task_1", "task_2"]

# PITFALL: queue.pop(0) is skipped completely under `python -O`!
assert queue.pop(0) == "task_1"

# CORRECT: Perform the operation first, then assert on the result
first_task = queue.pop(0)
assert first_task == "task_1"
```

### 3. Catching `AssertionError` in Production Code
Avoid writing `try ... except AssertionError:` to control normal application flow. `AssertionError` indicates a bug in the program itself that should be fixed in code rather than caught and ignored at runtime.

## 7. Quick Reference

| Construct / Flag | Syntax / Usage | Behavior / Notes |
| :--- | :--- | :--- |
| Basic assertion | `assert expr` | Raises `AssertionError` if `bool(expr)` is `False` |
| Assertion with message | `assert expr, msg` | Raises `AssertionError(msg)` if `bool(expr)` is `False` |
| `AssertionError` | Built-in exception class | Inherits from `Exception`; raised on failed `assert` |
| `__debug__` | Built-in boolean constant | `True` by default; `False` when Python runs with `-O` or `-OO` |
| `python -O script.py` | CLI optimization flag | Sets `__debug__ = False` and strips all `assert` statements |
| Tuple trap | `assert (cond, msg)` | Bug: non-empty tuple is always truthy; never use outer parentheses |
