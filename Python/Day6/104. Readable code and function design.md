# Readable Code and Function Design in Python

## 1. Overview
**Readable code** communicates its intent clearly to human readers without requiring mental simulation of every line. Because software is read and maintained far more frequently than it is initially written, clean **function design**—structuring logic into small, predictable, well-named units—is one of the highest-leverage engineering habits.

* **Core Design Principles:**
  * **Single Responsibility Principle (SRP):** Every function should have one clear purpose and one reason to change.
  * **KISS (*Keep It Simple, Stupid*):** Prefer straightforward, explicit logic over clever one-liners or premature abstractions.
  * **DRY (*Don't Repeat Yourself*):** Extract genuinely duplicated business rules into a single authoritative function (while avoiding premature abstraction of coincidental similarity).
  * **YAGNI (*You Aren't Gonna Need It*):** Implement only what current requirements demand rather than speculative flexibility.

## 2. Single Responsibility and Function Decomposition
A well-designed function operates at a **single level of abstraction**. When a single function validates input, parses files, applies business rules, formats output, and writes to disk, it becomes difficult to test, reuse, or modify safely.

### Refactoring a Monolithic Function into Focused Helpers

```python
# BEFORE: Mixed responsibilities (validation, calculation, formatting, and I/O in one function)
def process_payroll_bad(records: list[dict[str, float]]) -> None:
    for r in records:
        if r["hours"] < 0 or r["rate"] <= 0:
            raise ValueError("Invalid payroll record")
        gross = r["hours"] * r["rate"]
        if r["hours"] > 40:
            gross += (r["hours"] - 40) * r["rate"] * 0.5
        net = round(gross * 0.85, 2)
        print(f"{r['name']}: INR {net:.2f}")
```

```python
# AFTER: Decomposed into pure, testable functions with distinct responsibilities
STANDARD_HOURS = 40.0
OVERTIME_MULTIPLIER = 0.5
TAX_RETENTION_RATE = 0.85


def validate_payroll_record(record: dict[str, float]) -> None:
    """Ensure hours and hourly rate are within valid bounds."""
    if record["hours"] < 0 or record["rate"] <= 0:
        raise ValueError(f"Invalid hours or rate in record: {record}")


def calculate_net_pay(hours: float, hourly_rate: float) -> float:
    """Compute net pay including overtime premium and tax deduction."""
    base_pay = hours * hourly_rate
    overtime_hours = max(0.0, hours - STANDARD_HOURS)
    overtime_pay = overtime_hours * hourly_rate * OVERTIME_MULTIPLIER
    gross_pay = base_pay + overtime_pay
    return round(gross_pay * TAX_RETENTION_RATE, 2)


def format_payslip_line(employee_name: str, net_pay: float) -> str:
    """Format a single employee payslip summary string."""
    return f"{employee_name}: INR {net_pay:.2f}"


def generate_payroll_report(records: list[dict[str, float]]) -> list[str]:
    """Validate records and build formatted payslip lines without performing I/O."""
    payslips: list[str] = []
    for record in records:
        validate_payroll_record(record)
        net_pay = calculate_net_pay(record["hours"], record["rate"])
        payslips.append(format_payslip_line(str(record["name"]), net_pay))
    return payslips
```

## 3. Expressive Naming and Eliminating Magic Values

### 1. Naming Functions by Action and Intent
Functions perform actions or compute values—name them with clear **verb-noun phrases** that describe *what* they do, not *how* they do it internally:

| Weak / Vague Name | Clear, Intent-Revealing Name | Why It Is Better |
| :--- | :--- | :--- |
| `process_data(items)` | `filter_expired_subscriptions(items)` | States the exact filtering criterion |
| `handle_user(u)` | `deactivate_inactive_account(user)` | Specifies the state transition performed |
| `check(order)` | `is_eligible_for_free_shipping(order)` | `is_` prefix signals a `bool` return value |
| `get_info(id)` | `fetch_order_summary_by_id(order_id)` | Clarifies lookup source and returned structure |

### 2. Replacing Magic Numbers and Strings with Named Constants
Unexplained literal values (`86400`, `0.18`, `"A"`) force readers to guess their business meaning. Promote domain constants to `UPPER_SNAKE_CASE` variables:

```python
SECONDS_PER_DAY = 86_400
MAX_LOGIN_ATTEMPTS = 5
GST_RATE = 0.18


def is_session_expired(elapsed_seconds: int) -> bool:
    return elapsed_seconds > SECONDS_PER_DAY
```

## 4. Designing Clean Function Signatures

### 1. Keep Parameter Lists Small
* Aim for **0 to 3 parameters** per function.
* When multiple parameters always travel together (such as `host`, `port`, `username`, `timeout`), group them into a **`@dataclass`** or structured object rather than passing 6+ loose arguments.

```python
from dataclasses import dataclass


@dataclass(frozen=True)
class PaginationParams:
    page: int = 1
    page_size: int = 25
    sort_by: str = "created_at"


def list_trainees(track: str, pagination: PaginationParams) -> list[str]:
    offset = (pagination.page - 1) * pagination.page_size
    return [f"{track}: offset={offset}, limit={pagination.page_size}"]
```

### 2. Avoid Boolean Flag Parameters
Passing a boolean flag (`render_report(data, as_csv=True)`) usually indicates that the function actually performs **two different behaviors**. Split it into two explicit functions (or use an `Enum` when multiple formats exist):

```python
# Avoid: Caller must look up what `True` means at the call site
# export_users(users, True)

# Prefer: Explicit, self-documenting function names
def export_users_as_csv(users: list[dict[str, str]]) -> str: ...
def export_users_as_json(users: list[dict[str, str]]) -> str: ...
```

### 3. Enforce Keyword-Only Arguments (`*`) for Optional Flags
Placing `*` in a parameter list forces callers to pass subsequent arguments by keyword, preventing accidental positional swaps:

```python
def schedule_backup(
    database_name: str,
    *,
    compress: bool = True,
    verify_checksum: bool = True,
    retention_days: int = 30,
) -> None:
    """Schedule a database backup with explicit keyword-only options."""
    pass


# Call site is unambiguous and self-documenting:
schedule_backup("orders_prod", compress=True, retention_days=14)
```

### 4. Use Type Hints and Concise Docstrings
Combine PEP 484 type annotations with a clear docstring explaining preconditions, return values, and exceptions:

```python
def calculate_compound_interest(
    principal: float,
    annual_rate: float,
    years: int,
    compounds_per_year: int = 12,
) -> float:
    """Return final balance after compounding interest over a given number of years.

    Args:
        principal: Initial deposit amount (must be non-negative).
        annual_rate: Annual interest rate as a decimal (e.g., 0.07 for 7%).
        years: Investment duration in whole years (must be >= 0).
        compounds_per_year: Compounding frequency per year (defaults to monthly).

    Raises:
        ValueError: If principal, annual_rate, or years is negative.
    """
    if principal < 0 or annual_rate < 0 or years < 0:
        raise ValueError("Principal, rate, and years must be non-negative")
    return round(principal * (1 + annual_rate / compounds_per_year) ** (compounds_per_year * years), 2)
```

## 5. Reducing Nesting and Cognitive Complexity

### 1. Use Guard Clauses (Early Returns) Instead of Deep `if/else` Nesting
Deeply nested conditionals ("arrow code") force readers to track multiple active conditions simultaneously. Handle invalid states and edge cases at the top of the function and return or raise early:

```python
# BEFORE: Deeply nested conditionals obscure the primary logic
def approve_loan_nested(applicant: dict[str, object]) -> str:
    if applicant.get("is_verified"):
        if applicant.get("credit_score", 0) >= 700:
            if applicant.get("annual_income", 0) >= 500_000:
                return "APPROVED"
            else:
                return "REJECTED: Insufficient income"
        else:
            return "REJECTED: Low credit score"
    else:
        return "REJECTED: Unverified identity"


# AFTER: Flat guard clauses keep the happy path at the left margin
def approve_loan(applicant: dict[str, object]) -> str:
    if not applicant.get("is_verified"):
        return "REJECTED: Unverified identity"
    if int(applicant.get("credit_score", 0)) < 700:
        return "REJECTED: Low credit score"
    if float(applicant.get("annual_income", 0)) < 500_000:
        return "REJECTED: Insufficient income"

    return "APPROVED"
```

### 2. Extract Complex Boolean Expressions into Predicate Functions
When an `if` condition combines three or more logical checks, extract it into a descriptive helper function:

```python
def can_access_admin_panel(user: dict[str, object]) -> bool:
    return (
        bool(user.get("is_active"))
        and bool(user.get("mfa_enabled"))
        and user.get("role") in {"admin", "superadmin"}
    )
```

### 3. Prefer Idiomatic Python Constructs Over Manual Loops
```python
scores = [88, 92, 79, 95]

# Idiomatic: declarative, concise, and immediately clear
all_passed = all(score >= 60 for score in scores)
any_distinction = any(score >= 90 for score in scores)
```

## 6. Pure Functions, Side Effects, and Command-Query Separation

### 1. Pure Functions vs. Impure Functions
* **Pure Function:** Given the same inputs, always returns the exact same output and causes **zero observable side effects** (no mutating caller arguments, modifying global variables, reading files, or making network calls).
* **Why Pure Functions Matter:** They are trivial to unit test (no mocks required), safe to parallelize, and easy to cache (`@functools.lru_cache`).

### 2. Command-Query Separation (CQS)
Design functions to fall cleanly into one of two categories:
* **Queries:** Compute and return a value **without mutating external state** (e.g., `calculate_total(items)`).
* **Commands:** Perform a state mutation or I/O action and return **`None`** (e.g., `save_order_to_db(order)`).

*(Following CQS prevents surprises such as a `get_next_item()` function silently deleting records from a database while appearing to be a read-only lookup.)*

### 3. Functional Core, Imperative Shell
Push I/O operations (reading CSVs, querying databases, calling HTTP APIs, logging) to the outer boundary of your program, while keeping core business logic in pure functions that accept and return plain data structures.

## 7. Common Pitfalls and Best Practices

1. **Returning Inconsistent Types:**
   Avoid functions that return a `dict` on success, `False` when not found, and an error `str` on invalid input. Return a consistent type (such as `User | None`) and raise descriptive exceptions for invalid states.
2. **Silently Mutating Caller Arguments:**
   If a function takes `items: list[str]`, do not call `items.sort()` or `items.append(...)` in place unless the function's name explicitly signals mutation (e.g., `sort_items_in_place(items)`). Otherwise, return a new sorted list (`sorted(items)`).
3. **Writing Comments That Restate Code Instead of Explaining Intent:**
   Avoid `# Increment counter by 1` above `counter += 1`. Write comments only to explain **why** a non-obvious constraint, workaround, or business rule exists.
4. **Over-Engineering Tiny Scripts (Premature Abstraction):**
   Splitting a 15-line linear transformation into 8 single-line functions scattered across multiple files hurts readability rather than helping it. Extract helpers when a block has a distinct domain meaning, reduces nesting, or eliminates genuine duplication.
5. **Catching and Swallowing Exceptions Silently (`except Exception: pass`):**
   Hiding errors inside helper functions makes failures impossible to diagnose. Let exceptions propagate naturally or wrap them in domain-specific exceptions with context.

## 8. Quick Reference

| Guideline | Recommended Practice | Anti-Pattern to Avoid |
| :--- | :--- | :--- |
| **Responsibility** | One clear task per function at a single abstraction level | 150-line functions mixing I/O, parsing, and business math |
| **Function Naming** | Descriptive verb-noun phrases (`calculate_tax`, `is_valid`) | Vague names (`process`, `do_stuff`, `handle`) |
| **Parameters** | 0–3 parameters; group related fields into `@dataclass`; use `*` for flags | 6+ positional arguments or obscure boolean flags |
| **Control Flow** | Flat guard clauses (`if invalid: return`) at top of function | Deeply nested `if/else` blocks (3+ indentation levels) |
| **Constants** | `UPPER_SNAKE_CASE` named constants (`MAX_RETRIES = 3`) | Unexplained magic numbers/strings inline |
| **Side Effects** | Separate pure calculations (queries) from I/O/mutations (commands) | Functions that silently mutate input lists or globals |
| **Return Types** | Consistent return type + exceptions on error | Mixed return types (`dict | bool | str`) |
