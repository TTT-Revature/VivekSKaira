# Concurrency vs. Parallelism in Python

## 1. Overview
**Concurrency** and **parallelism** are related but distinct concepts for structuring and executing programs that handle multiple tasks:

* **Concurrency (Dealing with many things at once):**
  A program is concurrent if multiple tasks make progress over overlapping time periods by interleaving their execution. Concurrency is about **program structure** and works even on a **single CPU core** through rapid context switching or cooperative yielding.
* **Parallelism (Doing many things at once):**
  A program is parallel if multiple tasks execute **simultaneously at the exact same instant** on separate physical execution units (multiple CPU cores, processors, or machines). Parallelism is about **hardware execution**.

* **Key Relationship:**
  Concurrency can exist without parallelism (e.g., an `asyncio` event loop multiplexing 1,000 network sockets on one core), and parallelism is a specialized form of concurrent execution when multi-core hardware is available.

---

## 2. Core Conceptual Differences

| Dimension | Concurrency | Parallelism |
| :--- | :--- | :--- |
| **Core Idea** | Overlapping progress of multiple tasks (task composition) | Simultaneous execution of multiple tasks (hardware throughput) |
| **Hardware Requirement** | Works on a **single CPU core** (and scales across multiple cores) | Strictly requires **multiple CPU cores** or processors |
| **Execution Mechanism** | Time-slicing (preemptive OS switching) or cooperative yielding (`await`) | Independent instruction streams running simultaneously on separate cores |
| **Primary Goal** | Minimize idle waiting time, keep applications responsive, handle high I/O volume | Maximize raw computational speed and reduce total wall-clock runtime |
| **Ideal Workload** | **I/O-bound** tasks (HTTP requests, database queries, file reads, sockets) | **CPU-bound** tasks (matrix math, image processing, compression, parsing) |
| **Primary Python Tools** | `asyncio`, `threading`, `concurrent.futures.ThreadPoolExecutor` | `multiprocessing`, `concurrent.futures.ProcessPoolExecutor` |

---

## 3. Workload Types: I/O-Bound vs. CPU-Bound
Choosing between concurrency and parallelism depends first on identifying what limits your program's speed:

### 1. I/O-Bound Workloads
* **Characteristics:** The CPU spends most of its time **waiting** for external subsystems (network latency, disk read/write, database responses, user input).
* **Best Solution:** **Concurrency** (`asyncio` or `threading`). While one task waits for a network packet, another task uses the CPU to prepare or parse its own request.

### 2. CPU-Bound Workloads
* **Characteristics:** The program spends almost all of its time performing **active computation** in registers and cache (cryptographic hashing, numerical simulations, video encoding, heavy JSON/XML parsing) with minimal waiting.
* **Best Solution:** **Parallelism** (`multiprocessing` / `ProcessPoolExecutor`). Adding threads on a single core adds context-switching overhead without speeding up math; splitting work across $N$ physical CPU cores can approach an $N\times$ speedup.

## 4. The Global Interpreter Lock (GIL) and Free-Threaded Python
Understanding how CPython manages threads is essential when choosing between threads and processes:

* **What the GIL Does:**
  In standard CPython builds, the **Global Interpreter Lock (GIL)** is a mutex that allows **only one thread to execute Python bytecode at a time** within a single process, protecting internal memory management and reference counts.
* **Why Threads Still Help I/O-Bound Code:**
  CPython automatically **releases the GIL** whenever a thread performs blocking I/O operations (socket reads/writes, file I/O, `time.sleep()`) or calls C extensions that explicitly release it (such as NumPy array operations).
* **Why Standard Threads Do Not Parallelize Pure-Python CPU Work:**
  Because two threads cannot execute Python bytecode simultaneously under the GIL, multithreaded CPU-bound Python code runs sequentially on one core (often slightly slower due to lock contention).
* **Free-Threaded Python (`--disable-gil`):**
  Introduced experimentally in Python 3.13 (PEP 703) and officially supported as an optional build variant in Python 3.14+ (PEP 779, e.g., `python3.14t`), CPython offers a **free-threaded build** with the GIL disabled (`sys._is_gil_enabled() == False`), enabling true multi-core CPU parallelism using standard `threading`. Standard default Python builds still ship with the GIL enabled.

## 5. Python's Three Execution Models in Practice

### 1. Asynchronous Concurrency (`asyncio`) — Single Thread, Cooperative
**`asyncio`** runs a single-threaded **event loop**. Tasks voluntarily yield control using **`await`** whenever they wait on I/O, allowing thousands of lightweight coroutines to run concurrently with minimal memory overhead.

```python
import asyncio
import time


async def fetch_service_status(service_name: str, delay: float) -> str:
    """Simulate a non-blocking network request."""
    await asyncio.sleep(delay)  # Yields control back to the event loop
    return f"{service_name}: OK ({delay}s)"


async def main() -> None:
    start = time.perf_counter()

    # Schedule three I/O tasks concurrently on a single thread
    results = await asyncio.gather(
        fetch_service_status("auth-api", 1.0),
        fetch_service_status("billing-api", 1.0),
        fetch_service_status("inventory-api", 1.0),
    )

    elapsed = time.perf_counter() - start
    print(results)
    print(f"Total elapsed: {elapsed:.2f}s (instead of 3.00s sequentially)")


if __name__ == "__main__":
    asyncio.run(main())
```

### 2. Multithreading (`ThreadPoolExecutor`) — Multiple Threads, Preemptive
**Threads** share the same process memory space and are scheduled preemptively by the operating system. `ThreadPoolExecutor` is ideal for concurrent I/O when using synchronous libraries (such as standard file I/O, `sqlite3`, or blocking HTTP clients).

```python
from concurrent.futures import ThreadPoolExecutor
import time


def download_file(file_id: int) -> str:
    """Simulate a blocking I/O download that releases the GIL."""
    time.sleep(0.5)
    return f"file_{file_id}.csv downloaded"


def run_threaded_downloads() -> None:
    start = time.perf_counter()
    file_ids = [1, 2, 3, 4]

    with ThreadPoolExecutor(max_workers=4) as executor:
        results = list(executor.map(download_file, file_ids))

    elapsed = time.perf_counter() - start
    print(results)
    print(f"Total elapsed: {elapsed:.2f}s (instead of 2.00s sequentially)")


if __name__ == "__main__":
    run_threaded_downloads()
```

### 3. Multiprocessing (`ProcessPoolExecutor`) — Multiple Processes, True Parallelism
**Processes** each have their own independent Python interpreter, memory space, and GIL, allowing true simultaneous execution across multiple CPU cores.

```python
from concurrent.futures import ProcessPoolExecutor
import os
import time


def sum_of_squares(limit: int) -> tuple[int, int]:
    """CPU-intensive pure-Python calculation."""
    total = sum(i * i for i in range(limit))
    return os.getpid(), total


def run_parallel_computation() -> None:
    start = time.perf_counter()
    workloads = [15_000_000, 15_000_000, 15_000_000, 15_000_000]

    with ProcessPoolExecutor() as executor:
        results = list(executor.map(sum_of_squares, workloads))

    elapsed = time.perf_counter() - start
    for pid, total in results:
        print(f"Worker PID {pid}: result={total}")
    print(f"Parallel wall-clock time: {elapsed:.2f}s")


if __name__ == "__main__":
    run_parallel_computation()
```

## 6. Choosing the Right Approach

| Scenario | Recommended Tool | Why |
| :--- | :--- | :--- |
| High-concurrency network I/O (100s–10,000s of connections, web APIs, WebSockets) | **`asyncio`** | Lowest memory footprint per task; explicit `await` boundaries prevent thread race conditions |
| Moderate I/O concurrency using blocking/legacy libraries (`requests`, `boto3`, disk I/O) | **`ThreadPoolExecutor`** | Works with existing synchronous functions without rewriting into `async/await` |
| Heavy CPU computation in pure Python (data transformations, simulations, parsing) | **`ProcessPoolExecutor`** | Bypasses the GIL by running separate processes across physical CPU cores |
| Heavy numerical computation using NumPy / PyTorch / SciPy C-extensions | **`ThreadPoolExecutor`** or native library parallelism | Underlying C/C++ kernels release the GIL and manage internal thread pools |

## 7. Common Pitfalls and Best Practices

1. **Blocking the `asyncio` Event Loop with Synchronous Calls:**
   Calling `time.sleep(5)` or `requests.get(url)` inside an `async def` function freezes the entire event loop so **no other coroutine can make progress**. Always use non-blocking equivalents (`await asyncio.sleep(5)`, `httpx.AsyncClient`, `aiohttp`) or offload blocking functions via `await asyncio.to_thread(blocking_fn, arg)`.
2. **Unsynchronized Shared State in Multithreaded Code (Race Conditions):**
   Even with the GIL enabled, compound read-modify-write operations like `counter += 1` or checking-then-updating a dictionary are **not atomic** across bytecode instructions. Always protect shared mutable state with **`threading.Lock()`** or pass messages via **`queue.Queue`**.
3. **Omitting `if __name__ == "__main__":` When Using `multiprocessing`:**
   On Windows and macOS, Python spawns new worker processes by importing the main module. Without an `if __name__ == "__main__":` guard around `ProcessPoolExecutor` or `Process.start()`, each child process recursively spawns more processes until the system crashes (`RuntimeError`).
4. **Using `ProcessPoolExecutor` for Tiny, Fast Tasks:**
   Spawning processes and serializing (`pickle`) arguments and return values across process boundaries incurs noticeable overhead. If each task takes less than a few milliseconds, process communication overhead exceeds the parallel speedup—batch small items into larger chunks (`chunksize=...`).
5. **Spawning Unbounded Threads or Processes:**
   Creating 10,000 OS threads exhausts RAM and degrades throughput through context-switching thrashing. Always bound concurrency using a pool (`ThreadPoolExecutor(max_workers=...)`) or an `asyncio.Semaphore(limit)`.

## 8. Quick Reference

| Model / Module | Unit of Execution | Memory Model | Bypasses GIL? | Best Fit |
| :--- | :--- | :--- | :--- | :--- |
| **`asyncio`** | Coroutine (`async def` / `await`) | Single thread, shared memory | No (cooperative single-thread) | High-scale non-blocking network I/O |
| **`threading`** / `ThreadPoolExecutor` | OS Thread | Shared process memory | Only during I/O / C extensions (or in free-threaded `3.14t+`) | Blocking I/O libraries and GUI responsiveness |
| **`multiprocessing`** / `ProcessPoolExecutor` | OS Process | Isolated memory per process (IPC via `pickle` / shared memory) | **Yes** (separate interpreter per core) | CPU-bound pure-Python computations |
