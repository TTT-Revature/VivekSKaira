# PEP 8 and Naming Conventions in Python

## 1. Overview
**PEP 8** (*Python Enhancement Proposal 8*), originally authored by Guido van Rossum, Barry Warsaw, and Nick Coghlan, is the official **Style Guide for Python Code**. Its primary goal is to maximize code readability and maintain visual consistency across Python projects and teams.

* **Core Philosophy ("Readability Counts"):**
  Code is read far more often than it is written. Consistent formatting, spacing, and naming allow developers to understand unfamiliar modules quickly without mental friction.
* **When to Break a Rule ("Foolish Consistency"):**
  PEP 8 explicitly notes that consistency within a project or module matters more than rigid adherence to every rule—especially when:
  1. Applying a rule makes the code harder to read (even for someone accustomed to PEP 8).
  2. Surrounding legacy code uses a different style (avoid noisy formatting diffs unless refactoring the file).
  3. Maintaining backward compatibility with existing public APIs requires preserving legacy names.

## 2. Code Layout and Indentation

### 1. Indentation (4 Spaces)
* Use **4 spaces per indentation level**.
* Never mix tabs and spaces in the same file (Python 3 raises `TabError` when indentation mixes tabs and spaces inconsistently). Spaces are the strongly preferred indentation method.

### 2. Maximum Line Length
* **Code lines:** Limit all lines to a maximum of **79 characters** (many modern teams configure formatters to 88 or 100 characters, while keeping PEP 8's 79-character limit as the standard baseline for open-source libraries).
* **Docstrings and comments:** Limit flowing text blocks to **72 characters** for comfortable reading in split-pane editors and terminals.

### 3. Line Continuation and Multiline Alignment
Python implicitly joins lines inside parentheses `(...)`, brackets `[...]`, and braces `{...}`—prefer implicit continuation over backslashes (`\`).

```python
# 1. Aligned with opening delimiter
result = compute_weighted_score(
    assignment_score, exam_score,
    attendance_bonus, penalty_points,
)

# 2. Hanging indent (4 extra spaces; add extra indentation to distinguish arguments from body)
def register_trainee(
        full_name: str,
        email_address: str,
        track_name: str,
        batch_code: str) -> dict[str, str]:
    return {
        "name": full_name,
        "email": email_address,
        "track": track_name,
        "batch": batch_code,
    }
```

### 4. Line Breaks Around Binary Operators
Place line breaks **before** binary operators (Knuth's style) so each operator aligns vertically with its operand, making formulas easy to scan:

```python
# Recommended: operator appears at the start of each continued line
gross_pay = (
    base_salary
    + overtime_hours * overtime_rate
    - tax_deduction
    - insurance_premium
)
```

### 5. Blank Lines
* **2 blank lines** surrounding top-level function and class definitions.
* **1 blank line** between method definitions inside a class.
* Use single blank lines sparingly inside functions to separate logical sections.

## 3. Whitespace Rules in Expressions and Statements

### Where to Avoid Extraneous Whitespace
```python
# Correct
items = [1, 2, 3]
mapping = {"key": "value"}
value = items[1]
result = calculate(x, y=10)

# Incorrect (extra spaces inside brackets, before commas/colons, or before call parens)
# items = [ 1, 2, 3 ]
# mapping = { "key" : "value" }
# value = items [1]
# result = calculate (x, y = 10)
```

### Operator Spacing Rules
* **Binary Operators:** Surround assignment (`=`), augmented assignment (`+=`, `-=`), comparisons (`==`, `<`, `!=`, `is`, `in`), and boolean operators (`and`, `or`, `not`) with a **single space on both sides**.
* **Operator Precedence Grouping:** When mixing operators with different priorities, optionally omit spaces around the highest-precedence operator (`*`, `/`, `**`) to clarify grouping: `hypotenuse = x*x + y*y`.
* **Default Parameter Values:**
  * **Without type annotations:** Do **not** put spaces around `=` (`def connect(timeout=30):`).
  * **With type annotations:** Put a single space on both sides of `=` (`def connect(timeout: int = 30) -> None:`).
* **Slice Colons:** Treat the colon in slices like a binary operator with equal spacing on both sides (`data[1:5]`, `data[start + 1 : end - 1]`).

## 4. Imports Organization
Imports should always be placed at the **top of the file**, immediately after any module comments and docstrings, and before module globals and constants.

### Grouping and Ordering Rules
Group imports into **three distinct sections**, separated by a single blank line (alphabetical within each group):
1. **Standard library imports** (`os`, `sys`, `pathlib`, `typing`)
2. **Related third-party imports** (`pytest`, `requests`, `pydantic`)
3. **Local application / library-specific imports** (`from fde_app.models import User`)

```python
"""Order validation and reporting service."""

from datetime import datetime, timezone
import json
from pathlib import Path

import pytest
import requests

from order_service.config import API_TIMEOUT
from order_service.models import Order
```

* Put separate modules on **separate lines** (`import os` and `import sys` on two lines, not `import os, sys`).
* Importing multiple symbols from the same module on one line is acceptable: `from pathlib import Path, PurePath`.
* Avoid wildcard imports (`from module import *`), as they pollute the namespace and obscure where names originate.

## 5. Naming Conventions
Consistent identifier naming conveys what an object represents (a class, constant, function, or private helper) at a glance.

### Summary Table of Python Naming Styles

| Identifier Type | Convention | Valid Examples | Avoid |
| :--- | :--- | :--- | :--- |
| **Modules** | `snake_case` (short, all-lowercase) | `file_utils.py`, `auth.py` | `FileUtils.py`, `file-utils.py` |
| **Packages** | `lowercase` (short, prefer no underscores) | `analytics`, `datamodels` | `DataModels`, `data_models_pkg` |
| **Classes** | `CapWords` (PascalCase) | `UserProfile`, `HttpClient` | `user_profile`, `HTTP_Client` |
| **Exceptions** | `CapWords` + `Error` suffix (if error) | `ValidationError`, `TimeoutError` | `validation_error`, `InvalidInput` |
| **Functions** | `snake_case` (verb or action phrase) | `calculate_tax()`, `parse_csv()` | `CalculateTax()`, `calcTax()` |
| **Variables** | `snake_case` | `total_count`, `user_email` | `totalCount`, `TotalCount` |
| **Constants** | `UPPER_SNAKE_CASE` (module level) | `MAX_RETRIES = 3`, `DEFAULT_PORT = 8080` | `maxRetries`, `default_port` |
| **Methods & Instance Vars** | `snake_case` | `def get_balance(self):`, `self.is_active` | `def getBalance(self):` |
| **Method First Argument** | `self` (instance) / `cls` (class) | `def save(self):`, `def create(cls):` | `def save(this):` |
| **Type Variables** | `CapWords` (short) | `T`, `KeyT`, `ValueT`, `AnyStr` | `t`, `type_var` |

### Leading and Trailing Underscore Conventions

| Pattern | Example | Meaning & Interpreter Behavior |
| :--- | :--- | :--- |
| `_single_leading` | `_parse_header()` | **Internal / Non-public indicator:** Signals "internal use only" by convention; excluded from `from module import *`. |
| `single_trailing_` | `class_`, `type_` | **Keyword collision avoidance:** Prevents clashing with Python reserved keywords (`class`, `id`, `type`, `from`). |
| `__double_leading` | `__secret_key` | **Name mangling (inside classes):** Python rewrites `__secret_key` to `_ClassName__secret_key` to prevent accidental subclass overrides. |
| `__double_both__` | `__init__`, `__str__` | **"Dunder" (magic) attributes:** Reserved exclusively for Python's data model; never invent custom `__name__` identifiers. |
| `_` (single underscore) | `for _ in range(5):` | **Throwaway variable:** Indicates a value or unpacked element is intentionally unused. |

*(Characters to Avoid: Never use single-letter variable names `'l'` (lowercase L), `'O'` (uppercase O), or `'I'` (uppercase I), because in many fonts they are indistinguishable from the digits `1` and `0`.)*

## 6. Comments, Docstrings, and String Quotes

### 1. Comments
* Write comments as complete sentences with the first word capitalized.
* **Block comments:** Indent to the same level as the code they describe, starting each line with `# ` (hash followed by a single space).
* **Inline comments:** Separate from the statement by **at least two spaces**, start with `# `, and use sparingly only when explaining *why* something non-obvious is done rather than restating *what* the code already says.

```python
# Retry transient network errors up to 3 times before propagating failure
max_attempts = 3  # Includes the initial request attempt
```

### 2. Docstrings (PEP 257)
* Write docstrings for all public modules, functions, classes, and methods using **triple double quotes (`"""..."""`)**.
* **One-line docstrings:** Keep opening and closing `"""` on the same line.
* **Multi-line docstrings:** Place a one-line summary first, followed by a blank line, detailed description, and closing `"""` on its own line.

```python
def normalize_email(raw_email: str) -> str:
    """Return a trimmed, lowercase version of raw_email."""
    return raw_email.strip().lower()
```

### 3. String Quotes
PEP 8 does not mandate single (`'...'`) versus double (`"..."`) quotes—**pick one convention and apply it consistently across the project** (modern formatters like `ruff format` and `black` standardize on double quotes `"`). Always use triple double quotes `"""` for docstrings.

## 7. Programming Recommendations (Idiomatic PEP 8)
PEP 8 includes practical idioms that prevent subtle bugs and make intent explicit:

```python
# 1. Singleton comparisons: ALWAYS use 'is' or 'is not' (never '==')
if user is None:
    pass
if token is not None:
    pass

# 2. Negated identity: write 'x is not y' rather than 'not x is y'
if status is not None:
    pass

# 3. Sequence / collection emptiness: rely on truthiness instead of len() == 0
pending_tasks: list[str] = []
if not pending_tasks:
    print("Queue is empty")

# 4. Type checking: use isinstance() instead of comparing type() directly
if isinstance(value, str):
    print(value.upper())

# 5. Naming functions: use 'def' instead of binding a lambda to a variable
def double(x: int) -> int:
    return x * 2
# Avoid: double = lambda x: x * 2

# 6. Prefix / suffix checks: use .startswith() / .endswith() instead of slicing
filename = "report_2026.csv"
if filename.endswith(".csv"):
    pass

# 7. Exception handling: catch specific exceptions, never bare 'except:'
try:
    count = int(raw_input)
except ValueError:
    count = 0
```

## 8. Automating PEP 8 Checks and Formatting
Rather than checking style rules manually during code reviews, modern Python projects enforce PEP 8 automatically using linters and formatters configured in **`pyproject.toml`**:

* **`ruff`:** Ultra-fast Rust-based linter and PEP 8 formatter (`ruff check .` and `ruff format .`).
* **`flake8`:** Classic PEP 8 style checker (`pycodestyle` + `pyflakes`).
* **`black`:** Opinionated automated code formatter that enforces consistent layout.

```toml
# File: pyproject.toml
[tool.ruff]
line-length = 88
target-version = "py311"

[tool.ruff.lint]
select = [
    "E",   # pycodestyle errors (PEP 8)
    "W",   # pycodestyle warnings (PEP 8)
    "F",   # pyflakes unused imports/variables
    "I",   # isort import sorting
    "N",   # pep8-naming conventions
]
```

## 9. Common Pitfalls and Best Practices

1. **Using `== None` or `== True` Instead of `is None` / Truthiness:**
   Custom classes can override `__eq__` and return unexpected values when compared with `== None`. Always check singletons with `if obj is None:` and booleans with `if is_valid:`.
2. **Using `camelCase` for Python Functions and Variables:**
   Developers coming from Java, JavaScript, or C# often write `calculateTotal()` or `userName`. Use `snake_case` (`calculate_total()`, `user_name`) for all Python functions, methods, and variables, reserving `CapWords` strictly for classes and exceptions.
3. **Writing Bare `except:` Clauses:**
   A bare `except:` catches `SystemExit`, `KeyboardInterrupt` (`Ctrl+C`), and `MemoryError`, hiding genuine bugs and making scripts impossible to interrupt cleanly. Always specify the expected exception class (e.g., `except ValueError:` or `except OSError:`).
4. **Creating Custom `__dunder__` Attributes:**
   Names like `__my_metadata__` are reserved for Python's internal language protocol and may collide with future Python releases. Use a single leading underscore (`_my_metadata`) for internal attributes.
5. **Mixing Reformatting Changes with Feature Logic in One Git Commit:**
   When cleaning up PEP 8 formatting in an existing file, commit formatting changes separately from functional bug fixes or feature additions so `git diff` history stays clear and reviewable.

## 10. Quick Reference

| Rule / Category | PEP 8 Standard |
| :--- | :--- |
| **Indentation** | 4 spaces per level; never mix tabs and spaces |
| **Max Line Length** | 79 characters for code; 72 characters for docstrings and comments |
| **Blank Lines** | 2 around top-level functions/classes; 1 between methods in a class |
| **Imports Order** | 1. Standard library -> 2. Third-party -> 3. Local (alphabetical, 1 per line) |
| **Variables & Functions** | `snake_case` (`user_id`, `fetch_records()`) |
| **Classes & Exceptions** | `CapWords` (`OrderService`, `InvalidOrderError`) |
| **Constants** | `UPPER_SNAKE_CASE` (`MAX_CONNECTIONS = 10`) |
| **Non-Public / Internal** | `_single_leading_underscore` (`_helper_fn`) |
| **Singleton Checks** | `if x is None:` / `if x is not None:` |
| **Empty Collection Check** | `if not items:` / `if items:` (avoid `len(items) == 0`) |
