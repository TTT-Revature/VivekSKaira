# Race Conditions and Shared Data in Python

## 1. Overview
When multiple threads, coroutines, or processes access the same mutable state concurrently, uncoordinated reads and writes can corrupt data or produce unpredictable outcomes.

* **Shared Data:**
  Any mutable object, variable, collection, file, or database record accessible by two or more concurrent units of execution (such as threads sharing a process heap or coroutines sharing module/instance state).
* **Race Condition:**
  A concurrency defect in which the observable behavior or final state of a program depends on the **non-deterministic timing or interleaving** of execution steps across concurrent workers.
* **Data Race vs. Race Condition:**
  * **Data Race:** Occurs when two or more threads access the same memory location concurrently without synchronization, and at least one access is a write.
  * **Logical Race Condition:** Occurs even when individual reads and writes are atomic, because a multi-step business invariant (such as checking an account balance before withdrawing) is interrupted mid-sequence by another worker.

## 2. Common Types of Race Conditions

### 1. Read-Modify-Write (Lost Update)
A **read-modify-write** race happens when two workers read the same initial value, compute an updated value independently, and write their results back—causing the second write to overwrite the first.

```python
import threading
import time

total_hits = 0


def record_hits(iterations: int) -> None:
    """Increment a shared global counter without synchronization."""
    global total_hits
    for _ in range(iterations):
        # 1. Read current value
        current = total_hits
        # Yield execution briefly to expose thread interleaving
        time.sleep(0)
        # 2. Modify and 3. Write back
        total_hits = current + 1


threads = [threading.Thread(target=record_hits, args=(1_000,)) for _ in range(4)]
for t in threads:
    t.start()
for t in threads:
    t.join()

# Expected: 4000; Actual: significantly lower due to overwritten increments
print(f"Expected hits: 4000 | Actual hits: {total_hits}")
```

### 2. Check-Then-Act (Time-of-Check to Time-of-Use)
A **check-then-act** race occurs when a worker verifies a precondition (`if stock > 0:`) and then performs an action (`stock -= 1`), but another worker alters the shared state in the gap between the check and the action.

```python
import threading
import time


class UnsafeInventory:
    def __init__(self, initial_stock: int) -> None:
        self.stock = initial_stock

    def purchase_one(self, buyer: str) -> bool:
        # CHECK: Both threads may see stock == 1 at the same time
        if self.stock >= 1:
            time.sleep(0.01)  # Simulated processing delay
            # ACT: Both threads decrement, driving stock negative (-1)
            self.stock -= 1
            print(f"{buyer} purchased item (remaining stock: {self.stock})")
            return True
        return False


inventory = UnsafeInventory(initial_stock=1)
t1 = threading.Thread(target=inventory.purchase_one, args=("Buyer-A",))
t2 = threading.Thread(target=inventory.purchase_one, args=("Buyer-B",))

t1.start()
t2.start()
t1.join()
t2.join()
```

## 3. Why Race Conditions Happen Despite the GIL
A common misconception is that CPython's **Global Interpreter Lock (GIL)** makes multithreaded Python code automatically thread-safe.

1. **Bytecode Interleaving:**
   The GIL ensures only one thread executes a single Python bytecode instruction at a time, **not** an entire Python statement or function. A seemingly simple statement like `self.balance += amount` compiles into multiple bytecode instructions (`LOAD_ATTR`, `LOAD_FAST`, `BINARY_OP`, `STORE_ATTR`). The interpreter can switch threads between any two instructions.
2. **Compound Operations Are Never Atomic:**
   Operations such as `count += 1`, `items[key] = items.get(key, 0) + 1`, or checking `if key not in cache:` before inserting span multiple steps and are never atomic.
3. **Free-Threaded Python (`--disable-gil`):**
   In free-threaded CPython builds (PEP 703 / PEP 779, such as `python3.14t`), the GIL can be disabled at runtime, allowing threads to mutate objects on separate CPU cores simultaneously. Explicit synchronization is mandatory in both GIL-enabled and free-threaded builds.

## 4. Strategies for Protecting Shared Data

### 1. Avoid Sharing Mutable State (Confinement and Immutability)
The safest shared state is **no shared mutable state**:
* **Local Variables:** Keep intermediate data confined inside function local scopes.
* **Immutable Data Structures:** Share read-only objects (`tuple`, `frozenset`, `str`, `bytes`, or `@dataclass(frozen=True)`) so concurrent readers cannot corrupt state.
* **Thread-Local Storage (`threading.local()`):** Give each thread its own isolated copy of contextual attributes (such as per-thread database sessions or request IDs).

### 2. Mutual Exclusion with `threading.Lock` (Critical Sections)
Wrap every compound read-modify-write or check-then-act sequence in a **`threading.Lock`** using a **`with` context manager** so only one thread executes the **critical section** at a time:

```python
import threading


class ThreadSafeInventory:
    def __init__(self, initial_stock: int) -> None:
        self._stock = initial_stock
        self._lock = threading.Lock()

    def purchase_one(self, buyer: str) -> bool:
        with self._lock:
            # Both CHECK and ACT happen inside the same atomic critical section
            if self._stock < 1:
                return False
            self._stock -= 1
            remaining = self._stock

        # Perform slow logging or I/O outside the lock
        print(f"{buyer} purchased item (remaining stock: {remaining})")
        return True

    @property
    def stock(self) -> int:
        with self._lock:
            return self._stock


safe_inventory = ThreadSafeInventory(initial_stock=1)
t1 = threading.Thread(target=safe_inventory.purchase_one, args=("Buyer-A",))
t2 = threading.Thread(target=safe_inventory.purchase_one, args=("Buyer-B",))

t1.start()
t2.start()
t1.join()
t2.join()
print(f"Final stock: {safe_inventory.stock}")  # Guaranteed to be 0
```

### 3. Message Passing with `queue.Queue`
Instead of having multiple threads mutate a shared list or dictionary directly, pass immutable messages through a thread-safe **`queue.Queue`**. A single dedicated consumer thread owns and updates the state, eliminating manual locking in application logic.

### 4. Protecting Shared State in `asyncio` (`asyncio.Lock`)
Even though `asyncio` runs on a single thread, **logical race conditions still occur** whenever a coroutine reads shared state, hits an `await` suspension point, and writes back after another coroutine has modified that same state:

```python
import asyncio


class AsyncWallet:
    def __init__(self, balance: int) -> None:
        self.balance = balance
        self._lock = asyncio.Lock()

    async def withdraw(self, amount: int) -> bool:
        # Without asyncio.Lock, two coroutines awaiting concurrently could both pass the check
        async with self._lock:
            if self.balance < amount:
                return False
            await asyncio.sleep(0.05)  # Simulated async DB call
            self.balance -= amount
            return True


async def main() -> None:
    wallet = AsyncWallet(balance=100)
    results = await asyncio.gather(
        wallet.withdraw(80),
        wallet.withdraw(80),
    )
    print(f"Withdrawal outcomes: {results} | Final balance: {wallet.balance}")


if __name__ == "__main__":
    asyncio.run(main())
```

## 5. Related Shared-State Concurrency Hazards

| Hazard | Description | Primary Prevention |
| :--- | :--- | :--- |
| **Race Condition** | Final outcome varies depending on execution timing across threads or tasks | Guard critical sections with `Lock`; minimize shared mutable state |
| **Data Race** | Unsynchronized concurrent memory access where at least one thread writes | Synchronize all shared reads/writes or use thread-safe queues |
| **Deadlock** | Two or more threads block forever waiting for locks held by each other | Acquire multiple locks in a consistent global order; use lock timeouts |
| **Livelock** | Threads remain active and repeatedly change state in response to each other without making progress | Introduce randomized backoff delays before retrying |
| **Starvation** | A thread is perpetually denied access to a lock or CPU time because other threads monopolize it | Keep critical sections short; avoid unfair busy-waiting loops |

## 6. Common Pitfalls and Best Practices

1. **Locking Individual Getters/Setters Instead of the Whole Transaction:**
   Having thread-safe `get_balance()` and `set_balance()` methods does **not** make `set_balance(get_balance() - 50)` thread-safe. The lock must span the **entire read-check-modify-write sequence**.
2. **Mutating a Shared Dictionary or List While Iterating Over It:**
   If Thread A iterates over `for k, v in shared_dict.items():` while Thread B inserts or deletes a key, Python raises **`RuntimeError: dictionary changed size during iteration`**. Lock the dictionary or iterate over a copy (`list(shared_dict.items())`) inside a lock.
3. **Performing Slow Network or Disk I/O Inside a `Lock`:**
   Holding a `threading.Lock` while waiting for an HTTP request or database query forces all other threads to queue up behind it, turning concurrent code into slow sequential code. Read/update shared memory inside the lock, and execute I/O outside the lock.
4. **Using `threading.Lock` Inside `async def` Coroutines:**
   Calling a blocking `threading.Lock.acquire()` inside an `asyncio` coroutine can freeze the entire event loop (and deadlock if the lock holder awaits on that same loop). Always use **`asyncio.Lock`** in async code.
5. **Re-Acquiring a Standard `threading.Lock` in the Same Thread:**
   If a method holding `self._lock` calls another helper method on the same instance that also executes `with self._lock:`, the thread deadlocks itself permanently. Use **`threading.RLock`** when reentrant locking within the same thread is required.

## 7. Quick Reference

| Scenario / Pattern | Thread-Safe? | Recommended Fix |
| :--- | :--- | :--- |
| `counter += 1` across threads | **No** (multi-step read-modify-write) | Wrap in `with lock:` |
| `if k not in d: d[k] = val` | **No** (check-then-act race) | Wrap check + insert in `with lock:` |
| Iterating over `shared_list` while another thread appends | **No** (inconsistent iteration / skipped items) | Copy under lock (`with lock: snapshot = list(shared_list)`) |
| Sharing `@dataclass(frozen=True)` across threads | **Yes** (immutable state) | Safe to read concurrently without locks |
| Producer-consumer task handoff across threads | **Yes** (with `queue.Queue`) | Use `queue.Queue` instead of a locked `list` |
| Shared state modified across `await` in `asyncio` | **No** (coroutine interleaving at `await`) | Protect critical section with `async with asyncio.Lock():` |
