# Refactoring and Avoiding Duplicate Code in Python

## 1. Overview
**Refactoring** is the disciplined process of restructuring existing code—improving its readability, modularity, and maintainability—**without changing its external observable behavior**.

* **Why Refactoring Matters:**
  * **Reduces Maintenance Cost:** Eliminates redundant code paths so bug fixes and rule changes happen in one place instead of several.
  * **Improves Comprehension:** Breaks dense, monolithic logic into small, self-documenting units.
  * **Prevents Technical Debt:** Keeps a codebase adaptable as new requirements are added over time.
* **The Golden Rule of Refactoring:**
  Never refactor without a reliable **automated test suite**. Unit tests verify that inputs still produce the exact same outputs and exceptions after internal restructuring.

---

## 2. Principles of Code Duplication: DRY, Rule of Three, and AHA

### 1. DRY (*Don't Repeat Yourself*)
Formulated by Andy Hunt and Dave Thomas, **DRY** states: *"Every piece of knowledge must have a single, unambiguous, authoritative representation within a system."*
* **WET (*Write Everything Twice*):** The opposite of DRY—copy-pasting logic across modules. When a business rule changes (such as a tax rate or validation rule), developers inevitably update some copies and miss others, introducing silent inconsistencies.

### 2. The Rule of Three and AHA (*Avoid Hasty Abstractions*)
Not all visual similarity is true duplication:
* **Rule of Three:** The first time you write logic, write it inline. The second time you need similar logic, note the duplication. The **third time** you need it, refactor into a shared abstraction—now you have enough real examples to see which parts vary and which parts stay constant.
* **True Knowledge Duplication vs. Coincidental Similarity:** Two functions that both validate `age >= 18` (voting eligibility vs. credit card application) represent **separate domain rules** that may diverge independently later (e.g., credit cards changing to `21`). Merging unrelated domain rules creates brittle coupling.

---

## 3. Common Code Smells Signaling Refactoring Needs

| Code Smell | Symptom in Codebase | Primary Refactoring Remedy |
| :--- | :--- | :--- |
| **Duplicate Code** | Identical or near-identical blocks copied across functions or files | Extract Function / Parameterize Function |
| **Long Function** | Single function spanning 50+ lines across multiple levels of detail | Decompose into cohesive single-responsibility helpers |
| **Repetitive `if/elif` Chains** | Long branching blocks selecting behavior or values by key/type | Replace Conditional with Dictionary Dispatch |
| **Long Parameter List** | 4+ parameters repeatedly passed together across multiple functions | Introduce Parameter Object (`@dataclass`) |
| **Repeated Setup / Cleanup** | Identical `try/finally`, timing, or resource handling around calls | Extract Context Manager (`@contextmanager`) or Decorator |
| **Duplicated Class Attributes/Methods** | Multiple classes sharing identical fields and behavior | Extract Base Class, Mixin, or Composition |

## 4. Core Refactoring Techniques to Eliminate Duplication

### 1. Extract Function
Move a repeated code block into a clearly named helper function and call it from each location:

```python
# BEFORE: Duplicated normalization and validation logic in two endpoints
def register_student(email: str) -> str:
    cleaned = email.strip().lower()
    if "@" not in cleaned or "." not in cleaned.split("@")[-1]:
        raise ValueError(f"Invalid email address: {email}")
    return f"Student registered: {cleaned}"


def update_instructor_email(email: str) -> str:
    cleaned = email.strip().lower()
    if "@" not in cleaned or "." not in cleaned.split("@")[-1]:
        raise ValueError(f"Invalid email address: {email}")
    return f"Instructor updated: {cleaned}"
```

```python
# AFTER: Single authoritative normalization and validation helper
def normalize_and_validate_email(raw_email: str) -> str:
    """Return lowercase trimmed email or raise ValueError if format is invalid."""
    cleaned = raw_email.strip().lower()
    if "@" not in cleaned or "." not in cleaned.split("@")[-1]:
        raise ValueError(f"Invalid email address: {raw_email}")
    return cleaned


def register_student(email: str) -> str:
    return f"Student registered: {normalize_and_validate_email(email)}"


def update_instructor_email(email: str) -> str:
    return f"Instructor updated: {normalize_and_validate_email(email)}"
```

### 2. Parameterize Function
When two functions perform the exact same algorithm and differ only by a threshold, multiplier, or predicate function, merge them by turning the varying piece into a parameter:

```python
from collections.abc import Callable


# BEFORE: Two functions duplicating the exact same filtering loop
def get_high_scores(scores: list[int]) -> list[int]:
    return [s for s in scores if s >= 80]


def get_passing_scores(scores: list[int]) -> list[int]:
    return [s for s in scores if s >= 50]


# AFTER: Unified parameterized function (with optional predicate support)
def filter_scores_above(scores: list[int], minimum_score: int) -> list[int]:
    """Return all scores greater than or equal to minimum_score."""
    return [score for score in scores if score >= minimum_score]


def filter_scores_by(scores: list[int], predicate: Callable[[int], bool]) -> list[int]:
    """Return all scores matching an arbitrary boolean rule."""
    return [score for score in scores if predicate(score)]
```

### 3. Replace Repetitive Conditionals with Dictionary Dispatch
Long `if / elif / else` chains mapping keys to handlers or values add boilerplate and require editing control flow for every new case. Replace them with a lookup dictionary:

```python
# BEFORE: Repetitive branching logic
def calculate_shipping_bad(region: str, weight_kg: float) -> float:
    if region == "SOUTH":
        return round(50.0 + weight_kg * 10.0, 2)
    elif region == "NORTH":
        return round(70.0 + weight_kg * 12.0, 2)
    elif region == "WEST":
        return round(60.0 + weight_kg * 11.0, 2)
    else:
        raise ValueError(f"Unsupported shipping region: {region}")
```

```python
# AFTER: Data-driven rate table eliminates duplicated calculation formulas
SHIPPING_RATES: dict[str, tuple[float, float]] = {
    "SOUTH": (50.0, 10.0),
    "NORTH": (70.0, 12.0),
    "WEST": (60.0, 11.0),
}


def calculate_shipping(region: str, weight_kg: float) -> float:
    """Compute shipping cost from region base fee and per-kg rate."""
    if region not in SHIPPING_RATES:
        raise ValueError(f"Unsupported shipping region: {region}")
    base_fee, per_kg_rate = SHIPPING_RATES[region]
    return round(base_fee + weight_kg * per_kg_rate, 2)
```

### 4. Extract Shared Resource Wrappers (Context Managers & Decorators)
When cross-cutting concerns—such as execution timing, retry loops, or database transaction commits/rollbacks—are repeated across multiple functions, centralize them in a **decorator** or **context manager**:

```python
from collections.abc import Callable
from functools import wraps
import time
from typing import ParamSpec, TypeVar

P = ParamSpec("P")
R = TypeVar("R")


def log_execution_time(func: Callable[P, R]) -> Callable[P, R]:
    """Measure and print runtime of any wrapped function without duplicating timer code."""
    @wraps(func)
    def wrapper(*args: P.args, **kwargs: P.kwargs) -> R:
        start = time.perf_counter()
        result = func(*args, **kwargs)
        elapsed_ms = (time.perf_counter() - start) * 1000
        print(f"{func.__name__} completed in {elapsed_ms:.2f} ms")
        return result

    return wrapper


@log_execution_time
def generate_daily_summary() -> int:
    return sum(range(100_000))
```

### 5. Consolidate Class Duplication via Composition or Inheritance
When multiple classes share common fields or methods:
* Use **Inheritance** when a genuine *"is-a"* relationship exists (e.g., `BaseExporter` providing common file-writing and validation methods to `CsvExporter` and `JsonExporter`).
* Prefer **Composition** (*"has-a"*) when classes merely need a shared capability (e.g., injecting a `Serializer` or `Validator` helper object) without creating rigid class hierarchies.

## 5. Safe Step-by-Step Refactoring Workflow
Follow a disciplined loop so refactoring never introduces regressions:

1. **Verify Green Tests First:** Run `pytest` (or `unittest`) before touching any code. If the target module lacks unit tests, write characterization tests covering its current behavior first.
2. **Make One Small Transformation at a Time:** Extract one helper, rename one variable, or replace one conditional block per step—avoid rewriting an entire module in a single pass.
3. **Re-Run Tests Immediately:** Execute the test suite after each small edit to confirm external behavior remains unchanged.
4. **Keep Refactoring Commits Separate:** Commit structural refactoring separately from new features or bug fixes (`refactor: extract email normalization helper`) so code reviews and `git bisect` stay clean.

---

## 6. Common Pitfalls and Best Practices

1. **Refactoring Without Automated Tests:**
   Renaming variables, changing parameter defaults, or extracting helpers without unit tests frequently breaks edge cases silently. Always establish test coverage before refactoring critical logic.
2. **Over-Abstracting Coincidental Similarity (Wrong Abstraction):**
   Forcing two functions with different business purposes into a single complex function controlled by 4 boolean flags (`process(data, is_admin=True, skip_tax=False, legacy_mode=True)`) produces code harder to read and maintain than having two clean, separate functions. Duplication is cheaper than the wrong abstraction.
3. **Changing Behavior While Refactoring ("Scope Creep"):**
   If you spot an unrelated bug while refactoring, note it down and fix it in a **separate commit** after your refactoring tests pass. Mixing behavior changes with structural edits makes regressions hard to isolate.
4. **Creating Deep Inheritance Hierarchies Just to Share Two Methods:**
   Avoid 3–4 level class inheritance trees solely to reuse small helper methods. Extract stateless helpers into plain functions or compose small helper classes instead.
5. **Leaving Dead Code Behind After Refactoring:**
   Once a helper function or data structure replaces old duplicated blocks, delete the unused legacy code completely instead of leaving it commented out.

## 7. Quick Reference

| Concept / Technique | When to Use | Example / Pattern |
| :--- | :--- | :--- |
| **DRY Principle** | Same business rule or formula appears in multiple places | Single authoritative function or constant |
| **Rule of Three / AHA** | Deciding whether to abstract similar-looking code | Wait until the 3rd occurrence before generalizing |
| **Extract Function** | Identical multi-line block repeated across functions | Move block into `def helper_name(...):` |
| **Parameterize Function** | Two functions differ only by a threshold, value, or rule | Pass threshold or `Callable` predicate as parameter |
| **Dictionary Dispatch** | Repetitive `if/elif` mapping keys to values or handlers | `HANDLERS: dict[str, Callable] = {...}` |
| **Decorator / Context Manager** | Repeated timing, retries, logging, or `try/finally` cleanup | `@wraps` decorator or `@contextmanager` |
| **Composition vs. Inheritance** | Sharing behavior across multiple classes | Inject helper object (*has-a*) or subclass (*is-a*) |
| **Safe Refactoring Loop** | Modifying any existing production module | Green tests -> small edit -> run tests -> atomic commit |
