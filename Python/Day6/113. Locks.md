# Locks in Python

## 1. Overview
A **lock** (also known as a **mutex**, short for *mutual exclusion*) is a synchronization primitive used to coordinate access to shared mutable resources across concurrent threads, coroutines, or processes.

* **Core Purpose:**
  * **Mutual Exclusion:** Guarantees that **only one worker at a time** can execute a protected block of code (called a **critical section**).
  * **Invariant Preservation:** Ensures multi-step read-modify-write and check-then-act operations complete atomically without interference from other workers.
* **Lock Primitives in Python's Standard Library:**
  * **`threading.Lock`:** Basic non-reentrant mutual exclusion lock for threads.
  * **`threading.RLock`:** Reentrant lock that the same owning thread can acquire multiple times safely.
  * **`asyncio.Lock`:** Cooperative lock for `async`/`await` coroutines running on an event loop.
  * **`multiprocessing.Lock`:** Process-safe lock backed by OS synchronization primitives for coordinating separate processes.

## 2. `threading.Lock` (Standard Mutual Exclusion)
A **`threading.Lock`** exists in one of two states: **unlocked** (initial state) or **locked**.

### Core Methods
* **`lock.acquire(blocking=True, timeout=-1)`:**
  * If unlocked, transitions the lock to **locked** and immediately returns `True`.
  * If already locked by another thread and `blocking=True`, suspends the calling thread until the lock is released (or until `timeout` seconds expire, returning `False`).
* **`lock.release()`:**
  * Transitions the lock back to **unlocked** and wakes one waiting thread. Calling `release()` on an unlocked lock raises **`RuntimeError: release unlocked lock`**.
* **`lock.locked()`:**
  * Returns `True` if the lock is currently held, `False` otherwise (useful for diagnostics; never use it for check-then-act synchronization).

### Using `with lock:` (Context Manager Protocol)
Always acquire and release locks using a **`with` statement**. The context manager guarantees `lock.release()` executes automatically even if an exception is raised inside the critical section:

```python
import threading


class ThreadSafeCounter:
    def __init__(self) -> None:
        self._value = 0
        self._lock = threading.Lock()

    def increment(self, step: int = 1) -> int:
        with self._lock:
            # Critical section: exclusive access guaranteed
            self._value += step
            return self._value

    @property
    def value(self) -> int:
        with self._lock:
            return self._value


counter = ThreadSafeCounter()


def worker(iterations: int) -> None:
    for _ in range(iterations):
        counter.increment()


threads = [threading.Thread(target=worker, args=(5_000,)) for _ in range(4)]
for t in threads:
    t.start()
for t in threads:
    t.join()

print(f"Final counter value: {counter.value}")  # Guaranteed: 20000
```

## 3. `threading.RLock` (Reentrant Lock)
A standard `threading.Lock` does **not** track which thread currently holds it. If a thread holding a `Lock` tries to acquire that same `Lock` a second time before releasing it, **the thread deadlocks itself permanently**.

An **`RLock` (Reentrant Lock)** tracks both the **owning thread** and an **acquisition recursion count**:
* The thread that currently owns the `RLock` can call `acquire()` (or enter `with rlock:`) multiple times without blocking.
* Every acquisition increments the internal counter; an equal number of `release()` calls is required before another thread can acquire the lock.

### When to Use `RLock`
Use `RLock` when public locked methods on a class call other locked methods on the same instance (or in recursive algorithms):

```python
import threading


class Ledger:
    def __init__(self, balance: float) -> None:
        self._balance = balance
        self._lock = threading.RLock()

    def deposit(self, amount: float) -> None:
        with self._lock:
            self._balance += amount

    def withdraw(self, amount: float) -> None:
        with self._lock:
            if amount > self._balance:
                raise ValueError("Insufficient balance")
            self._balance -= amount

    def apply_fee_and_bonus(self, fee: float, bonus: float) -> float:
        # Acquires _lock at outer level, then re-acquires inside withdraw() and deposit()
        with self._lock:
            self.withdraw(fee)
            self.deposit(bonus)
            return self._balance


ledger = Ledger(balance=1000.0)
print(ledger.apply_fee_and_bonus(fee=50.0, bonus=120.0))  # 1070.0
```

## 4. Non-Blocking Acquisition and Timeouts
When a thread should not block indefinitely waiting for a busy resource (for example, skipping an optional background task or failing fast on contention), pass **`blocking=False`** or **`timeout=<seconds>`** to `acquire()`:

```python
import threading
import time

resource_lock = threading.Lock()


def try_background_sync(worker_name: str) -> None:
    # Wait at most 0.2 seconds to acquire the lock
    acquired = resource_lock.acquire(timeout=0.2)
    if not acquired:
        print(f"[{worker_name}] Resource busy; skipping sync cycle.")
        return

    try:
        print(f"[{worker_name}] Acquired lock; running sync...")
        time.sleep(0.5)
    finally:
        # Explicit release is mandatory when not using `with`
        resource_lock.release()
        print(f"[{worker_name}] Released lock.")


t1 = threading.Thread(target=try_background_sync, args=("Worker-1",))
t2 = threading.Thread(target=try_background_sync, args=("Worker-2",))

t1.start()
time.sleep(0.05)  # Ensure Worker-1 acquires the lock first
t2.start()

t1.join()
t2.join()
```

## 5. Locks in `asyncio` and `multiprocessing`

### 1. `asyncio.Lock` (Coroutine Synchronization)
In single-threaded `asyncio` programs, coroutines switch only at **`await`** points. Use **`asyncio.Lock`** with **`async with`** when a critical section contains one or more `await` expressions (such as querying and updating a shared cache or rate limiter):

```python
import asyncio


class TokenCache:
    def __init__(self) -> None:
        self._token: str | None = None
        self._lock = asyncio.Lock()

    async def get_token(self) -> str:
        # Only one coroutine refreshes the token; others wait and reuse the cached value
        async with self._lock:
            if self._token is None:
                await asyncio.sleep(0.2)  # Simulated async auth request
                self._token = "jwt_token_abc123"
            return self._token


async def main() -> None:
    cache = TokenCache()
    tokens = await asyncio.gather(cache.get_token(), cache.get_token(), cache.get_token())
    print(tokens)


if __name__ == "__main__":
    asyncio.run(main())
```

### 2. `multiprocessing.Lock` (Cross-Process Synchronization)
Because separate OS processes do not share memory, `threading.Lock` has no effect across processes. Use **`multiprocessing.Lock`** when multiple worker processes write to the same shared file, shared memory buffer (`multiprocessing.Value` / `Array`), or console output:

```python
from multiprocessing import Lock, Process
from pathlib import Path


def append_log_entry(lock: Lock, log_path: Path, worker_id: int) -> None:
    with lock:
        with log_path.open("a", encoding="utf-8") as f:
            f.write(f"Worker {worker_id} completed task\n")


if __name__ == "__main__":
    shared_lock = Lock()
    output_file = Path("worker_audit.log")
    output_file.write_text("", encoding="utf-8")

    processes = [
        Process(target=append_log_entry, args=(shared_lock, output_file, i))
        for i in range(4)
    ]
    for p in processes:
        p.start()
    for p in processes:
        p.join()

    print(output_file.read_text(encoding="utf-8").strip())
    output_file.unlink(missing_ok=True)
```

## 6. Deadlocks and Consistent Lock Ordering
A **deadlock** occurs when two or more workers wait indefinitely for locks held by one another, creating a circular dependency:
* **Thread 1** holds `Account_A.lock` and waits for `Account_B.lock`.
* **Thread 2** holds `Account_B.lock` and waits for `Account_A.lock`.

### Preventing Deadlocks with Global Lock Ordering
Always acquire multiple locks in a **deterministic, globally consistent order** (such as ascending `account_id`) regardless of which direction the operation runs:

```python
import threading


class BankAccount:
    def __init__(self, account_id: int, balance: float) -> None:
        self.account_id = account_id
        self.balance = balance
        self.lock = threading.Lock()


def transfer_funds(source: BankAccount, target: BankAccount, amount: float) -> None:
    """Transfer funds safely without deadlock by acquiring locks in account_id order."""
    if source.account_id == target.account_id:
        raise ValueError("Source and target accounts must be distinct")

    # Enforce strict global ordering by account_id
    first_lock, second_lock = (
        (source.lock, target.lock)
        if source.account_id < target.account_id
        else (target.lock, source.lock)
    )

    with first_lock:
        with second_lock:
            if source.balance < amount:
                raise ValueError("Insufficient funds")
            source.balance -= amount
            target.balance += amount


acc_1 = BankAccount(account_id=101, balance=1000.0)
acc_2 = BankAccount(account_id=202, balance=1000.0)

# Concurrent bidirectional transfers cannot deadlock because both threads lock acc_1 before acc_2
t1 = threading.Thread(target=transfer_funds, args=(acc_1, acc_2, 200.0))
t2 = threading.Thread(target=transfer_funds, args=(acc_2, acc_1, 350.0))

t1.start()
t2.start()
t1.join()
t2.join()

print(f"Account 101: {acc_1.balance} | Account 202: {acc_2.balance}")
```

## 7. Common Pitfalls and Best Practices

1. **Calling `lock.acquire()` Manually Without `try ... finally` or `with`:**
   If an exception is raised between `lock.acquire()` and `lock.release()`, the lock remains permanently locked and freezes every other thread waiting on it. Always prefer **`with lock:`** (or `async with lock:`).
2. **Holding a Lock During Slow Network or Disk I/O:**
   Executing HTTP requests, database queries, or `time.sleep()` inside a `with lock:` block forces all other threads to wait sequentially. Keep critical sections as short as possible—perform only fast in-memory state updates under the lock.
3. **Using `threading.Lock` Inside `async def` Coroutines:**
   A blocking `threading.Lock` halts the entire OS thread running the `asyncio` event loop, stalling every other coroutine (and causing immediate deadlock if the lock holder awaits on that same loop). Always use **`asyncio.Lock`** inside `async` functions.
4. **Re-Acquiring a Standard `threading.Lock` on the Same Thread:**
   Calling a locked helper method from inside another locked method on the same thread causes an instant self-deadlock with `threading.Lock`. Use **`threading.RLock`** when nested re-entry on the same thread is needed.
5. **Passing `multiprocessing.Lock` via Regular Function Arguments on Spawned Pools:**
   When using `ProcessPoolExecutor`, passing a `multiprocessing.Lock` directly to `executor.submit()` raises `RuntimeError: Lock objects should only be shared between processes through inheritance`. Initialize process locks via the pool's **`initializer`** parameter instead.

## 8. Quick Reference

| Lock Class | Module | Context Manager | Reentrant? | Scope / Intended Use |
| :--- | :--- | :--- | :--- | :--- |
| **`Lock`** | `threading` | `with lock:` | No | Mutual exclusion across threads in one process |
| **`RLock`** | `threading` | `with rlock:` | **Yes** | Nested/recursive locking by the same owning thread |
| **`Lock`** | `asyncio` | `async with lock:` | No | Mutual exclusion across coroutines on an event loop |
| **`Lock`** | `multiprocessing` | `with lock:` | No | Mutual exclusion across separate OS processes |
| **`RLock`** | `multiprocessing` | `with rlock:` | **Yes** | Reentrant locking owned by a specific OS process |
