# CPU-Bound vs. I/O-Bound Tasks in Python

## 1. Overview
Every software workload is constrained by the slowest resource in its execution path. Classifying tasks as **CPU-bound** or **I/O-bound** determines how an application scales and which concurrency or parallelism model will actually improve performance:

* **CPU-Bound Tasks:**
  Execution speed is limited by the **central processing unit (CPU)**—specifically clock speed, instruction throughput, and CPU cache/memory bandwidth. The processor remains actively computing instructions for almost the entire duration of the task.
* **I/O-Bound Tasks:**
  Execution speed is limited by **input/output (I/O) subsystems**—such as network latency, disk read/write speeds, database queries, or external API responses. The CPU spends most of its time sitting idle, waiting for external data transfers to complete.

* **Why Classification Matters:**
  Applying the wrong execution strategy produces no speedup and often degrades performance. Adding threads to a CPU-bound pure-Python loop adds lock contention under the Global Interpreter Lock (GIL), whereas spawning heavy OS processes for thousands of lightweight network requests wastes RAM and process-creation overhead.

---

## 2. Core Differences: CPU-Bound vs. I/O-Bound

| Dimension | CPU-Bound Task | I/O-Bound Task |
| :--- | :--- | :--- |
| **Primary Bottleneck** | Processor compute cycles (ALU/FPU) and cache bandwidth | Network latency, disk throughput, database or peripheral response time |
| **CPU Utilization** | High (near 100% on active cores) | Low (CPU is mostly idle waiting on external events) |
| **Execution Pattern** | Continuous computation without voluntary pauses | Frequent blocking waits interleaved with brief bursts of processing |
| **Hardware Upgrade That Helps** | Faster CPU clock speed or **more CPU cores** | Faster SSDs, higher network bandwidth, lower latency, connection pooling |
| **Scaling Strategy** | **Parallelism** across multiple CPU cores | **Concurrency** by overlapping wait times on one or more threads |
| **Best Python Tools** | `multiprocessing`, `concurrent.futures.ProcessPoolExecutor`, C-extensions (NumPy) | `asyncio`, `threading`, `concurrent.futures.ThreadPoolExecutor` |
| **Standard CPython GIL Impact** | **High** (GIL prevents multiple threads from running Python bytecode simultaneously) | **Minimal** (CPython releases the GIL during blocking OS I/O calls) |

## 3. Deep Dive: CPU-Bound Tasks

### Characteristics and Common Examples
A task is CPU-bound when the time required to complete it is governed primarily by how fast the processor can execute instructions:
* **Mathematical and Scientific Computing:** Matrix multiplication, statistical simulations, Monte Carlo methods, linear algebra.
* **Data Transformation and Parsing:** Parsing massive CSV/XML/JSON payloads, regular expression matching over large text corpora, AST analysis.
* **Media and Cryptography:** Image resizing/filtering, video transcoding, file compression (`gzip`, `lzma`), cryptographic hashing (`hashlib`, password key derivation).
* **Machine Learning:** Feature engineering over large arrays, model training, batch inference.

### Scaling CPU-Bound Work in Python (`ProcessPoolExecutor`)
Because standard CPython enforces the GIL per process, true parallel execution of pure-Python CPU work requires separate processes—each with its own Python interpreter and memory space—sized to the machine's available CPU cores (`os.cpu_count()`):

```python
from concurrent.futures import ProcessPoolExecutor
import hashlib
import os
import time


def compute_heavy_hash(seed: int, iterations: int = 400_000) -> str:
    """Perform repeated SHA-256 hashing (purely CPU-bound workload)."""
    digest = f"block-{seed}".encode("utf-8")
    for _ in range(iterations):
        digest = hashlib.sha256(digest).digest()
    return digest.hex()[:16]


def run_cpu_bound_benchmark() -> None:
    seeds = list(range(8))
    worker_count = os.cpu_count() or 4

    start_seq = time.perf_counter()
    seq_results = [compute_heavy_hash(s) for s in seeds]
    seq_elapsed = time.perf_counter() - start_seq

    start_par = time.perf_counter()
    with ProcessPoolExecutor(max_workers=worker_count) as executor:
        par_results = list(executor.map(compute_heavy_hash, seeds))
    par_elapsed = time.perf_counter() - start_par

    assert seq_results == par_results
    print(f"Sequential runtime : {seq_elapsed:.2f}s")
    print(f"Parallel runtime   : {par_elapsed:.2f}s ({worker_count} workers)")


if __name__ == "__main__":
    run_cpu_bound_benchmark()
```

## 4. Deep Dive: I/O-Bound Tasks

### Characteristics and Latency Hierarchy
A task is I/O-bound because external storage and network operations operate orders of magnitude slower than CPU registers and RAM:
* **CPU L1 Cache Access:** ~1 nanosecond
* **Main Memory (RAM) Access:** ~100 nanoseconds
* **NVMe SSD Read:** ~10–100 microseconds ($10,000\times$ slower than L1 cache)
* **Network / HTTP API Call:** ~10–500 milliseconds ($10,000,000\times$ slower than L1 cache)

Common I/O-bound workloads include:
* Calling external REST/GraphQL APIs or microservices.
* Querying relational or NoSQL databases (`PostgreSQL`, `MySQL`, `Redis`, `MongoDB`).
* Reading and writing files on local disks or cloud storage (`Amazon S3`, `GCS`).
* Handling concurrent client connections in web servers, chat systems, or message brokers.

### Scaling I/O-Bound Work in Python (`asyncio` and `ThreadPoolExecutor`)
Instead of waiting idly for one network or disk call to finish before starting the next, concurrent I/O overlaps wait periods:

```python
import asyncio
from concurrent.futures import ThreadPoolExecutor
import time


# Approach 1: Non-blocking concurrency with asyncio (best for high-scale network I/O)
async def fetch_endpoint_async(endpoint: str, latency: float = 0.4) -> str:
    await asyncio.sleep(latency)  # Simulates non-blocking socket wait
    return f"200 OK from {endpoint}"


async def run_async_io() -> None:
    endpoints = [f"/api/v1/items/{i}" for i in range(10)]
    start = time.perf_counter()
    responses = await asyncio.gather(*(fetch_endpoint_async(ep) for ep in endpoints))
    elapsed = time.perf_counter() - start
    print(f"asyncio fetched {len(responses)} endpoints in {elapsed:.2f}s")


# Approach 2: ThreadPoolExecutor (best for synchronous/blocking I/O libraries)
def fetch_endpoint_blocking(endpoint: str, latency: float = 0.4) -> str:
    time.sleep(latency)  # Releases the GIL while waiting
    return f"200 OK from {endpoint}"


def run_threaded_io() -> None:
    endpoints = [f"/api/v1/items/{i}" for i in range(10)]
    start = time.perf_counter()
    with ThreadPoolExecutor(max_workers=10) as executor:
        responses = list(executor.map(fetch_endpoint_blocking, endpoints))
    elapsed = time.perf_counter() - start
    print(f"ThreadPoolExecutor fetched {len(responses)} endpoints in {elapsed:.2f}s")


if __name__ == "__main__":
    asyncio.run(run_async_io())
    run_threaded_io()
```

## 5. How to Identify Whether a Workload Is CPU-Bound or I/O-Bound

Rather than guessing, measure the ratio between **wall-clock time** and **actual CPU execution time**:

* **`time.perf_counter()` (Wall-Clock Time):** Measures total real-world elapsed time from start to finish, including time spent sleeping or waiting on disk/network I/O.
* **`time.process_time()` (CPU Time):** Measures only the sum of user and kernel CPU time actively consumed by the current process (excludes sleep and I/O wait time).

### Diagnostic Ratio Rule
$$\text{CPU Utilization Ratio} = \frac{\Delta \text{process\_time}}{\Delta \text{perf\_counter}}$$

* **Ratio close to `1.0` (or `> 1.0` on multi-core C extensions):** Almost every millisecond of wall-clock time was spent executing CPU instructions -> **CPU-bound**.
* **Ratio close to `0.0` (e.g., `0.01`–`0.15`):** The process spent most of its elapsed time waiting on external resources -> **I/O-bound**.

### Practical Profiling Helper

```python
from collections.abc import Callable
import time
from typing import TypeVar

T = TypeVar("T")


def classify_workload(label: str, func: Callable[[], T]) -> T:
    """Measure wall-clock vs. CPU time to classify a function as CPU- or I/O-bound."""
    wall_start = time.perf_counter()
    cpu_start = time.process_time()

    result = func()

    wall_elapsed = time.perf_counter() - wall_start
    cpu_elapsed = time.process_time() - cpu_start
    cpu_ratio = cpu_elapsed / wall_elapsed if wall_elapsed > 0 else 0.0

    category = "CPU-bound" if cpu_ratio >= 0.7 else "I/O-bound"
    print(
        f"[{label}] wall={wall_elapsed:.4f}s | cpu={cpu_elapsed:.4f}s | "
        f"ratio={cpu_ratio:.2f} -> {category}"
    )
    return result


classify_workload("Sum of squares", lambda: sum(i * i for i in range(5_000_000)))
classify_workload("Simulated network wait", lambda: time.sleep(0.3))
```

*(For deeper function-level inspection, run `python -m cProfile -s tottime script.py`: high cumulative time inside `socket.recv`, `ssl.read`, or `os.read` confirms an I/O bottleneck, whereas high time in pure-Python loops confirms a CPU bottleneck.)*

## 6. Hybrid Workloads (Mixed CPU and I/O Pipelines)
Production pipelines—such as ETL jobs, document ingestion engines, and ML inference APIs—frequently combine both stages:
1. **Fetch stage (I/O-bound):** Download files or query database records concurrently.
2. **Transform stage (CPU-bound):** Parse, validate, embed, or compress data in parallel across CPU cores.
3. **Store stage (I/O-bound):** Write processed results back to storage concurrently.

In `asyncio` applications, offload CPU-heavy steps to a `ProcessPoolExecutor` using **`loop.run_in_executor()`** so heavy computation never freezes the event loop:

```python
import asyncio
from concurrent.futures import ProcessPoolExecutor


def cpu_intensive_parse(raw_payload: str) -> int:
    """Runs inside a separate worker process to avoid blocking the event loop."""
    return sum(ord(ch) * idx for idx, ch in enumerate(raw_payload))


async def process_document(
    doc_id: int,
    pool: ProcessPoolExecutor,
) -> tuple[int, int]:
    # Step 1: I/O-bound fetch
    await asyncio.sleep(0.1)
    raw_text = f"document-{doc_id}-" * 20_000

    # Step 2: CPU-bound transform offloaded to ProcessPoolExecutor
    loop = asyncio.get_running_loop()
    checksum = await loop.run_in_executor(pool, cpu_intensive_parse, raw_text)

    return doc_id, checksum


async def run_hybrid_pipeline() -> None:
    with ProcessPoolExecutor() as pool:
        tasks = [process_document(doc_id, pool) for doc_id in range(6)]
        results = await asyncio.gather(*tasks)
    print(f"Processed {len(results)} documents successfully.")


if __name__ == "__main__":
    asyncio.run(run_hybrid_pipeline())
```

## 7. Common Pitfalls and Best Practices

1. **Using Threads or `asyncio` to Speed Up CPU-Bound Pure-Python Code:**
   On standard GIL-enabled CPython builds, multithreaded CPU loops execute sequentially on a single core and suffer from GIL lock-switching overhead. Use `ProcessPoolExecutor` (or vectorized C libraries like NumPy) for CPU-bound work.
2. **Using `ProcessPoolExecutor` for I/O-Bound Tasks:**
   Spawning OS processes and pickling arguments/results across process boundaries is expensive. For network or disk I/O, `asyncio` or `ThreadPoolExecutor` achieves higher concurrency with a fraction of the memory and startup cost.
3. **Executing Blocking I/O or CPU Loops Inside `async def` Coroutines:**
   Calling `time.sleep()`, `requests.get()`, or heavy loops directly inside an `async def` function blocks the entire event loop, stalling every other active coroutine. Offload blocking I/O via `await asyncio.to_thread(...)` and CPU work via `await loop.run_in_executor(process_pool, ...)`.
4. **Over-Allocating Worker Processes Beyond CPU Core Count:**
   Setting `max_workers=64` on an 8-core machine for CPU-bound tasks causes heavy OS context-switching overhead and high memory consumption. Cap CPU-bound process pools at `os.cpu_count()`.
5. **Optimizing Without Measuring First:**
   A slow database query or unindexed lookup often masquerades as slow application code. Measure `perf_counter()` vs. `process_time()` or profile with `cProfile` before introducing multiprocessing or async complexity.

## 8. Quick Reference

| Workload Type | Diagnostic Signal (`cpu / wall`) | Recommended Execution Model | Ideal Worker Count | Key Caveat |
| :--- | :--- | :--- | :--- | :--- |
| **CPU-Bound** | Ratio $\approx 1.0$ (high CPU usage) | `ProcessPoolExecutor` / `multiprocessing` | Up to `os.cpu_count()` | Guard entry point with `if __name__ == "__main__":`; minimize `pickle` payload size |
| **I/O-Bound (Async Libraries)** | Ratio $\ll 1.0$ (low CPU usage) | `asyncio` event loop (`async`/`await`) | Bounded by `asyncio.Semaphore` | Never call synchronous blocking I/O inside `async def` |
| **I/O-Bound (Sync Libraries)** | Ratio $\ll 1.0$ (low CPU usage) | `ThreadPoolExecutor` / `threading` | Higher than core count (e.g., 10–50, tuned to external rate limits) | Protect shared mutable state with `threading.Lock` |
| **Hybrid (I/O + CPU)** | Mixed phases across pipeline | `asyncio` + `loop.run_in_executor(ProcessPoolExecutor, ...)` | Separate bounds for I/O semaphore and CPU process pool | Decouple fetch, compute, and write stages cleanly |
