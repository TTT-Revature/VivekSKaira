# Assertions and Testing Exceptions in Python

## 1. Overview
Automated tests verify software behavior through two fundamental mechanisms:
* **Assertions:** Verify that normal execution produces the expected return values, object states, or side effects.
* **Exception Testing:** Verifies that invalid inputs, edge cases, and failure modes fail predictably by raising the exact expected exception type and informative error message.

---

## 2. Python's Built-In `assert` Statement vs. Framework Assertions

### 1. The Built-In `assert` Statement
Python provides a native `assert` keyword for checking boolean conditions during development and testing:

```python
# Syntax: assert <expression>, <optional_failure_message>
total = 100
assert total == 100, f"Expected 100, got {total}"
```

* If `<expression>` evaluates to `True`, execution continues silently.
* If `<expression>` evaluates to `False`, Python raises **`AssertionError`** with the optional message.
* **Important Runtime Behavior (`python -O`):** Running Python in optimized mode (`python -O` or `PYTHONOPTIMIZE=1`) sets the built-in constant `__debug__` to `False` and **completely strips all `assert` statements from bytecode**. Therefore, never rely on `assert` for production input validation or security checks—use explicit `if ...: raise ValueError(...)` statements instead.

### 2. Why `unittest` Uses `self.assert*` Methods
Unlike bare `assert` statements:
* **`unittest.TestCase` methods** (`self.assertEqual`, `self.assertIn`, etc.) remain active even if tests run under `python -O`.
* They provide **type-aware failure diffs** (highlighting exact differing elements in lists, dictionaries, sets, and multi-line strings).

*(Note: Third-party test runners such as **`pytest`** use Python's bare `assert` keyword enhanced through **assertion rewriting**, which automatically inspects intermediate sub-expressions to display detailed diffs on failure.)*

## 3. Core Assertion Methods in `unittest`
Every class inheriting from `unittest.TestCase` provides specialized assertion methods. All `self.assert*` methods accept an optional **`msg="..."`** keyword argument to append custom diagnostic context on failure.

### 1. Equality, Identity, and Boolean Assertions

| Method | Verifies That | Notes |
| :--- | :--- | :--- |
| `self.assertEqual(a, b)` | `a == b` | Delegates to type-specific diff helpers for `str`, `list`, `dict`, `set`, `tuple` |
| `self.assertNotEqual(a, b)` | `a != b` | Fails if values are equal |
| `self.assertTrue(x)` | `bool(x) is True` | Use for truthy checks; prefer `assertEqual(x, True)` for strict boolean equality |
| `self.assertFalse(x)` | `bool(x) is False` | Use for falsy checks; prefer `assertEqual(x, False)` for strict boolean equality |
| `self.assertIs(a, b)` | `a is b` | Checks exact object identity in memory (`id(a) == id(b)`) |
| `self.assertIsNot(a, b)` | `a is not b` | Checks that two references point to distinct objects |
| `self.assertIsNone(x)` | `x is None` | Preferred way to assert `None` over `assertEqual(x, None)` |
| `self.assertIsNotNone(x)` | `x is not None` | Preferred way to assert a non-`None` result |

### 2. Membership, Type, and Numeric Assertions

| Method | Verifies That | Example |
| :--- | :--- | :--- |
| `self.assertIn(item, container)` | `item in container` | `self.assertIn("token", response_headers)` |
| `self.assertNotIn(item, container)` | `item not in container` | `self.assertNotIn("password", user_dict)` |
| `self.assertIsInstance(obj, cls)` | `isinstance(obj, cls)` | `self.assertIsInstance(result, UserProfile)` |
| `self.assertAlmostEqual(a, b, places=7)` | `round(a - b, places) == 0` | `self.assertAlmostEqual(0.1 + 0.2, 0.3, places=7)` |
| `self.assertGreater(a, b)` / `assertLess(a, b)` | `a > b` or `a < b` | `self.assertGreater(latency_ms, 0)` |
| `self.assertGreaterEqual(a, b)` / `assertLessEqual(a, b)` | `a >= b` or `a <= b` | `self.assertLessEqual(retry_count, 3)` |

### 3. Collection and Sequence Assertions

| Method | Purpose | Example |
| :--- | :--- | :--- |
| `self.assertCountEqual(seq1, seq2)` | Asserts both sequences contain the **exact same elements with the same frequencies**, regardless of order | `self.assertCountEqual(["a", "b", "a"], ["a", "a", "b"])` |
| `self.assertListEqual(l1, l2)` | Compares two lists element by element with index-level diff output | `self.assertListEqual(actual_ids, [101, 102])` |
| `self.assertDictEqual(d1, d2)` | Compares two dictionaries and reports missing, extra, or mismatched keys | `self.assertDictEqual(actual_cfg, expected_cfg)` |
| `self.assertSetEqual(s1, s2)` | Compares two sets and lists items missing from either side | `self.assertSetEqual(actual_tags, {"api", "v2"})` |

## 4. Testing Exceptions in `unittest`
When a function is expected to reject invalid input or signal a domain error, use **`self.assertRaises()`** or **`self.assertRaisesRegex()`** as a **`with` context manager**.

### Sample Production Module
```python
# File: src/accounts.py
class InsufficientFundsError(Exception):
    """Raised when a withdrawal exceeds the available account balance."""

    def __init__(self, balance: float, attempted: float) -> None:
        self.balance = balance
        self.attempted = attempted
        super().__init__(f"Cannot withdraw {attempted:.2f}; available balance is {balance:.2f}")


def withdraw(balance: float, amount: float) -> float:
    if amount <= 0:
        raise ValueError("Withdrawal amount must be positive")
    if amount > balance:
        raise InsufficientFundsError(balance=balance, attempted=amount)
    return round(balance - amount, 2)
```

### 1. Verifying Exception Type and Inspecting the Exception Object (`assertRaises`)
Binding the context manager (`as ctx`) captures the raised exception instance on **`ctx.exception`** so you can assert on its message, `.args`, or custom attributes:

```python
# File: tests/test_accounts.py
import unittest
from src.accounts import InsufficientFundsError, withdraw


class TestWithdrawExceptions(unittest.TestCase):
    def test_non_positive_amount_raises_value_error(self) -> None:
        with self.assertRaises(ValueError) as ctx:
            withdraw(balance=500.0, amount=0.0)

        self.assertEqual(str(ctx.exception), "Withdrawal amount must be positive")

    def test_overdraft_raises_custom_exception_with_metadata(self) -> None:
        with self.assertRaises(InsufficientFundsError) as ctx:
            withdraw(balance=100.0, amount=250.0)

        # Assert custom attributes attached to the exception instance
        self.assertEqual(ctx.exception.balance, 100.0)
        self.assertEqual(ctx.exception.attempted, 250.0)
```

### 2. Verifying Exception Type and Message Pattern Together (`assertRaisesRegex`)
**`self.assertRaisesRegex(ExceptionType, pattern)`** checks both the exception class and that `str(exception)` matches a regular expression—useful when a function can raise the same exception type (such as `ValueError`) for several distinct reasons:

```python
class TestWithdrawRegex(unittest.TestCase):
    def test_overdraft_error_message_contains_amounts(self) -> None:
        with self.assertRaisesRegex(InsufficientFundsError, r"Cannot withdraw 250\.00.*100\.00"):
            withdraw(balance=100.0, amount=250.0)
```

### 3. Accepting Multiple Exception Types
Pass a **tuple of exception classes** when any one of several specified exceptions is valid:

```python
with self.assertRaises((ValueError, TypeError)):
    withdraw(balance=100.0, amount=-10.0)
```

## 5. Testing Exceptions in `pytest` (`pytest.raises`)
In codebases using `pytest`, exception testing uses **`pytest.raises()`** with an optional **`match=`** regular expression parameter:

```python
import pytest
from src.accounts import InsufficientFundsError, withdraw


def test_withdraw_negative_amount_raises_value_error() -> None:
    with pytest.raises(ValueError, match=r"must be positive"):
        withdraw(balance=200.0, amount=-5.0)


def test_withdraw_overdraft_captures_exception_info() -> None:
    with pytest.raises(InsufficientFundsError) as exc_info:
        withdraw(balance=50.0, amount=75.0)

    assert exc_info.value.balance == 50.0
    assert exc_info.value.attempted == 75.0
```

## 6. Testing Exception Chaining (`__cause__`)
When service or repository layers catch low-level exceptions (such as `OSError` or `sqlite3.Error`) and re-raise a domain exception using **`raise DomainError(...) from original_exc`**, verify that the underlying cause is preserved on **`ctx.exception.__cause__`**:

```python
class StorageError(Exception):
    pass


def load_config_file(path: str) -> str:
    try:
        with open(path, encoding="utf-8") as f:
            return f.read()
    except FileNotFoundError as exc:
        raise StorageError(f"Missing config file: {path}") from exc
```

```python
class TestExceptionChaining(unittest.TestCase):
    def test_missing_file_chains_file_not_found_cause(self) -> None:
        with self.assertRaises(StorageError) as ctx:
            load_config_file("non_existent_settings.json")

        self.assertIsInstance(ctx.exception.__cause__, FileNotFoundError)
```

## 7. Common Pitfalls and Best Practices

### 1. Putting Multiple Statements Inside a Single `with assertRaises(...)` Block
Only place the **single line of code expected to raise the exception** inside the `with` block. If an earlier setup call raises the same exception type prematurely, the test passes without ever executing the target call:

```python
# PITFALL: If setup_invalid_state() raises ValueError, withdraw() never even runs!
with self.assertRaises(ValueError):
    account = setup_invalid_state()
    withdraw(account.balance, -10.0)

# CORRECT: Arrange outside the with-block; isolate only the target call inside
account = setup_valid_state()
with self.assertRaises(ValueError):
    withdraw(account.balance, -10.0)
```

### 2. Calling the Function Directly Inside `assertRaises()` Without `with`
Writing `self.assertRaises(ValueError, withdraw(100.0, -5.0))` invokes `withdraw()` *before* `assertRaises` starts listening, crashing the test with an unhandled `ValueError`. Always use the **`with self.assertRaises(...):`** context manager form.

### 3. Catching Overly Broad Exceptions (`Exception` or `BaseException`)
Writing `with self.assertRaises(Exception):` will pass even if your code fails due to an unintended `TypeError`, `KeyError`, or `AttributeError` bug. Always assert the **most specific exception class** expected.

### 4. The Python `assert` Tuple Trap
Adding parentheses around an `assert` expression and message turns them into a 2-element tuple, which is **always truthy** and never fails:

```python
# PITFALL: Always passes (and triggers a SyntaxWarning)!
assert (1 == 2, "Numbers do not match")

# CORRECT: No outer parentheses around condition and message
assert 1 == 2, "Numbers do not match"
```

### 5. Using `assertEqual` for Floating-Point Arithmetic
Binary floating-point precision artifacts (`0.1 + 0.2 == 0.30000000000000004`) cause exact `assertEqual(0.1 + 0.2, 0.3)` checks to fail. Use **`self.assertAlmostEqual(0.1 + 0.2, 0.3, places=7)`** (or `pytest.approx(0.3)` in `pytest`).

## 8. Quick Reference

| Construct / Method | Purpose |
| :--- | :--- |
| `assert cond, "msg"` | Built-in Python assertion (disabled when running `python -O`) |
| `self.assertEqual(a, b)` | Asserts `a == b` with detailed collection/string diffing |
| `self.assertAlmostEqual(a, b, places=7)` | Asserts floating-point equality within specified decimal places |
| `self.assertIsNone(x)` / `assertIsNotNone(x)` | Asserts `x is None` or `x is not None` |
| `self.assertIn(item, seq)` / `assertCountEqual(a, b)` | Asserts membership or order-independent element equality |
| `with self.assertRaises(ExcType) as ctx:` | Asserts `ExcType` is raised and captures instance on `ctx.exception` |
| `with self.assertRaisesRegex(ExcType, r"..."):` | Asserts `ExcType` is raised and its message matches the regex |
| `with pytest.raises(ExcType, match=r"..."):` | Equivalent exception assertion context manager in `pytest` |
| `ctx.exception.__cause__` | Inspects the original chained exception raised via `raise ... from ...` |
